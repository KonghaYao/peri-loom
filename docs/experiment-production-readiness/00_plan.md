# v1.0.1 生产能力模拟验收计划

## 问题与范围

判断已发布的 v1.0.1 镜像在单机容器和隔离对象存储模拟环境中，是否具备异常中断恢复、灾难恢复、高可用能力。既有的正常停机后原卷重启验收作为对照，不重新定义生产标准。

## 成功标准

1. 异常中断：已确认写入的数据在容器被强制终止后，无人工绕过安全标记即可重新对外服务，且数据一致。
2. 灾难恢复：通过有记录的备份和恢复步骤，在新的宿主卷上恢复同一数据库和凭据，并读回已确认写入，报告 RPO/RTO。
3. 高可用：单个应用实例或宿主卷故障后，另一实例可自动接管同一服务身份并继续成功读写，报告中断时间。

如系统有意拒绝不安全恢复，记录为“安全拒绝通过、可用性未通过”，不能把安全拒绝误报为恢复成功。

## 实验设计

| 轮次 | 自变量 | 观测值 | 控制变量 |
| --- | --- | --- | --- |
| 1 | 干净 TERM 与异常 KILL；原卷与替代卷 | 退出码、启动结果、TLS/SQL、确认写入读回、Authority 标记 | 固定 v1.0.1 镜像、独立 Docker 卷、同一数据库 |
| 2 | 单实例故障、应用卷丢失、对象存储恢复 | 自动接管、恢复步骤、RPO/RTO、读写结果 | 同镜像、独立对象存储命名空间、同一服务身份 |

先做实验 1 与独立验证，再依据其结果收窄实验 2。每轮保留可复现命令和脱敏证据；不触碰其他现有容器、卷、桶或用户未提交的文件。最后综合结论并进行对抗审查。Docker Desktop/OrbStack 仿真结果只能证明被测环境中的行为，不能替代 Linux 多主机生产演练。

## 继续验收：四项能力逐项闭环

前两轮已测本地 `local` 后端的异常拒绝和干净冷克隆，但还没有覆盖生产部署使用的 S3 后端、源卷不可用时的预先备份恢复或真实故障后的自动接管。后续以同一发布镜像及各自独立的新 Docker 网络、卷、容器、桶补齐：

| 能力 | 后续实际故障注入与通过条件 | 失败条件与证据 |
| --- | --- | --- |
| 1. 干净停机后恢复 | S3 隔离桶中确认 SQL 写入；`TERM` 完整退出后从同一持久状态再次启动，读回同库同凭据同写入 | 进程无法就绪、身份改变或已确认写入不可读；记录终止证明、状态、请求结果 |
| 2. 异常中断后恢复 | S3 隔离桶中确认写入并 `SIGKILL`；不修改安全标记，原卷重启并检查同一 SQL 写入 | 无法就绪即恢复能力失败；dirty 安全拒绝单独记为安全通过 |
| 3. 灾难恢复 | 在故障前制作独立、可校验的状态卷与 S3 对象备份；使原卷与原对象存储不可用于恢复；从备份重建新卷和新桶，读回备份前确认写入，量化备份后写入损失与恢复时长 | 不能从预先备份恢复、身份不一致、已承诺的 RPO/RTO 不可测或无正式机制；明确区分模拟演练与生产验收 |
| 4. 高可用与自动接管 | 对同一客户端入口持续查询/写入并故障注入；在单实例故障时，无人工操作，由另一个实例接管同一身份且已确认写入一致，记录失败窗口 | 没有接管、需要人工操作或出现双主；同卷/跨卷 fencing 与服务入口独立核验 |

以上四项以“完成实际检测并判定通过、失败或未能验证”为测试闭环；能力本身只有满足对应通过条件才能判定具备。不得把拒绝不安全恢复或手动冷克隆计作自动恢复、灾难恢复或 HA。每轮由不同 subagent 复核脱敏原始证据，最后更新 `conclusion.md` 并进行对抗审查。
