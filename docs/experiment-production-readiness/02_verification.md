# 验证报告 2：同卷并发启动与正常停机后的新卷冷恢复

## 总体评估：PARTIAL

报告的两个**窄结论**有证据支持：本次同卷第二实例被启动器拒绝，主实例随后仍能读写；正常 `TERM` 后，从仍可读取的完整源卷手动冷拷贝到新卷，恢复实例成功启动并读回两条写入。它没有满足计划中的灾难恢复或高可用成功标准。验证仅只读检查了保留的 Docker 资源、私有证据和脚本，没有重跑或清理资源，也没有输出凭据。

## 逐维度评估

### 数据完整性：PARTIAL

- 当前 Docker 中有本轮标签对应的四个容器和三个卷。四个容器镜像 ID 相同，`main` 与 `second` 挂同一源卷，两个恢复容器分别挂新卷；应用容器的默认用户、启动参数、资源限制和无自动重启配置与报告一致。`second` 的保留状态为 `ExitCode=1, OOMKilled=false`，其带时间戳原始日志为 `runtime directory already has an active launcher`；其余三个容器最终退出码均为 0。
- `evidence.jsonl` 有 73 条带 UTC 时间的记录，包括主实例就绪、第二实例启动与退出、两次写入确认、主实例在竞争者退出后的两行查询、`TERM` 后 `docker wait` 输出 `0`、clean 标记、冷拷贝及两次恢复读回。私有文件中的 clean 标记为 `636c65616e0a`；938 字节终止证明的 SHA-256 与报告一致。原始 `docker` 命令、返回码和部分输出也有保存，比第一轮的布尔摘要更完整。
- 首次普通 PAX 归档哈希确实不等；随后排除 atime/ctime 的稳定归档哈希在源卷、首个目标卷和第二个目标卷均为 `00667f58ccaacb3cabc676dc22e41d229b551bcf482a0b6a56999e1e0a53a403`。归档命令使用 `--xattrs --acls --numeric-owner`，源卷在复制与归档时以只读方式挂载。首次不等由 atime/ctime 导致是合理解释，但保留证据没有逐项 PAX 差异，不能独立证明这是唯一差异。
- SQL 证据保存了 `{"executed": true}`、行数、`matched=true`、值与查询结果哈希，以及计算哈希的脚本；SQL 响应正文和脱敏后的行值未保存。因此可核对脚本断言和前后哈希相等，无法在不重新查询的条件下独立重算结果哈希或逐值核验两条写入。报告所称另行使用 `find` 比对路径、mode、UID、GID、大小和 mtime，在保留的 `evidence.jsonl` 中未见命令和输出，应视为未留存的补充观察。

### 方法正确性：PARTIAL

- 同卷竞争测试使用相同镜像、挂载路径和启动参数；第二实例启动时主实例仍运行。第二实例退出后，主实例再次确认写入并读回两行，足以检验这次并发尝试没有立即破坏主实例的基本读写。只有一次竞争试验，不能估计偶发竞态或所有并发启动时序。
- 冷拷贝发生在主实例 `TERM` 正常退出之后，源卷只读挂载，新卷此前创建；归档传输使用 GNU tar，并对两侧做稳定归档哈希比对。两个新卷分别启动并完成 SQL 读回，增强了这一特定路径的可重复性。读回依赖脚本保留的断言与哈希，独立审计能力仍受上述脱敏证据限制。
- 实验变量已按第一轮反馈收窄，但本轮没有模拟源卷丢失、远端或定期备份、原实例故障后的自动接管，也没有同一服务入口的切换测试。源卷可用、数据量很小、镜像已在本机、操作者预先知道步骤；这些条件与计划中的灾难恢复及高可用故障条件不同。首次恢复的 58.976 秒包含人工排查；第二次 2.440 秒是本地连续手动流程耗时，均不能作为实际故障 RTO。

### 结论合理性：PASS

- `docker start` 返回 0 与业务就绪被正确区分：第二实例随后于 `04:06:00.402357954Z` 以 1 退出，没有新的 `ready`；原实例的后续写入和两行读回有脚本记录。启动器拒绝并发挂载的窄结论成立；不能由此推断自动接管能力。
- 新卷归档哈希相等、恢复实例有新 `ready`、TLS 校验成功、数据库与凭据比较为相等，以及恢复前后两行查询哈希相等，共同支持这次 clean 冷恢复的结论。相同 CA 和服务端证书文件的哈希也与同一服务身份相符。这些观察不覆盖第一轮 KILL 后 dirty 标记的恢复路径。
- 报告明确将 2.440 秒限定为本机手动冷恢复测量，没有命名为 RTO；也没有从两条备份前写入的读回推断持续备份 RPO。按计划，RPO 需要定义可恢复的最近确认写入相对故障时刻的时间差；RTO 需要从故障发生到同一服务恢复可用的时间。两者本轮均未测得，HA 中断时间亦未测得。

### 报告质量：PARTIAL

- 报告区分了历史观察、当前资源状态、手动恢复耗时及未证实的生产目标；保留了私有证据路径和实际脚本，没有在文档中公布凭据。首次哈希不等也如实披露。
- 私有临时目录是主要证据载体，尚无可长期保存、可供第三方复算的脱敏 SQL 结果和元数据比对输出。`find` 比对的表述应附原始证据，或标明为未留存观察。脚本分为失败后继续执行的 `run.py`、`continue.py`、`timed.py`，报告应明确其执行顺序，以及稳定归档哈希是在首次普通归档哈希失败后采用的校正方法，以免读者误以为首次流程一次通过。

## 关键问题与改进建议

1. **SQL 读回仍主要依赖脚本断言。** 后续隔离实验保存不含凭据与原值的规范化结果，例如每行随机值哈希、排序规则、行数、SQL 状态码和请求时刻，使第三方可核对每次确认写入与恢复后的读回对应关系。
2. **元数据比对缺少原始记录。** 将 `find` 命令、退出码和脱敏输出或结果哈希写入证据；对首次 PAX 哈希不等保存字段级差异，才可确证 atime/ctime 是唯一原因。
3. **生产目标尚无故障路径证据。** 若继续验收灾难恢复，需使用独立、预先存在的备份并令源卷不可用，记录备份时点、最后确认写入、故障时刻与新卷读回；若验收 HA，需记录自动故障检测、同一入口接管及成功读写的时间线。均应使用新隔离资源，不复用本轮保留资源。

## 上一轮反馈的处理情况

第一轮要求保留命令、返回码、时间戳和脱敏 SQL 证据，本轮已保存逐步 Docker 命令与状态、带时间戳事件、写入确认及查询哈希；SQL 结果本身仍无法独立复算。第一轮指出的正常停机对照和替代卷观测，本轮以 clean `TERM` 后新卷冷恢复覆盖了一条受控路径，但未覆盖 KILL 后替代卷恢复。灾难恢复、RPO/RTO、自动接管与 HA 中断时间仍未完成计划中的验收。
