# 当前工作树镜像四项 S3 模拟：对抗审查

审查对象：[实验报告](./10_current_sim_report.md)、[独立核验](./10_current_sim_verification.md)、本轮私有事件与驱动脚本。审查仅做只读检查，未操作容器、卷或对象存储；私有证据目录为 `/tmp/peri-current-sim-a7c9`，本文不记录凭据和探针原值。

## 裁定

**CONCLUSION_WEAKENED。** “这枚本地镜像在四条指定路径上分别表现为干净重启成功、脏重启未恢复、冷备份恢复成功且丢失备份后写入、预建备用约 60 秒内未接管”有连贯的事件和资源证据。没有发现足以推翻这些**观察结果**的矛盾。应降低两项更强主张的置信度：镜像与指定工作树源码的精确对应关系，以及脏标记是启动失败的唯一原因。手动 DR 的秒数和 HA 失败窗口也不能充当生产目标值。

## 影响本轮结论的攻击

| 攻击 | 严重性 | 证据与影响 | 可证伪的补证方式 |
| --- | --- | --- | --- |
| 本地镜像缺少源码到二进制的独立证明 | **严重，削弱“当前工作树代码”归因** | 三套有效驱动以同一 Docker image ID 创建应用，镜像创建时间和架构一致；当前 HEAD 及两处 diff 哈希可复算。但私有证据没有完整构建命令、构建日志、构建上下文摘要或构建 attestation。标准构建下载超时后使用临时 Go 基底，增加了未冻结输入。因而可以判断**被测本地镜像**的行为，不能独立证明它恰好包含报告所述全部源码，也不能外推到 GHCR 发布镜像。见核验报告“镜像与实验边界”，以及 `dr_current.py`、`clean_dirty.py`、`ha_current.py` 的 image ID 固定方式。 | 保留可复现的构建命令、完整构建日志、基底 digest、构建上下文及产物哈希；从冻结提交和补丁重建，并比较二进制或提供可核验 provenance；再对目标发布 digest 重测。 |
| “安全拒绝生效”的因果解释没有被直接隔离 | **中等，削弱原因判定；不推翻未恢复事实** | 干净重启 `wait=0`、marker 为 `clean\n`、SQL 重读成功；KILL 后 `wait=137`、marker 为 `dirty\n`、再次启动后进程退出 1。HA 备用也退出 1、无 ready，固定入口 56 次探测失败。源码 `prototypes/v1/src/authority_rpc/startup.rs` 确有 dirty marker 检查，但现存简短启动日志没有独立给出可归因的拒绝原因。其他启动失败因素尚未被对照排除。报告可写“与 dirty guard 拒绝一致”，保留“未恢复”的强结论。 | 在同一冻结镜像和数据快照上采集结构化启动错误码，或用受控的 clean/dirty 状态对照实验；同时验证后端 seal、进程退出码和 SQL 状态。不可在原证据卷上改 marker。 |
| 干净/脏重启脚本未严格检查 SQL execute 回执的值 | **轻微，略削弱 ACK 用词** | `clean_dirty.py` 的 `write_read()` 记录 `ack_type`，没有像 DR 和 HA 驱动那样断言 `{"executed": true}`。不过请求正常返回且故障前逐值 SQL 读回匹配，因此写入可见性证据仍成立。 | 在新实验中断言回执内容，并保留脱敏的响应结构及写入后读回摘要。 |

## 仅影响生产推广的缺口

| 攻击 | 严重性 | 证据与影响 | 可证伪的补证方式 |
| --- | --- | --- | --- |
| DR 时钟起点与指标定义窄于生产 RTO/RPO | **严重，阻止使用 `3.696s`/`4.330s` 作为生产承诺** | `04_dr_driver.py` 在两源容器已 KILL 且 `docker wait` 返回后才记录 `source_fault`；RTO 不含故障检测和两次 KILL 耗时。RPO 是故障时可恢复 ACK A 的年龄，备份后 ACK B 实际丢失 1 笔；它不是周期备份的最坏数据丢失上界。恢复过程包括本机移除源卷、解包、预热镜像启动和小规模数据读回。数值计算本身与单调时钟证据一致。 | 先定义业务可接受的 RPO/RTO，再在持续写入、定期备份、跨故障域恢复中，从实际故障发生/首次服务不可用到固定客户端入口恢复读写计时，并报告多轮分布及最坏值。 |
| “独立备份”仅独立于源卷，不独立于宿主故障域 | **严重，阻止灾备验收** | 两份归档和恢复卷位于同一宿主；测试确实在恢复前移除了本轮源容器与源卷，并核对两个归档哈希、13 个对象清单及 A/B 结果。这证明本机冷备份恢复，不证明宿主或机房丢失时仍有备份。 | 将备份移到另一故障域，校验保留、恢复权限、对象与应用状态的一致性，并在源宿主不可用时重演。 |
| HA 只测试单宿主、共享应用卷和外部 watcher 的特定接管路径 | **严重，限制失败结论的范围** | watcher 故障前就位，检测主进程退出后 `docker start` 备用；它不是产品控制器。主备共享 Docker 卷和 RustFS，不能模拟网络分区、主机失联或旧主复活；固定 TLS 入口约 60 秒不可用足以判定**该路径**失败，不能推出所有编排下都不会接管。反过来，实验也没有证明任何生产级自动 HA 能力。 | 用独立主机/故障域、真实控制器、固定客户端入口和持续读写探针测切换；加入网络分区及旧主复活，验证全局 fencing、无双主及 ACK 一致性。 |
| 逻辑隔离不等于性能或故障域隔离 | **中等，影响时延与可复现性** | 每场景有独立 owner、网络、卷、桶和回环端口；应用设了 CPU/内存限制，但场景仍共享 Docker daemon、宿主 CPU/磁盘和本地镜像缓存。RustFS 是固定本地 digest，未模拟云 S3 延迟、一致性与服务故障。单次小数据运行不能估计尾延迟或长期稳定性。 | 在隔离或记录负载的环境中重复运行，记录资源占用与时延分布；用目标对象存储和生产规模数据复测。 |
| 恢复后的客户端入口未保持不变 | **中等，限制 DR 端到端解释** | DR 的 `same_endpoint` 指应用看到的 S3 名称 `http://rustfs:9000`；恢复应用的宿主 TLS 端口由 Docker 重新分配。已验证恢复实例的 TLS SQL 读回，没有验证原客户端 URL 继续可用。 | 使用固定入口或真实路由，在恢复前后用同一客户端配置连续探测读写。 |

## 四项结果的保留范围

1. **干净重启：保留“本轮通过”。** TERM 退出 0、`clean\n`、ready 事件从 1 到 2，同库同 key 且故障前行摘要一致；这是单次、同卷同桶的功能检查。
2. **脏重启：保留“本轮业务未恢复”。** KILL 退出 137 后新进程退出 1，没有故障后 SQL 读回。将“dirty guard 导致拒绝”表述为与观测及源码一致的推断。
3. **手动 DR：保留“本机冷备份恢复 A，丢失 B”。** 归档与对象清单核对支持此结果；RPO/RTO 仅按脚本时间区间解释。
4. **预建备用 HA：保留“指定接管路径约 60 秒未恢复”。** watcher 及备用启动事件早于 56 次失败探测；最终恢复时间未知，也未覆盖其他部署拓扑。

**最终判断：** 本轮四条模拟路径的观察结论成立；“当前源码已经具备生产 DR/HA 能力”不成立，且本地镜像的构建溯源需补齐后才能将结果严格归因到当前工作树。
