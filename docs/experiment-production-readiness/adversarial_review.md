# 对抗验证报告：v1.0.1 生产能力模拟验收

## 总结

两轮实验足以说明：在所测单宿主 `local` 配置中，一次 KILL 后原卷直接重启没有恢复服务；一次 clean TERM 后完整卷冷拷贝能够在新卷读回两笔写入；运行中的实例阻止了同卷第二启动。它们不足以证明产品在所有生产配置中客观上“不具备”灾难恢复或高可用，也不足以把冷拷贝称为安全的服务身份迁移。综合结论作为**本计划的验收结果**成立，作为**产品能力的普遍事实**需要收窄。以下只读审查了所列报告、保留的第 2 轮证据与源码/部署模板；未重跑或更改资源。

## 攻击结果

### 攻击 1：验收失败与能力不存在被混同

- **目标结论**：`conclusion.md` 的“尚不具备可验收的生产能力”，尤其“灾难恢复与 HA 未证实”被读作“产品不具备灾难恢复与 HA”。
- **攻击角度**：逻辑链、外部效度。
- **攻击内容**：灾难恢复和故障后自动接管根本未按计划执行；未证实只能得出“未达到本次验收标准”，不能得出对所有部署和运维方案的能力否定。相反，KILL 后**原卷直接重启**确实未通过计划中无人工干预的异常恢复标准。部署文档本身明确将镜像定为预览版，并声明 dirty restart、DR、HA 尚未完成生产验证；Helm 模板固定 `replicas: 1`、`Recreate`、`ReadWriteOnce`，支持“此模板不提供 HA”的较窄判断。第 2 轮使用 `--backend local`，而根 Compose 部署使用 `s3`，也不能把所测结果直接归给后者。
- **严重程度**：严重，影响综合标题和适用范围，不推翻单次 KILL 失败。
- **建议处理**：改为“v1.0.1 在本计划与已测配置下未通过生产能力验收；DR/HA 尚无合格证据”。分别标明“已测失败”和“未测试”。若要支持生产配置判断，按固定镜像在隔离 S3、实际部署配置及多主机故障域完成故障演练。

### 攻击 2：完整冷备份复制了服务身份，却没有排除双主

- **目标结论**：“正常停机后冷恢复有限通过”及“同库同凭据”作为迁移的正面证据。
- **攻击角度**：遗漏、方法论。
- **攻击内容**：两次恢复把整个状态树复制到独立卷，报告确认数据库和凭据逐值相等。`dev.py` 的 `acquire_run_lock()` 使用运行目录内 `launcher.lock` 的 `flock`，同卷竞争会被拒绝；不同卷的锁不共享。`prepare()` 对现有状态检查卷内 owned stop proof、终止证明与 clean Authority 标记，然后消费本**卷**的证明。由此无法从“同卷第二实例被拒绝”推出“两个克隆卷不会以同一身份同时服务”。本轮两个恢复实例先后启动，没有测克隆卷并行启动、旧源卷被误重启、旧端点隔离或外部 fencing。现有证据也**不能证明已发生双主**；这是冷备份复用身份后的未排除风险。
- **严重程度**：严重，影响冷恢复可作为安全运维步骤的解释。
- **建议处理**：把“同身份读回”限定为功能观察，给出源卷销毁/隔离、旧身份撤销或外部租约/fencing 的可审计协议。在新隔离资源中验证两个 clean 克隆卷并行启动时至多一个能对同一服务身份成功写入；同时验证旧源卷重启及网络分区场景。该演练前不要把卷复制流程定为可安全重复执行的正式恢复手册。

### 攻击 3：单宿主 local 仿真不能覆盖 S3 与故障域

- **目标结论**：两轮结果对“生产能力”的外推。
- **攻击角度**：外部效度、混淆变量。
- **攻击内容**：两轮均为同一 Docker daemon 上的 `local` 后端；第 2 轮 `linux/amd64` 镜像还在 `arm64` 宿主上运行。根 Compose 则使用 S3，并需同时保护私有状态与外部对象；第 2 轮只复制本地状态，源卷仍可读。该环境未施加宿主丢失、跨宿主卷挂载、真实 S3 一致性、网络分区、备份滞后或同一客户端入口切换。因此 2.440 秒仅是预热本机上小数据量的手动复制与读回耗时，不能成为故障 RTO；两笔备份前写入读回也不能成为 RPO。
- **严重程度**：严重，限制 DR/HA 结论与时间指标。
- **建议处理**：保持结论对 2.440 秒和两笔写入的现有限定；另外使用故障前已存在的独立备份，在源卷不可用、S3 对象与私有状态联合恢复条件下测 RPO/RTO，并在不同故障域测试自动接管和持续客户端请求。

### 攻击 4：SQL 历史结果难以独立复算

- **目标结论**：两笔确认写入在新卷完整读回，及第 1 轮 KILL 前写入已确认。
- **攻击角度**：数据可审计性。
- **攻击内容**：第 1 轮只有脚本摘要，没有保存可脱敏复核的原始 SQL 请求/响应；第 2 轮 `evidence.jsonl` 保存 `{"executed": true}`、行数、`matched=true`、值哈希与查询结果哈希，但没有可由第三方独立重算的行内容或规范化逐行哈希清单。第 2 轮的归档哈希与恢复前后查询哈希相等、两次新卷成功读回，仍为这条窄结论提供相互支持，不能因此断言数据不一致。首次普通 PAX 归档哈希不等；atime/ctime 解释合理，但没有字段级差异证据证明它们是唯一差异。
- **严重程度**：中等，降低数据完整性证据置信度，不推翻服务退出和启动观察。
- **建议处理**：后续保存请求时间、SQL 状态、行数、稳定排序后的每行随机值哈希及计算规则，让审查者可从保留证据复算前后对应关系；保存元数据比对命令/退出码与 PAX 字段差异。第 1 轮历史过程无法事后补成原始证据，只能在新资源复验。

### 攻击 5：同卷竞争没有检验故障接管

- **目标结论**：“本次同卷第二实例不能并发接管”的 HA 关联表述。
- **攻击角度**：实验变量与因果链。
- **攻击内容**：第二实例在主实例健康、仍占有锁时启动，`runtime directory already has an active launcher` 与退出码 1 证实了此时的互斥行为。它既没有模拟主实例故障，也没有使用同一服务入口、自动检测或接管控制器。因此它不能测试“故障后是否可接管”，更不能给出 HA 中断时间。此拒绝本身是预期安全行为，不能单独作为 HA 缺陷证据。
- **严重程度**：中等，影响对该项实验的解释；综合报告已将 HA 列为未证实。
- **建议处理**：把该行写成“健康主实例运行期间同卷第二启动被拒绝”；单独安排故障后接管测试，并检查旧实例 fencing、同一入口和确认写入一致性。

## 综合评估

| 攻击 | 严重程度 | 结论是否仍成立 |
| --- | --- | --- |
| 验收失败与能力不存在混同 | 严重 | 验收未通过成立；普遍能力否定被削弱 |
| 冷备份身份复制与双主风险 | 严重 | 单次冷读回成立；安全迁移未证实 |
| 单宿主 local 与生产 S3 差异 | 严重 | 本机观察成立；生产外推被削弱 |
| SQL 结果无法独立复算 | 中等 | 窄结论有支持，置信度应维持中等 |
| 健康实例竞争不等于故障接管 | 中等 | 互斥观察成立；HA 仍未证实 |

## 最终裁定

**CONCLUSION_WEAKENED**。应保留“本计划未通过生产能力验收”和三个已观察到的窄结果；把总判定明确限定于所测镜像、`local` 单宿主配置与既定验收标准。DR/HA 应维持“未证实”，不能写成实验已证明其不存在。冷拷贝应标为“可读回的手动克隆”，直到独立证明旧副本隔离及同身份克隆不会双主，才可作为安全恢复方案验收。
