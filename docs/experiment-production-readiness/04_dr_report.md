# 实验 4：独立 S3 与应用卷的预先备份恢复

执行时间：2026-10-15 05:26 UTC。固定应用镜像为 `ghcr.io/konghayao/peri-loom@sha256:901f37f2cceb62bf265072e5b0159fa86974af3440a79383ba31e351c0895333`，对象存储为本机已缓存且以 digest 固定的 RustFS 1.0.1。实验脚本为 [`04_dr_driver.py`](./04_dr_driver.py)。本次使用全新随机标签 `peri.dr.owner=a245460bf8a0d3083fb30f6151361b11`、独立 Docker 网络、桶、应用卷和 RustFS 卷；与现有服务和其他实验资源隔离。

## 方法与结果

1. 在隔离 S3 桶上启动应用，以项目凭据和 TLS 连接执行写入 A，收到 SQL execute 确认并立即逐值读回。
2. 应用正常 TERM 退出，Authority 标记为 `clean\n`。列举桶内所有当前对象并逐个 GET 计算大小与 SHA-256；停止对象存储后，对整个应用卷和对象存储卷做冷 tar 备份、计算 SHA-256，备份文件独立保存在宿主私有目录。
3. 重启原对象存储和原应用，在备份后执行写入 B，收到 SQL 确认并立即读回 A、B。随后 KILL 原应用和原对象存储；恢复过程只挂载两个**新卷**，原容器停止、旧卷不挂载至恢复进程。
4. 从故障前的两个归档恢复新卷；新 RustFS 以相同网络别名、桶名和 S3 endpoint 字符串启动。恢复后的 13 个对象的 key、长度和 SHA-256 与备份前逐项相同。新应用通过 TLS 就绪，数据库标识和项目凭据逐值相同；SQL 只读回 A，B 不存在。

脚本测得**本次模拟 RPO 为 4.045 秒**：故障时刻到最近可恢复的已确认写入 A 的时间。故障与备份之间有一笔已确认写入 B 被有意制造并实际未恢复，丢失确认写入数为 1。**本次模拟 RTO 为 2.983 秒**：原应用与对象存储停止后，到新实例完成 TLS SQL 读回 A 的时间。均为同一宿主、小数据量、镜像已缓存、备份文件已就绪的手动流程数字，不能作为生产承诺。原始源卷仍保留供审计，但恢复容器没有挂载它们；这模拟了源卷不可用于恢复，未模拟物理毁损或跨主机搬运。

报告写成后另做了一次**独立在线 SQL 复核**：只读确认恢复容器仍运行且 owner 标签匹配，从私有连接文件与 CA 通过 TLS 查询 `sqlite_master` 中唯一的 `dr_` 表，并查询其行。结果为 `table_count=1`、`row_count=1`，该行 SHA-256 等于 A 的记录值、没有 B 的哈希，数据库标识与源连接文件相同；未在输出中暴露原值或凭据。这个复核补强了脚本自身断言，但不改变手动备份与同宿主范围。

## 判定与限制

这次**预先冷备份的恢复流程在隔离模拟环境中通过**，同时证实备份之后的确认写入可以丢失。它不证明产品已有自动备份、定期备份、生产 RPO/RTO、跨主机灾备或旧副本 fencing。完整卷复制保留服务身份，旧源卷如果重新启动可能产生相同身份的两个副本；本次原容器已 KILL，尚未检验跨卷双主防护。

首次两个独立试跑为 `PARTIAL`，资源均保留：第一轮在备份后因 Docker 随机端口在 RustFS 重启时变化，脚本仍检查旧端口；第二轮在恢复 RustFS 尚未就绪时立即枚举对象。两处均修正为重新读取宿主端口并等待恢复桶就绪后，才得到本次完整结果。首次试跑未作为能力成功或失败的样本。所有临时资源仅按本轮随机 owner 标签创建，没有清理其他资源。
