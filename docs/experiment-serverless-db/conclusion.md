# Serverless DB 压测结论

## 研究问题

当前仓库在本机能达到什么 SQL 压力与 serverless 生命周期表现？哪些设计验收指标已有足够实测证据？

## 核心发现

1. 本机 release **Simple / local_fsync**、单库单行主键热点下，两轮各 8 秒读档中，64 并发分别完成 1,214.4 与 2,747.2 次/s；P95 分别为 157.75 与 46.55 ms。两轮差异 2.26 倍，不能视作稳定容量。
2. 同一模式下，两轮各 5 秒写档中，8 并发完成 256.1 与 241.2 次/s；P95 分别为 40.97 与 44.09 ms。32 并发 P95 升至 162.89–258.07 ms。写后总行数为 5,293，与 5,292 次成功写加预置 1 行一致。
3. release 读写共 72,223 次请求，脚本观察到 0 错误。此结果只覆盖短时正常运行，不能证明长期错误率、断电持久性或 RPO。
4. 五个独立 Simple 库完成显式 Stop 后，首个 `SELECT 1` 均成功，HTTP 端到端耗时 21.26–25.31 ms。它不是 distributed 模式的 DB Process 冷启动。
5. Docker Engine 在本机不响应，distributed 拓扑未启动。Worker 密度、自动回收、跨 Worker 恢复、远程 WAL、设计第 16 章的 10,000 req/s 与内部平台附加延迟目标均未验收。

## 置信度

| 结论 | 置信度 | 证据与边界 |
|---|---|---|
| 各档短时吞吐、延迟分位 | 中 | 14 份原始延迟 CSV 已独立复算；同档两轮差异显著，客户端同机发压 |
| 本次读写观察到 0 错误 | 中 | 每次请求由脚本校验，汇总有 72,223 次；原始文件未保存逐请求响应状态 |
| 写后行数与成功写数一致 | 中 | 脚本末尾断言通过；原始计数响应未单独保存，未做重启恢复 |
| Simple 显式停库后首查询成功 | 中 | 5 个独立样本有 HTTP 状态、行值和耗时；样本数不足以估计尾部分位 |
| distributed serverless 满足设计阈值 | 无结论 | 集群未运行，不存在对应实测 |

## 限制与下一轮

本次数据集只有一行，读档 8 秒、写档 5 秒，且闭环客户端与服务同机。它适合发现明显的延迟增长和轮次波动，不适合推断系统容量上限。下一轮应在 Docker 可用的 Linux/cgroup v2 环境中，以独立负载机运行固定到达率测试，并记录 1 GiB 多 key 点查、服务与客户端 CPU、磁盘同步耗时、路由缓存、Worker/WAL 指标、冷启动与故障注入的原始时间线。
