# Simple 延迟问题结论

## 研究问题

为什么 Simple 单行 SQL 请求常需 10–100 ms？这是否说明原版 TursoDB 引擎慢？

## 已确认的实现问题

`database-host` 的每库执行线程原先在命令队列为空时 `try_recv` 后固定睡眠 10 ms。单请求串行负载下，请求多数会遇到这个睡眠。隔离基线的两轮主键点查 HTTP P50 为 12.895/12.732 ms，其中响应 `elapsed_micros` P50 为 12.171/11.914 ms。非 SQL 端点 P50 约 0.1–0.2 ms。

修复后，无会话、无活动事务的执行线程改用 `blocking_recv` 等待新命令；有会话时保留定期唤醒，以维护闲置会话和事务超时。相同脚本与工作负载的首次两轮修复后实验中，主键点查 HTTP P50 降为 0.332/0.326 ms，约下降 97.4%；同步单行写 P50 从 16.015/15.992 ms 降为 4.032/4.034 ms，约下降 74.8%。空闲唤醒修复版再次运行同脚本时，读 P50 为 2.070/0.418 ms、写 P50 为 6.945/8.829 ms。四轮均低于旧版，但波动说明不能把 0.33 ms 当作稳定值。这一前后对照确认了空闲轮询是低并发固定延迟的主要原因。首次修复后读请求的 `elapsed_micros` P50 为 40/43 µs，仍包含执行线程、引擎和目录同步，不能称为纯 TursoDB 引擎耗时。

| 场景 | 修复前 HTTP P50 | 首次空闲唤醒修复后 HTTP P50 | 空闲唤醒修复版复测 HTTP P50 |
|---|---:|---:|---|
| 单并发主键点查，两轮 | 12.895 / 12.732 ms | 0.332 / 0.326 ms | 2.070 / 0.418 ms |
| 单并发同步写，两轮 | 16.015 / 15.992 ms | 4.032 / 4.034 ms | 6.945 / 8.829 ms |

首次修复对照见[基线](perf_diagnosis_experiment.md)与[对照](perf_diagnosis_after.md)；空闲唤醒修复版的原始样本保存在本地 `raw/perf_diagnosis_final/`，不提交 Git。

## 仍需解释的高并发尾延迟

空闲唤醒修复版在另一轮 32/64 并发点查中，32 并发 HTTP P95 为 26.65/29.06 ms、64 并发为 42.82/46.57 ms；88,583 次请求中 79 次达到 100 ms。最慢 1% 请求的单条服务计时占客户端总耗时的标准中位比例为 95.0%–96.8%。服务计时包含单库执行队列等待，因此现有数据只能说明尾延迟主要落在该区间，无法拆成引擎执行、排队、文件同步各自的贡献。此前修复后另一轮 32 并发 P95 达 96–135 ms，此轮没有复现，说明短时同机负载波动显著。后续结果帧通道容量实验见[单行点查尾延迟报告](frame_capacity_experiment.md)。

代码中每库只有一条执行线程；stateless SQL 每次新建引擎连接；每条成功 SQL（包括 SELECT）结束时都同步数据库目录；JWT 认证、资源授权与库状态检查每请求访问单连接 SQLite Catalog。这些都是可疑的扩展性开销，尚无各阶段计时，不能把高并发尾延迟单独归罪于其中任一项。同步写的 `elapsed_micros` P50 修复后仍为 3.55–3.58 ms，包含 FULL/FULLFSYNC、引擎和目录同步，尚未分段。

## 原版 TursoDB 对照

官方早期 Limbo [嵌入式读微基准](https://turso.tech/blog/introducing-limbo-a-complete-rewrite-of-sqlite-in-rust)在 M2 上报告 `SELECT * FROM users LIMIT 1` 约 506 ns；[Turso 0.8 批量事务基准](https://turso.tech/blog/turso-0.8.0)在另一台 Linux/NVMe 主机上报告 64 连接约 9,500 个事务/s（每事务 100 行、`BEGIN CONCURRENT`、FULL 同步），1,000 TPS 条件下 32 连接 P99.9 为 2.4 ms。它们与本项目 macOS、单行 HTTP、逐请求认证/状态检查及单库线程的条件不同，不能直接相除或判断达标。仓库使用 `turso_core=0.8.1`；目前没有同机同工作负载的原版直接对照。详情见[一手资料核对](upstream_perf_research.md)。

## 验证与后续

最终改动的 `database-host` 11 个测试和 `db-server` 的 Simple 真实二进制集成测试通过。后续若要解决高并发尾延迟，应增加入队、开始执行、SQL 完成、目录同步、响应完成的分段时间线，并使用独立负载机、固定到达率和更大数据集重复测试。目录同步涉及崩溃持久性，不能仅凭读请求延迟就直接移除。
