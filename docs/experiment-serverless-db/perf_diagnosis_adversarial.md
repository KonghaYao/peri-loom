## 数字复算

样本脚本的分位实现取排序后 0 起始下标 `ceil(p*(n-1))`；因此每组 120 条的 P50 取第 61 条。按这一实现，所有下列数字与报告一致。它与一些资料所称的标准 nearest-rank（`ceil(p*n)`，120 条时取第 60 条）不同；方法文档宜给出公式，尤其最终版第一轮读的第 60/61 条分别为 0.652/2.070 ms。

| 实验 | 读 HTTP P50，两轮 | 写 HTTP P50，两轮 | 样本与说明 |
| --- | ---: | ---: | --- |
| 原版 SHA `8e3c...` | 12.895 / 12.732 ms | 16.015 / 15.992 ms | 各轮各项 120 条 |
| 首次修复 SHA `5c8e...` | 0.332 / 0.326 ms | 4.032 / 4.034 ms | 同脚本、独立进程与数据目录 |
| 最终版 SHA `55ea...` | 2.070 / 0.418 ms | 6.945 / 8.829 ms | 同脚本、独立进程与数据目录 |

首次修复实验读 P50 相对原版下降约 97.4%，写下降约 74.8%，计算无误。但最终版第一轮读 P50 是首次修复第一轮的 6.2 倍，最终版第二轮写 P50 是首次修复第二轮的 2.2 倍。因此 0.33 ms 和 4.03 ms 只能称为**该次短时实验结果**，不能作为稳定性能承诺。README 和结论现已同时列出最终版复测，避免了只引用最好结果。

并发逐请求文件合计 21,357 + 23,782 + 23,190 + 20,254 = **88,583** 条、均为成功；四档达到 100 ms 的请求为 14 / 26 / 39 / 0，合计 **79** 条（约 0.089%）。32 并发两轮 HTTP P95 为 26.651 / 29.064 ms，64 并发为 42.822 / 46.567 ms，与 `results.json` 和结论一致。每档最慢 1% 请求的 `server_us/client_us` 比例中位数依次为 **95.0%、95.2%、96.8%、95.8%**（按文件顺序 `round1_c32`、`round1_c64`、`round2_c64`、`round2_c32`）。结论所写的范围 95.1%–96.8% 下界略高，应为 **95.0%–96.8%**；这是小数舍入问题，不改变定性判断。

## 归因边界

- 代码确有空队列后固定 `sleep(10 ms)`，修改空闲等待后，相同脚本的四轮低并发 P50 均明显低于原版。称其为原先**主要固定延迟来源**有充分支持；不能把全部 12 ms 的差值精确归到一次 10 ms 睡眠，因为不同构建和实验时刻的系统负载、调度及持久化成本未受控。
- `elapsed_micros` 在 `services/db-server/src/simple/execution.rs` 中于 `host.execute(...).await` **返回后**开始，到收到完成帧为止。它可能包含命令排队、连接建立、引擎和目录同步，也可能漏掉开始计时之前已发生的处理；`client_us-server_us` 也不是纯 HTTP 时间。因此最慢 1% 的约 95% 落在这个计时区间，只能定位到区间，**不能证明执行线程排队或 Turso 引擎各占多少**。
- 并发脚本是固定并发、零思考时间、同机发压，吞吐会反过来决定到达率；独立负载机、固定到达率和阶段计时仍是必要的。最终版 64 并发 P95 约 43–47 ms、79 条达到 100 ms，说明高并发尾延迟仍存在。短时轮次之间差异大，不能从单轮决定稳定容量。
- [Turso 官方 2024 Limbo 微基准](https://turso.tech/blog/introducing-limbo-a-complete-rewrite-of-sqlite-in-rust)的 506 ns 是 M2 上嵌入式 `SELECT * FROM users LIMIT 1`；[官方 0.8 基准](https://turso.tech/blog/turso-0.8.0)的约 9,500 TPS 是 Linux/NVMe 上每事务插入 100 行、`BEGIN CONCURRENT`、FULL 同步。两者均不是本项目 macOS Simple 单行 HTTP 请求的直接对照。结论对此的限定正确。

## 判定

**核心结论成立，需收紧两处表述。** 修复确实消除了串行负载中原先约 13 ms 的固定读延迟；最终版仍有明显波动和并发尾延迟。建议将结论中最慢 1% 的下界修为 95.0%，并在方法文档写清分位算法公式。现有数据不足以对 Turso 引擎性能、单库执行排队或目录同步逐项定责。

复核后已将结论的下界改为 95.0%，并在实验报告中写明分位算法公式；原始复核意见保留在上文。
