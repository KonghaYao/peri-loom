# Simple 持续优化：只读目录同步与热库启动锁

## 改动与边界

1. `engine-adapter` 从已编译语句返回 `is_readonly`。`database-host` 仅对无状态、执行后处于自动提交状态的只读语句跳过数据库目录 `fsync`。写入、DDL、会话语句和非自动提交状态仍同步目录。此处只省去目录同步，不改变 TursoDB 自身的 WAL 同步设置。
2. `SimpleServices::ensure_available` 在完成停止与待处理变更检查后先读数据库状态；已在服务的 Warm/Hot 库直接通过。冷库仍通过全局 `starting` 锁串行启动，且在锁内重读状态。

两个改动依次实现并分别对照。压测仅覆盖 Simple、单库单行热点点查；未测试 distributed，也未测试断电故障注入。原始逐请求样本放在本地被 Git 忽略的 `raw/`。

## 只读目录同步：A/B/A/B

A 为原版 release，SHA-256 前缀 `4555a10c`；B 只加入只读目录同步优化，前缀 `fceb8f47`。固定脚本 [bench_concurrent_attribution.py](bench_concurrent_attribution.py)，每次启动隔离 Simple 进程和临时数据目录，先预热 100 次，再按 32→64→64→32 并发，每档 5 秒、档间休息 1 秒。按 A1→B1→A2→B2 运行，共 313,856 次请求、0 错。下表每格为同一次运行中该并发的两档 HTTP P95 范围（ms）。

| 并发 | A1 | B1 | A2 | B2 |
|---:|---:|---:|---:|---:|
| 32 | 11.15–13.05 | 7.25–9.24 | 14.46–98.01 | 10.99–11.45 |
| 64 | 20.12–22.55 | 15.67–16.24 | 34.44–152.82 | 24.91–30.57 |

全部 8 组按同位置比较，B 的 HTTP P95 均低于 A。单并发短测中，点查两轮的 HTTP P50 从 A 的 0.342/0.379 ms 降到 B 的 0.313/0.337 ms；响应 `elapsed_micros` P50 从 42/48 µs 降到 22/27 µs。同步单行写的 HTTP P50 仍约 4 ms。该字段的计时从 `host.execute` 返回之后开始，可能漏掉执行线程已经完成的工作，**不能解释为完整服务端耗时**，也不能直接与原生 TursoDB 微基准相比。

A2 明显慢于 A1，说明同机闭环负载受环境影响很大；B2 的 64 并发吞吐也低于 A1。因此结果支持这项改动改善本负载的尾延迟，**不支持稳定容量或吞吐提升的数值承诺**。原始数据见本地 `raw/sync_read_ab_{a1,b1,a2,b2}/` 和 `raw/sync_read_seq_{before,after}/`。

## 热库启动锁：A/B/A/B

A 为只读同步优化版，前缀 `fceb8f47`；B 再加入热库启动锁快路径，前缀 `43819852`。同脚本、同顺序、同参数，共 381,526 次请求、0 错。

| 并发 | A 的 HTTP P95 范围 ms | B 的 HTTP P95 范围 ms | 判断 |
|---:|---:|---:|---|
| 32 | 7.78–9.21 | 7.07–9.41 | 区间重叠 |
| 64 | 15.48–17.01 | 13.63–22.44 | 区间重叠 |

8 组同位比较中 6 组改善、2 组退化，**未证实稳定的同库吞吐或尾延迟收益**。该改动减少热库对全局启动锁的依赖；尚未单独测量“一个库冷启动时另一个热库查询”的场景。原始数据见本地 `raw/start_lock_ab_{a1,b1,a2,b2}/`。

## 正确性与剩余热点

`cargo test -p engine-adapter -p database-host`、针对只读标记的新测试，以及 `cargo test -p db-server --test simple_http` 通过。独立审查确认写入、DDL、会话事务仍走目录同步；热库快路径仍执行待处理删除/恢复检查，冷库锁内重读避免重复启动。现有测试验证写入和会话提交后重开可读，但未做真实掉电实验。

未解决的热点：每次请求仍重复读取 Catalog；无状态 SQL 仍每次新建 TursoDB 连接；超过三帧的结果仍可能在满队列上固定休眠 5 ms；同库执行仍由一条线程串行处理。下一轮应按排队、引擎执行、目录同步、Catalog 和 HTTP 响应分段计时，再选择改动。
