# Simple 空闲唤醒修复后并发梯度复测

## 方法与范围

沿用原来的 [bench_simple.py](bench_simple.py)，对新 release 二进制（SHA-256 `5c8ec697ff7ee666f17ae06487612357c2c93e46c607a201ef9c12c130e6bbe7`）运行相同参数：读并发 1/8/32/64，各 8 秒；写并发 1/8/32，各 5 秒；档间休息 2 秒；第一轮升序、第二轮降序；读前预热 100 次。独立 `127.0.0.1` 随机端口、临时数据目录，未接触现有 `18081` 或 `data`。原始结果：[修复后汇总](raw/perf_load_after/results.json)、[逐请求延迟](raw/perf_load_after/)；旧版：[原始汇总](raw/release/results.json)。

复现命令：

```sh
python3 docs/experiment-serverless-db/bench_simple.py \
  --binary target/release/peri-loom \
  --output docs/experiment-serverless-db/raw/perf_load_after \
  --duration 8 --write-levels 1 8 32 --write-duration 5 --rest 2
```

修复后共 **97,515** 次 HTTP SQL 请求，全部返回预期内容或写入成功、观测错误 0；共 6,661 次写入，测试末尾行数 6,662（含预置 1 行）。两版均为本机 macOS ARM64、同机 `aiohttp` 闭环发压、单进程 Simple、同一 SQL 和 release 构建，但在不同时间运行，可能有系统负载、OS 缓存及调度差异。旧版同档两轮本就有较大波动，不能将每项差值全归因于这一次代码变更。

## 判读

- **单并发瓶颈明显消失。** 点查 P50 由 12.74–14.93 ms 降至 0.35–0.37 ms，单并发吞吐由 70–75 升至 806–1,742 req/s；写入 P50 由约 16 ms 降至 4.02–6.92 ms。这与[单请求计时分解](perf_diagnosis_after.md)中服务 `elapsed_micros` 的下降方向一致。
- **100 ms 级高并发尾延迟依然存在。** 32 并发读的新 P95 为 96.05–134.99 ms，P99 为 128.05–145.94 ms，反而差于旧版两轮；64 并发读的新 P95 为 51.42–53.38 ms，P99 为 81.04–82.46 ms，其中首轮比旧版明显改善，第二轮略差。不能称“高并发尾延迟已解决”。
- **同步写在并发 8 后几乎不扩容。** 新版 8 并发约 256–274 req/s，32 并发约 194–204 req/s，P95 升至 202–230 ms。与单库串行执行、写入持久化和排队相符；本实验没有分段测量队列、SQL、WAL、`sync_dir`，因此不能定量归因。
- **读并发档位不呈单调关系。** 新版 32 并发吞吐仅 654–1,076 req/s，64 并发反而为 2,494–2,630 req/s；32 并发两轮明显慢于 64 并发。这一异常说明本机短时闭环负载受运行时或系统状态影响明显，不能用单一档位拟合稳定容量曲线。服务进程在 32 并发读时平均 CPU 约 0.32–0.43 核，64 并发读约 0.83–0.89 核，CPU 数据也不支持“服务已用尽 18 核”的解释。

要定位剩余高并发瓶颈，应在 `LocalHost` 单库队列入队、开始执行、SQL 完成、目录同步和响应完成处做低开销分段计时，并在固定到达率、独立负载机和重复稳定窗口下再测。此处未运行分布式拓扑，也未对照原版 TursoDB。
