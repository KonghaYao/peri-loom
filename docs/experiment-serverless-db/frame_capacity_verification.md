## 解释与限制

代码中的点查响应依次产生 `Columns`、`Rows`、`End` 三帧。容量 2 时，若异步接收任务尚未取走前两帧，发送第 3 帧会走 `send_frame` 的 `try_send` 满队列分支，执行线程每次固定睡眠 **5 ms** 再试。容量 3 可容纳此负载的三帧，因而有明确的性能改善机制；上述 A/B/A/B 观察与该机制一致。

这仍是关联证据，未直接记录 `Full` 次数、睡眠时间或各请求的执行线程排队时长。A1 与 A2 的 64 并发吞吐档位范围分别是 **1,489–1,704** 和 **2,136–2,823 req/s**，相同二进制也有明显漂移，说明同机客户端、CPU 调度、文件系统缓存或其他共享资源可能影响数字。测试仅短时闭环热点读；吞吐上升会同时改变请求到达率，不能据此推断固定到达率下的 P99 或长期稳定容量。B 在 64 并发仍有 **223/83,664（0.267%）** 个请求达到 100 ms，尾延迟尚未消除。`elapsed_micros` 包含主机队列与执行过程，不能把剩余尾延迟直接归责于数据库引擎。

**判定：** 在这个单行点查负载和本机条件下，容量 3 稳定优于容量 2；三帧填满两格通道后触发 5 ms 睡眠是可信的主要解释。若需确定它贡献了多少尾延迟，应在服务端分别计数满队列事件并记录发送等待、命令入队/出队、SQL 和目录同步耗时，再用独立负载机或固定到达率重复实验。
