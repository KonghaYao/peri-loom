# 压测报告对抗复核

复核对象：[实测报告](01_experiment_report.md)、[release 汇总](raw/release/results.json)、[Simple 压测脚本](bench_simple.py)、[后续生命周期样本](raw/release/lifecycle.json)及对应脚本。本次只读复核，未启动服务或施加负载。

## 判定

**作为本机 Simple 模式的短时观测，报告主体可信；作为 serverless DB 性能验收，证据不足。** 表格逐档列出而未掩盖两轮差异，端到端与平台附加延迟也已区分。第 16 章 distributed 环境、1 GiB 数据集、Worker/Remote WAL 路径未覆盖，所有这些目标应继续标“未验收”。

| 挑战点 | 证据与影响 | 建议措辞/补证 |
| --- | --- | --- |
| 最大 RPS 不是容量 | 热读并发 64 两轮分别 1,214.4 和 2,747.2 req/s，差 2.26 倍；各档仅 8 s，闭环客户端随延迟升高自动降速。同档重复两次无法估计稳态吞吐或可持续容量。 | 保留“最大观测吞吐”，不要称峰值容量/SLA。使用独立负载机、固定到达率梯度、长稳态、多次重复，记录丢弃/排队。 |
| 延迟分位的范围不能当置信区间 | 两轮 P95/P99 是两个短窗口的点估计；报告的 `46.55–157.75 ms` 只是两轮观测范围。读并发 64 的两个窗口差异还显示时间/轮次效应。 | 写清“两个 8 s 窗口的范围”，避免把它表述成总体 P95/P99 的统计区间；记录请求时间戳以检查窗口内漂移。 |
| 工作负载过窄 | SQL 是 `SELECT v FROM bench WHERE id = 1`，表只有 1 行；虽然是主键点查，却没有架构目标中的 1 GiB DB，也没有不同 key/page、缓存未命中、混合读写或多租户争用。 | 仅代表单行热点。另测 1 GiB 的索引点查、均匀/偏斜 key 分布、读写混合与多库。 |
| 写入吞吐的因果解释仍是推测 | 并发 8 到 32 后尾延迟增大，可能来自单库写串行、fsync、客户端事件循环或系统负载；`server_cpu_cores` 低于 1 不能定位瓶颈。 | 把“符合写争用或排队表现”保留为假设；需服务端排队时间、fsync 分位、磁盘 I/O、客户端 CPU 与事件循环延迟。 |
| 零错误的可靠性范围 | 72,223 次请求观察到 0 错误，原始 CSV 只存延迟；逐请求状态/响应未落盘，脚本内部检查逻辑是证据。5,292 次写入的最终行数断言通过，但计数响应未写入结果文件；未测重启后的持久性。 | 写“0 次已观测错误”，不要写成错误率保证或 RPO=0。保存脱敏的状态/结果校验标记与最终计数证据，做故障恢复读回。 |
| 资源数据不能证明密度 | RSS 每档只测开始和结束两点；CPU 只计服务进程、不计客户端或系统开销；单进程 Simple 没有 Worker、per-DB 进程/cgroup。 | 不从 26–45 MiB 两点值推断峰值、空闲驻留成本或每 Worker 可承载 DB 数。要持续采样进程树、cgroup RSS/CPU 和 DB 个数。 |
| 环境口径不同 | macOS Apple Silicon 18 核、同机 localhost、无 TLS/代理；设计基线为 8 vCPU Server + 32 vCPU Worker、网络和 Remote WAL RTT 条件，且 distributed 路由和数据路径不同。 | Simple 与 distributed 分表；不拿本机读吞吐/延迟给架构热路径目标判 PASS 或 FAIL。 |
| Simple 生命周期样本范围 | `raw/release/lifecycle.json` 已有 5 个不同库在 Stop 操作完成后首个 `SELECT 1`：21.26、21.31、21.37、23.49、25.31 ms，均 HTTP 200 且结果 `[[1]]`。主报告已纳入此结果。[脚本](bench_lifecycle.py)还记录单次服务启动至 `/readyz` 306.45 ms。 | 保持“Simple 显式 Stop 后首查询，5 个样本”的口径；启动 Ready 是另一个指标。不能据此给 P95/P99 或 distributed 冷启动验收结论。 |
| Simple Stop 与分布式 COLD 含义不同 | Simple 的 Stop job 调 `LocalHost::close_db`，下一次查询经 `ensure_available` 串行锁、Catalog 状态转换及本地 host `describe` 后恢复；没有独立 DB Process spawn、Worker placement、快照恢复或 Remote WAL replay。 | 称“Simple 本地库关闭后首查询”，不要称分布式 `COLD→READY`。只计 5 个库且每库一次，无法估计尾部分位或成功率 ≥99.9%。 |

## 数字核查与结论边界

- 汇总请求数相符：热读 66,931 + 写入 5,292 = 72,223。写后预期行数为预置 1 + 5,292 = 5,293；该断言存在于脚本，并因结果文件成功生成而可推知通过，但原始响应未保存。
- 写并发 32 的 P95 最低 162.89 ms，写并发 8 的 P95 最高 44.09 ms，比例约 3.69；报告写“至少约 3.7 倍”是合理四舍五入。读并发 32 的两轮吞吐比约 1.78，读并发 64 约 2.26，均与表格一致。
- `bench_simple.py` 的分位数为每档全部客户端请求延迟按 `ceil((N−1)×p)` 取秩；成功和失败延迟都会进入样本。本次 0 失败，因而分位代表已观测成功请求。CSV 无请求时间戳、状态与 SQL 结果，不能复核窗口内是否持续稳定或独立重放语义校验。
- `lifecycle.json` 的 5 个样本只有最小/最大及单次启动 Ready 可陈述；少量样本的经验 P95/P99 没有验收意义。它也没有测空闲自动回收、并发同库唤醒、资源释放、崩溃恢复或多库密度。

主报告已将生命周期样本加进 Serverless 性能表格；保持“Simple 本地显式 Stop 后首查询”的命名，并将 distributed 项标为“未测”。
