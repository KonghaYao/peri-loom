# Simple 单机模式延迟分解：隔离基线实验

## 目标与方法

验证先前单并发主键点查约 13–15 ms、写入约 16 ms 的延迟主要发生在哪里。用已构建的 release 二进制（SHA-256 `8e3c2473e7ac05292b9925278fd852a213b228f88e203d49246cc602ab2b3184`），启动独立 Simple 进程，使用随机 `127.0.0.1` 端口和测试结束后删除的临时数据目录。未连接或修改已有 `18081` 实例和仓库 `data`。同机 `aiohttp` 单个持久连接，所有请求串行，预热 100 次点查。随后每轮依次测 `/readyz`、`/api/v1/deployment`、主键点查、单行写入，每项 120 次，重复两轮。无请求间人为等待。

客户端计时从调用 `session.request` 前到读完并解析 JSON 后，含 HTTP、认证、数据库访问和 JSON 解析；响应字段 `elapsed_micros` 是服务器 `LocalExecutor::open_stream` 在 `host.execute(...).await` **之后**开始的计时，直到产生最后的执行帧。两者之差称为“计时器外耗时”，包含客户端、HTTP、认证、资源授权、`ensure_available`、发送命令前等待及响应序列化；不能简单等同“HTTP 开销”或纯引擎时间。`/readyz` 和 `/api/v1/deployment` 无此字段，仅有客户端计时。所有值为毫秒。P 分位对升序样本取零基下标 `ceil((N-1)×p)` 的值；N=120 的 P50 为第 61 个样本，和标准偶数样本中位数略有区别。

原始样本：[samples.csv](raw/perf_diagnosis/samples.csv)（960 条、无凭据）、[metadata.json](raw/perf_diagnosis/metadata.json)、[server.log](raw/perf_diagnosis/server.log)；可复现脚本：[bench_perf_diagnosis.py](bench_perf_diagnosis.py)。两轮各 120 次写入均返回 `affected_rows=1`，末尾行数为 241，等于初始 1 行加 240 次写入。

## 代码与数据联合判断

1. **延迟主要在 Simple 执行计时区间，而非本机 HTTP 往返。** 点查的服务计时中位数为 11.9–12.2 ms，客户端中位数为 12.7–12.9 ms；纯 API 基线低于 0.2 ms。计时器外仍有约 0.9–1.0 ms 的中位数成本，可能包含 metadata 查询与 HTTP，但本实验不能把这些进一步拆开。
2. **10 ms 轮询是强疑点。** `crates/database-host/src/lib.rs` 的 `run_worker` 在 `commands.try_recv()` 空队列时固定 `std::thread::sleep(Duration::from_millis(10))`，而上述串行请求使执行线程有机会在请求之间进入睡眠。它可直接制造 0–10 ms 的额外等待，并与几乎所有点查落在 10–20 ms 的现象相符。这里是代码推断，尚无修改轮询方式的因果对照。
3. **每条 SQL 的目录同步也是强疑点。** 同文件 `execute_on_connection` 在发送完成帧前无条件调用 `sync_dir`，包括只读 `SELECT`；写入另外执行 `enforce_full_sync`。点查与写入的中位差约 3.1–3.3 ms，但无法把该差值全归因于 fsync，因为 SQL 和写入本身也不同。现有 `elapsed_micros` 不能拆分轮询等待、引擎执行和目录同步。
4. **先前 100 ms 级高并发尾延迟不能由本串行基线单独解释。** 单库只有一条执行线程；并发请求会在其前面排队。此前 32/64 并发压测已经测到更高 P95/P99，本轮没有重复并发实验，不能量化排队与 CPU/IO 各自贡献。

## 限制和下一步

样本是同机单连接、单行表的短时测试，不能外推到远程客户端、较大数据库或 distributed 模式。服务计时包含执行线程等待，但不含进入 `host.execute` 之前的 metadata / `ensure_available`；没有内部分段埋点，也没有直接原版 TursoDB 对照。下一轮应仅改变执行线程的空闲唤醒方式，在相同二进制配置、SQL 与负载下做前后对照；随后单独检验只读请求是否需要无条件目录同步。改变持久性逻辑前须验证崩溃恢复语义。
