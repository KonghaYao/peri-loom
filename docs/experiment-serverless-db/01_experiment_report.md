# Serverless DB 压力测试：实测报告

## 测试范围与环境

本次实测对象是仓库的 **Simple 单机模式**（`mode=simple`、`durability=local_fsync`），不是三副本 Remote WAL 的 distributed 模式。Docker Desktop 的 CLI 在输出 `Server:` 后持续无响应，无法启动 Compose；本机也没有 k6。因而 distributed 的 Worker 扩缩、跨节点路由、Remote WAL 和云平台冷启动指标均 **未测**，不能用下表代替。

| 项目 | 实测配置 |
|---|---|
| 代码 | Git `5851f22640ec`；Rust `1.98.1`；`cargo build --release --locked --bin peri-loom` |
| 二进制 | `target/release/peri-loom`，SHA-256 `8e3c2473e7ac05292b9925278fd852a213b228f88e203d49246cc602ab2b3184` |
| 主机 | macOS 26.5.1 / Apple Silicon ARM64，18 逻辑核，48 GiB RAM；无容器 |
| 拓扑 | 同机 `aiohttp` 客户端 → `127.0.0.1` HTTP → 单进程 Simple → 临时本地数据目录；没有公网、TLS、代理、负载均衡 |
| 数据与请求 | `bench(id INTEGER PRIMARY KEY, v INTEGER)`，预置 `(1,42)`；热读 `SELECT v FROM bench WHERE id = 1`，每次校验 `rows=[[42]]`；写入 `INSERT INTO bench(v) VALUES (42)` |
| 负载 | 固定并发、零思考时间、持久连接；读每档 8 s，写每档 5 s，档间休息 2 s；第一轮升序、第二轮降序；读前预热 100 次 |
| 指标 | 端到端 HTTP 响应耗时，含客户端、TCP、认证、路由、引擎与 JSON；吞吐按实际墙钟时间计；错误同时检查 HTTP 状态及响应内容 |

原始数据：[release 汇总](raw/release/results.json)、[逐请求延迟文件](raw/release/)；脚本：[bench_simple.py](bench_simple.py)。原始字段 `server_rss_end_mib` 实际取每档开始与结束两次 RSS 中较大者，**不是严格的结束值或持续采样峰值**。CPU 指标为单个服务进程在该档位使用的平均 CPU 核数；客户端与系统开销未计入。

复现命令：

```sh
cargo build --release --locked --bin peri-loom
python3 docs/experiment-serverless-db/bench_simple.py \
  --binary target/release/peri-loom \
  --output docs/experiment-serverless-db/raw/release \
  --duration 8 --write-levels 1 8 32 --write-duration 5 --rest 2
```

## 2. Serverless 性能表格

| 能力 / 场景 | 本次实测或状态 | 解释 |
|---|---|---|
| Simple 热主键点查最大观测吞吐 | 2,747.2 req/s，64 并发第 2 轮 | 另一轮同档仅 1,214.4 req/s，不能当作稳定容量 |
| Simple 热主键点查延迟 | 64 并发 P95 46.55–157.75 ms、P99 70.15–218.01 ms | HTTP 端到端；两轮差异显著 |
| Simple 本地持久写最大观测吞吐 | 256.1 req/s，8 并发第 1 轮 | 32 并发无稳定收益，且尾延迟显著增加 |
| Simple 本地持久写延迟 | 8 并发 P95 40.97–44.09 ms；32 并发 P95 162.89–258.07 ms | 测后行数核对成功 |
| Simple 手动停库后首次查询 | 5 个独立库全部 HTTP 200 且返回 `[[1]]`；耗时 21.26–25.31 ms，中位数 21.37 ms | 停库操作完成后立即查询；`SELECT 1`，端到端；样本数仅 5，不能代表自动 idle 回收或高分位 SLA |
| Simple 实例启动到 `/readyz` | 306.45 ms（单次） | 全新临时数据目录、启动新进程；不能当作数据库冷启动分位 |
| Simple 内存 | 生命周期实验末尾 RSS 38.91 MiB | 仅一个时间点、已有 5 个测试库；空闲驻留和峰值均未测 |
| distributed 冷启动、自动扩缩、Worker 密度、Remote WAL | 未测 | Docker Engine 不响应，集群未启动；Simple 不能外推 |
| 架构目标：热读 ≥10,000 req/s，平台附加延迟 P95 ≤3 ms / P99 ≤8 ms | 未验收 | 目标针对 distributed 平台；本次 HTTP 端到端耗时与内部附加延迟不同口径 |

## 结果解释与限制

热读同并发两轮最大吞吐差异达到 2.26 倍（64 并发），32 并发差 1.78 倍。客户端与服务共用主机；轮次顺序、OS 缓存、引擎内部状态及背景进程均可能影响结果。当前数据足以说明有较大波动，**不足以定位具体瓶颈或给出稳定容量 SLA**。写入从 8 增至 32 并发后 P95 至少增加约 3.7 倍，符合单库写争用或排队的表现；具体原因仍需服务内部队列、磁盘同步耗时等指标验证。

为交叉核查，还以 debug 二进制完成相同的两轮热读：共 50,247 次、零错误，原始数据在 [debug 汇总](raw/debug/results.json)。debug 与 release 结果不同，正式性能判断应以 release 表为准。

生命周期复核使用 [bench_lifecycle.py](bench_lifecycle.py)，[原始结果](raw/release/lifecycle.json) 记录 5 个独立数据库先查询、完成手动 stop 操作、再执行首个 `SELECT 1`。全部透明唤醒并返回正确行。该小样本仅说明此受控路径可用；没有模拟长期 idle 驱逐、进程 crash 或多节点迁移。

后续要回答真正的 serverless 容量问题，需要在可用的 Linux Docker / cgroup v2 环境启动 distributed 集群，以独立负载机运行 k6，采集 Worker、路由缓存、WAL quorum、资源占用与冷启动分位，并至少重复三轮稳定窗口。
