# Simple 高并发点查尾延迟归因：最终修复版

## 实验边界

最终修复版 release 二进制 SHA-256 `55ea2c21a8a4d752b3921841ffca7c311d7ae0822276c69f5fa88a765cb9f438`。这个版本仅在 **无会话、无活动事务** 的空闲执行线程上使用 `blocking_recv`；有会话时仍定期唤醒以清理过期会话。隔离 Simple 进程使用随机本机端口和测试后删除的临时数据目录，未触碰现有 `18081` 或仓库 `data`。

工作负载：一个表、预置 `(id=1,v=42)`，执行 `SELECT v FROM bench WHERE id = 1`，每次核对响应 `rows=[[42]]`。先预热 100 次，随后并发 32→64、64→32 两轮；每档 8 秒、档间休息 2 秒，`aiohttp` 持久连接、零思考时间。原始数据：[results.json](raw/perf_concurrent_attribution/results.json)及每档逐请求 `csv.gz` 文件位于[原始数据目录](raw/perf_concurrent_attribution/)；脚本：[bench_concurrent_attribution.py](bench_concurrent_attribution.py)。共 **88,583** 次请求，验证结果与 `elapsed_micros` 字段，**0 错误**。

`client_us` 从请求发出前计至 HTTP JSON 读取完成。`server_us` 是响应中的 `elapsed_micros`：`LocalExecutor::open_stream` 在 `host.execute(...).await` **之后**开始计时，到执行完成帧为止，因此**包含单库执行线程队列等待、引擎及持久化过程**，不能称为纯 SQL 引擎耗时。`outside_us = client_us - server_us` 包含客户端、HTTP、鉴权、Catalog 查询、`ensure_available`、进入执行计时前的等待与响应序列化，不能单独归因于某一步。

## 尾部逐样本归因

按**客户端总耗时最高的 1% 请求**取样，然后对这些相同请求计算 `server_us / client_us`。下表“中位数”对最慢 1% 样本采用标准中位数（偶数样本取中间两个的平均值）。因此此处的占比确实来自同一批请求，而不是两个独立分位数之比。

| 轮次 | 并发 | 客户端最大 ms | ≥100 ms 请求 | 最慢 1% 的服务计时占比中位数 | 最慢 1% 服务计时中位 ms | 最慢 1% 计时器外中位 ms |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 32 | 103.41 | 14 | 95.0% | 48.08 | 2.46 |
| 1 | 64 | 112.64 | 26 | 95.2% | 67.93 | 3.79 |
| 2 | 64 | 114.04 | 39 | 96.8% | 66.19 | 2.65 |
| 2 | 32 | 67.41 | 0 | 95.8% | 43.43 | 2.31 |

**判断：最慢请求的主要延迟位于服务计时器内；这一区间包含单库执行队列，不能进一步声称是引擎计算本身。** 计时器外的中位数在高并发下仍有约 6–8 ms，且 64 并发 P99 达约 19 ms，说明 Catalog/鉴权/客户端路径也有可测开销，但它不是此轮最慢 1% 请求的主要部分。要在队列与引擎之间继续归因，需要记录命令入队、执行线程取出、SQL 完成和目录同步各时间点。

本轮的 P95/P99 明显好于[前一轮并发复测](perf_load_after.md)中 32 并发读 P95 96–135 ms；但仍有总计 79 次 ≥100 ms 请求（约 0.089%），最高 114 ms。两个短时实验在不同时间运行，且最终版二进制还有 idle-session 修正、主机状态也可能改变；无法把两轮差异归因于该修正或宣称尾延迟稳定消除。这是同机闭环负载，不代表固定到达率或远程网络表现。
