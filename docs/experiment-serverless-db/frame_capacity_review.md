# Simple 结果帧通道容量复核

结论：**PARTIAL**。把每请求结果通道从 2 帧改成 3 帧，对单行点查是一项合理的局部优化，代码层面没有发现帧顺序、取消或 deadline 语义变化。现有 A/B 数据显示整体 P95 与吞吐明显改善，但尚无满队列分段计时证明改善的具体占比；大结果集仍可能因背压阻塞同库执行线程。

## 代码证据

| 检查项 | 结果 | 依据与限制 |
|---|---|---|
| 单行点查 | **PASS** | `execute_on_connection` 依次发送 `Columns`、非空 `Rows`、`End`。若消费任务在这期间尚未调度，容量 2 会让第三帧在 `send_frame` 的 `Full` 分支每次睡 5 ms；容量 3 可完整容纳三帧。零行 SELECT 通常只有 `Columns`、`End`；单纯写入通常没有这三个结果帧，因此不能把所有请求的改善归于此处。 |
| 帧顺序及成功语义 | **PASS** | 单生产者按原顺序向同一 Tokio mpsc 通道发送；未修改 `Columns`、`Rows`、`End` 内容和接收方映射。`End` 仍在引擎执行和 `sync_dir` 成功后发送。 |
| 取消与 deadline | **PASS** | `ExecutionStream::drop/cancel` 设置取消标志；`send_frame` 每次发送前及满队列重试时检查取消、接收方关闭和 deadline。容量 3 使点查可以更早完成，取消若在执行完成后到达，自然不能撤销已执行 SQL；这一点原逻辑也成立。未读的大结果集仍会在队列满后按 5 ms 间隔检查，直至取消或超时。 |
| 背压及同库公平性 | **PARTIAL** | 容量从 2 提到 3，只是把背压推迟一帧。每库只有一个执行线程，慢消费者的大查询仍可使该线程在 `send_frame` 睡眠，拖住后续请求；单次 `Full` 的实际等待可能超过 5 ms，受操作系统调度影响。 |
| 内存边界 | **PARTIAL** | `max_result_frame_bytes` 默认 256 KiB，通道额外允许一个结果帧，约增加每个未消费请求至多一个帧的估算数据量；`row_batch_size` 默认 64。该限制基于 `estimated_size` 和列名估算，不是严格的进程堆内存上限。请求队列及流数量也需一并计入内存预算。 |
| 错误传递 | **PARTIAL** | 执行失败后的错误用 `output.try_send(Err(error))` 发送。若缓冲已经占满，错误帧可能被丢弃，接收端只看到已有帧随后 EOF。容量变化没有新建这个问题，也没有修复它；慢消费者与较大结果集仍会触发。建议独立修复或测试该路径。 |
| 现有测试 | **PARTIAL** | `unread_stream_does_not_pin_worker_after_deadline` 使用 `row_batch_size=1` 和 100 行覆盖未读流超时；其他测试会收集结果帧。但没有专测“未消费单行点查在发送第三帧后即可释放执行线程”，也没有容量 2/3 同条件负载对比。 |

## 对尾延迟 A/B 差异的解释范围

这是**机制上成立的候选原因**：容量 2 且接收端尚未取走前两帧时，第三帧至少要经历一次 5 ms 睡眠。即使接收端在这段时间立刻取走帧，执行线程也要等睡眠结束才重试。因此它能制造约 5 ms 或更高的离散延迟，并在单执行线程中传播给排在后面的请求。容量 3 可以消除单行点查的这一次等待。

当前四组 A/B 结果与上述机制高度一致。容量 2 的两组中，32 并发 HTTP P95 为 26.28–41.96 ms、64 并发为 49.75–81.17 ms；容量 3 的两组对应为 10.75–11.71 ms 和 23.50–29.41 ms。容量 3 的 32 并发成功吞吐为 4,409–4,546 req/s，64 并发为 4,073–4,355 req/s；各组汇总均为零错误。这是短时、同机、闭环请求的关联证据；容量 2 组自身也有明显波动，不能从这些汇总统计反推每个请求究竟等待了多少次 5 ms。

尤其要注意 `elapsed_micros` 的计时起点：`LocalExecutor::open_stream` 在 `host.execute(...).await` 返回**之后**设置 `started`，最后消费 `End` 时计算时长。执行线程可能在消费任务开始前已经产生结果，因此容量 3 组的所谓 `server_us_p50_ms` 低至 0.035–0.044 ms，并不代表完整服务处理只用了几十微秒；它排除了排队及此前执行时间。`outside_us = client_us - server_us` 也不能直接解释为客户端或网络耗时。应避免用这两个字段对 A/B 做阶段归因。

仍不能把全部 100 ms 级尾延迟归于结果帧通道。需要记录 `send_frame` 满队列次数与等待时间、命令入队至开始执行时间、引擎执行时间、`sync_dir` 时间，并让服务耗时从收到请求或入队前开始。若慢请求没有满队列等待，该修改就不是其直接原因。

复核方式：静态检查 `crates/database-host/src/lib.rs` 的通道容量改动、`services/db-server/src/simple/execution.rs` 消费路径及现有测试；本复核未运行负载，也未修改产品代码。
