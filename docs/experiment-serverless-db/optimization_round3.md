# Simple 持续优化：Catalog 热路径

## 范围与方法

macOS ARM64，同机 Simple release 二进制、一个库、单行热点 `SELECT v FROM bench WHERE id = 1`，JWT 管理员认证。每次启动隔离进程和数据目录，预热 100 次；按 32→64→64→32 并发，每档 5 秒，档间休息 1 秒。使用 [bench_concurrent_attribution.py](bench_concurrent_attribution.py) 按 A1→B1→A2→B2 交错运行，逐请求验证 `rows=[[42]]`。这是短时、同机、闭环负载，阶段均值不是稳定容量或置信区间。原始 CSV/JSON 保存在本地被 Git 忽略的 `raw/`。

## 尝试 1：Catalog 连接池 1→4（撤回）

`SqliteCatalog` 原连接池上限为 1。尝试增至 4 后，尚未进行性能测试，`cargo test -p catalog` 已出现 `concurrent_submission_has_one_operation_and_job` 的 `database is locked`，以及并发 token 轮换测试失败。该配置破坏现有并发写契约，已撤回；后续压测均保持单连接。

原热路径先分别查询待处理删除/恢复作业与数据库记录；新实现用一条 SQLite 语句取二者，同一快照检查，并保持待处理作业优先拒绝。A 二进制 SHA-256 前缀 `43819852`，B 前缀 `3cf00531`。后续源码还补充了 pending=true 时跳过损坏 record 解码的边界处理，该变化不影响正常热点读路径。

读池 4（`e73de5f5`）与读池 8（`8a0630b7`）按 A1→B1→A2→B2 交错点查，共 **1,331,711 请求、0 错误**。阶段平均 RPS：32 并发 16,594→16,932（+2.0%）；64 并发 16,206→16,836（+3.9%）。部分对应阶段退化，收益小。后续固定先 4 后 8 的单次短时同步写复测中，8 并发写从 275/279 降到 140/197 req/s，P95 从 41–44 升到 57–83 ms；因顺序固定、每档仅 3 秒，**不能把写入回退归因于读池大小**。综合小读收益与写入风险，默认值回退到 4。原始数据：`raw/read_pool_8_ab_{a1,b1,a2,b2}/`、`raw/read_pool_8_workload_{4,8}/`。

## 多进程压测器归因

保持总并发 64，独立 aiohttp 进程数按 1→2→4→2→1 交错，每档 8 秒，同一隔离 Simple 实例。开启分段计时共 612,255 请求，关闭分段计时共 641,495 请求，均 0 错。脚本 [bench_multi_client.py](bench_multi_client.py) 保存逐请求样本、服务端/客户端 CPU 和 `/metrics` 差分，原始数据在 `raw/multi_client_{on,off}/`。

| 客户端进程 | 1 | 2 | 4 | 2 | 1 |
|---|---:|---:|---:|---:|---:|
| 计时关闭：RPS | 16,378 | 15,628 | 15,516 | 15,905 | 16,736 |
| 计时关闭：HTTP P95 ms | 5.11 | 4.79 | 4.70 | 4.60 | 4.62 |
| 计时开启：RPS | 16,363 | 14,450 | 14,272 | 14,907 | 16,513 |
| 计时开启：路由至响应构造平均 µs | 3,307 | 4,200 | 4,270 | 4,078 | 3,324 |
| 计时开启：三个 Catalog 阶段平均值之和 µs | 3,238 | 4,118 | 4,185 | 3,999 | 3,256 |

多进程没有突破单进程的吞吐，且回切后恢复；关闭计时也有同样方向。计时本身在 2/4 进程档位使吞吐再降约 7–9%，因此只用计时数据归因，不能把计时开启时的绝对值当成无扰动服务延迟。单进程客户端约占 0.95 核，四进程合计约 1.6 核；服务端约 4.4–4.6 核。三项 Catalog 计时分别是 JWT 当前用户/权限、数据库资源授权和 Simple 准入；它们的均值总和接近路由计时均值，表明重复 Catalog 读取与读池等待主导此热点。单库 host SQL 流平均约 15–19 µs。`http_query_response_ready` 从 query 路由中间件入口计至内联响应创建，不含外层中间件与 socket 写；独立直方图的 P95 不能相加。

### 同步写波动的定向归因

早先 A/B/A/B 三档 3 秒同步写短测 16,626 次写、0 错，B 的末次出现明显回退。反序 B3→A3 和 A4→B4 的每档 8 秒复测也在 8 并发观察到 B 偏慢，但两版自身都随时间退化，B4 的单并发末档发生一次约 2.08 秒离群值。仅凭吞吐不能判定改动造成写回退。

随后用同一 release 二进制开启分段计时，按 A1→B1→B2→A2 顺序，只测 1/8 并发同步写（每档两轮、8 秒）。计时模式影响绝对性能，只用于归因：

| 版本/轮次 | 8 并发 RPS（两轮） | 8 并发 HTTP P95 ms（两轮） | `host_directory_sync` 均值 µs（两轮） | `host_sql_stream` 均值 µs（两轮） |
|---|---:|---:|---:|---:|
| A1 | 238 / 249 | 50.0 / 41.9 | 543 / 363 | 3,620 / 3,606 |
| B1 | 235 / 237 | 45.9 / 45.9 | 505 / 511 | 3,701 / 3,657 |
| B2 | 206 / 239 | 57.1 / 53.3 | 1,340 / 811 | 3,489 / 3,354 |
| A2 | 202 / 160 | 63.9 / 75.0 | 1,371 / 2,435 | 3,556 / 3,769 |

旧版 A2 在最后退化得比新版 B2 更明显，且同步目录耗时随时间大幅上升；JWT/数据库 Catalog 读取仍是几十 µs，合并路径的内存准入约 1 µs。**现有证据支持写入波动主要落在同步目录/执行排队，而非新授权快照；不能保证写性能无回归。**WAL 文件大小仅作上下文保存，不代表 fsync 耗时。原始数据：`raw/merged_write_{a1,b1,a2,b2,b3,a3,a4,b4}/`、`raw/merged_write_stage_{a1,b1,b2,a2}/`。

合并版另做计时开启的多进程 1→2→4→2→1 交错点查，合计 775,241 请求、0 错，RPS 19,205→19,684→19,129→19,621→19,243。单客户端进程时路由到内联响应创建平均约 251–252 µs，JWT 与合并数据库快照各约 88–97 µs；2/4 进程时两段 Catalog 均值各约 1.46–1.53 ms，路由约 3.0–3.15 ms。相同总并发下进程数改变了 Catalog 等待与客户端/服务端调度，阶段计时本身也扰动吞吐；需要拆开读池获取等待与 SQL 执行，才能定位剩余瓶颈。原始数据：`raw/merged_multi_on/`。

## 尝试 7：只读池跳过取连接前的健康 ping（保留）

根据仓库锁定的 SQLx 0.8.6 本机源码，`PoolOptions` 默认在每次取得 idle 连接前执行 `ping`，归还连接时仍无条件再执行一次。SQLite 的 ping 需要与其 worker 往返。只在 Simple Catalog 的**只读池**设置 `test_before_acquire(false)`；写池、归还时健康检查、实际 SQL 与每请求即时授权均保持原语义。A 为默认 ping（SHA `31f6cef4`），B 为跳过取得前 ping（`b3774bc8`）。

| 进程数 | A 的 RPS 范围 | B 的 RPS 范围 | A 的 HTTP P95 范围 ms | B 的 HTTP P95 范围 ms |
|---:|---:|---:|---:|---:|

## 正确性与未完成的归因

`cargo test -p catalog --lib` 通过，`cargo test -p db-server --test simple_http` 通过。新增测试覆盖准入 pending 优先级、JWT UUID/用户名 subject、角色撤销、禁用用户、无权限用户、超管与重复角色。源码中 JWT UUID subject 先规范化为标准 UUID 字符串，保持旧查询语义。

Astra 在复核全部交错实验后判断：**这一限定工作负载已接近当前架构的实用极限**。三次串行 Catalog 读取已合为每请求一次 SQL，重复的取得前 ping 已去除；4→8 连接在两个独立轮次均显著降低吞吐、增加 CPU，host SQL 流仍是几十 µs。最终源码恢复只读池 4 后，`cargo test -p catalog --lib` 为 57 通过、33 个 PostgreSQL 依赖测试跳过，`cargo test -p db-server --test simple_http` 为 2 通过；`cargo check -p database-host -p db-server` 和 release 构建通过。此判断只适用于本机 macOS ARM64、Simple 单库、JWT 管理员、单行热点点查、总并发 64、即时撤权和库生命周期逐请求检查、当前 SQLx/SQLite 与宿主架构。它不代表原生 TursoDB 的理论极限，也不代表多库、多行、混合读写或 distributed 性能。继续大幅提升需要新的 Catalog 连接/执行模型或不同的认证失效语义，属于另一次架构实验。现有响应 `elapsed_micros` 从 `host.execute` 返回之后开始，不能代表完整服务端耗时。
