# Simple 单请求延迟归因计划

## 问题

解释当前 Simple 模式单行点查约 10–100 ms、同步写约 10–100 ms 的主要耗时，判断是否为平台实现问题，并与原版 TursoDB 可比数据区分。

## 假设与测量

1. 每库执行线程在队列空时轮询并睡眠 10 ms，增加请求唤醒时间。比较修复前后单并发及多并发客户端端到端分位。
2. 每次 SQL 尾部都执行目录 `sync_all`，纯读请求也承担存储同步开销。用响应 `elapsed_micros` 与客户端总耗时、代码边界和必要的隔离对照归因；不在未证明持久性正确时移除同步。
3. JWT 认证、资源授权及 Simple `ensure_available` 每请求访问单连接 SQLite Catalog；高并发时可能形成排队。对照简单健康端点与 SQL，并检查服务端执行时间和客户端差值。
4. 同库只有一条执行线程，同步写还需 FullFsync，负载升高时排队可造成 100 ms 尾延迟。比较读/写并发梯度与服务端耗时。

## 约束

实验使用 release 二进制、独立临时目录和随机端口；同一时间一个执行者发压。保存原始样本、构建哈希、计时边界、统计方法。先建立基线，再只改一个机制复测，独立验证结论。原版公开 benchmark 仅按工作负载和测量边界对照，不把嵌入式引擎耗时等同于 HTTP 请求耗时。
