# Simple 点查尾延迟：结果帧通道容量对照

## 假设

一个单行点查通常产生 `Columns`、`Rows`、`End` 三帧，而每请求结果通道原容量为 2。若异步消费者尚未取走前两帧，执行线程发送第三帧时进入 `send_frame` 的满队列分支，每次睡眠 5 ms。该线程串行处理同一个数据库的所有请求，睡眠会传递到后续请求的排队时间。

## 方法

只改动结果帧通道容量：A=2（release SHA `55ea2c21...`），B=3（release SHA `4555a10c...`）。按 **A1 → B1 → A2 → B2** 顺序运行，进程和数据目录每次重新创建。每次运行同一脚本：单库单行主键点查，32/64 并发，升序和降序两轮，每档 5 秒、档间休息 1 秒；客户端与服务同机，持久 HTTP 连接，每次校验 `rows=[[42]]`。保存逐请求客户端耗时、响应 `elapsed_micros`、状态和汇总；本地 `raw/capacity_ab_*` 被 Git 忽略。脚本为 [bench_concurrent_attribution.py](bench_concurrent_attribution.py)。

| 并发 | 容量 2：成功吞吐 req/s | 容量 3：成功吞吐 req/s | 容量 2：HTTP P95 ms | 容量 3：HTTP P95 ms | 容量 2/3：≥100 ms 请求 |
|---:|---:|---:|---:|---:|---:|
| 32 | 1,765–2,688 | **4,409–4,546** | 26.28–41.96 | **10.75–11.71** | 105 / 0 |
| 64 | 1,489–2,823 | **4,073–4,355** | 49.75–81.17 | **23.50–29.41** | 387 / 223 |

四次运行、16 个档位合计 **259,291 次请求，0 个观测错误**；独立复核逐请求样本与汇总统计一致。上表是各档四次运行的观测范围，不是稳定容量或置信区间。容量 2 的两次运行自身也有波动，但回切后 32/64 并发的 P95 均再次高于容量 3，方向一致。容量 3 在更高完成吞吐下仍取得更低 P95，支持满通道 5 ms 轮询是单行点查尾延迟的重要来源。

## 边界与风险

- 容量 3 恰好容纳本负载的三帧；多行结果若产生更多 Rows 帧，慢消费者仍会使 `send_frame` 满队列轮询并阻塞单库线程。因此这次修复不是通用背压优化。
- 容量 3 的 64 并发仍有 223 次请求达到 100 ms。小结果已不会走满队列分支，这些剩余异常需要进一步区分 Catalog、客户端调度、单库队列和系统负载。
- 多缓冲一帧仍是有界内存；单帧受 `max_result_frame_bytes` 限制，但大量并发请求会增加总缓存。取消、deadline 与帧顺序代码未变。
- 响应 `elapsed_micros` 的计时起点在 `host.execute(...).await` 之后，执行线程有时已发送帧，故不能把该字段与客户端耗时的差值直接解释成 HTTP 或 Catalog 开销。
