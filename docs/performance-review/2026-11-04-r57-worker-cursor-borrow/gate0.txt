## 命中计数

H1 每查询 8,625 行、每页 256 行，共 **34 页**；两种协议的每条只读页都由
`WorkerResult::ReadCursorPage` 产生。两次独立批次（原始三次场景运行 + 复测三步运行）
读数完全一致。

| 场景 | 协议 | 每查询页数 | 每条查询 `first` | 每条查询 `fetch` | 判定 |
|---|---|---:|---:|---:|---|
| H1.content-20mb | json-cursor | 34 | 1 | 33 | OK |
| H1.content-20mb | protobuf-cursor | 34 | 0 | 34 | OK |
| L2.list-empty（单页 0 行） | json-cursor | 1 | 1 | 0 | OK（关掉对照） |

- json-cursor 走 v3 JSON cursor 的**融合首页**（`open_read_cursor_first`，`cols=Some`），
  之后 33 页是 `fetch_read_cursor`（`cols=None`）——`1 + 33 = 34` 页全部命中借用序列化。
- protobuf-cursor 走 native HTTP cursor：先 `/v1/sql/cursor/open` 取列元数据，再逐页
  `/v1/sql/cursor/fetch`，因此**每页 `cols` 都是 `None`**，34 页都记作 `fetch`。
  这是既有协议差异（见 `hrana_http_cursor.go` 的 open/fetch 分支），不是本轮引入；
  两种协议下每查询的借用序列化次数都是 34。
- 全局计数（两次批次一致）：json `first+1 fetch+33`，pb `fetch+34`，
  L2 `first+1 fetch+0`。

## 「关掉」对照

- **单页 cursor**：`L2.list-empty`（0 行、1 页）`fetch=0`——没有下一页就没有额外页序列化。
- **写 cursor**：用同一 gate 二进制经 `/v3/cursor` 发
  `UPDATE threads SET title = title WHERE id = '__r57_gate_none__' RETURNING id`：
  返回 `200`、`step_begin` 带 `cols=[{"decltype":"TEXT","name":"id"}]`、
  `step_end affected_row_count=0`，**探针行数为 0**（276 → 276）。
  说明写 cursor 的回复仍由 `serde_json::Value` 树产生、不经过借用序列化；
  行的确由 worker 执行（`step_begin`/`step_end` 都在），不是「命令没到 worker」。
  数据未被修改（`WHERE id = '__r57_gate_none__'` 不匹配任何行）。
- 写 cursor 的窗口形状不变另由 `TestHranaV3JSONWriteCursorKeepsPageFetchesSequential`
  等 Go 平台用例与 `worker_rpc` 单元测试覆盖。
