# R62：延后耐久账户待办上限 256→4096（X1 尾部）

日期：2026-11-04
状态：A/B 完成；验收协议在 A/B 之前冻结（见“冻结的 A/B 协议”）。
结论：主指标（c8/c16 的 p95、p99）两轮四个单元全部达标（−31% ~ −79%），但冻结护栏的
**c1 p95** 失败（合并中位 0.97→6.37ms，+555%）；按 A/B 前冻结的判据，本轮**不合入**，
分支 `perf/r62-deferred-bound` 保留为证据。c1 p50 与 p99 均不差于基线（−3.2% / −22.1%），
失败集中在 5–9ms 的中间尾部；反序诊断中候选 c1 p95 干净（0.54ms），说明它是间歇性的，
需要下一轮用请求级相位探针归因，而不是靠继续加腿数去“洗”过护栏。

## 机制与改动

R37 把非提交操作（open、只读 statement/cursor、close）的 completion/audit 屏障移到回复之后，
由 `deferredDurability` 账户按 FIFO 支付。账户此前最多持有 256 条待办；达到上限后，下一条
complete 会在回复刷出之前**内联**支付自己的屏障，于是账户饱和直接变成客户端时延。

R59 已排除池宽（8→64 使 X1 c16 退化）；R61 已排除周期 checkpoint。剩下的上限就是待办条数：
`deferredDurabilityMaximum = 4096` 与审计队列自身的准入上限（4096 条 / 8 MiB）对齐，使审计
队列仍愿意接收的突发不再被账户改写成回复延迟。内联路径保留为账户停止时的 fail-closed 守卫；
顺序、`outcome_unknown`、关闭排空语义均未改动。

分支 `perf/r62-deferred-bound`：
- `861eb8a` `perf(v1)：延后耐久账户的待办上限对齐审计队列（256→4096）`
- `530fcf7` `test(perf)：新增 X1 尾部时间线探针`
- 同分支新增 `/v1/metrics` 的 `deferred_durability`（`pending`、`pending_max`、`maximum`、
  `enqueued_total`、`inline_total`、`semantics`），用于直接判断账户是否饱和。

## Gate 0：100 请求/级下的令牌桶混杂（已解决）

Gate 0 首先在 **100 请求/级**（X1 合同值）上跑：

| 腿 | 二进制 | c16 中位 | c16 p95 | c16 p99 | 429 | 其他拒绝 |
|---|---|---:|---:|---:|---:|---:|
| `g0base1` | 基线 | 20.75ms | 147.62ms | 155.09ms | 0 | 0 |
| `g0cand1` | 候选 | 11.65ms | 536.76ms | 539.02ms | 13 | 3×`quota_exceeded`（HTTP 200 内联错误） |

候选复现 16 次拒绝，基线 0 次。逐请求拆开后原因明确：

- c16 的 16 条拒绝全部来自固定 **500 rps** 项目令牌桶（`rejection_reasons_total.rate_limit=16`）。
  候选在 c1–c8 比基线快约一个数量级（c8 计时段 19ms vs 251ms），把桶提前耗尽；基线因为慢，
  在同一窗口内没有触到桶。
- 拒绝本身是配额的正确行为，但拒绝路径的审计记录（`RecordClass`）要等自己的屏障，而屏障
  排在延后账户积压的 completion 记录之后，于是 429 / 内联 `quota_exceeded` 响应耗时
  **498–547ms**；账户指标 `pending_max=1218`、`inline_total=0`。
- **成功请求不受影响**：同一次 c16 中 84 条成功请求 p50 6.46ms、p95 18.92ms、p99 20.37ms、
  max 20.95ms（调试版 harness 抓取的响应体证明 HTTP 200 的 0 行记录是 pipeline 内
  `{"error":{"code":"quota_exceeded"}...}`，不是查询结果错误）。

把每级请求数减半到 **50**（配额不变）后，桶有余量，两侧 Gate 0 干净：

| 腿 | 二进制 | c8 p95 / p99 | c16 p95 / p99 | 错误 | 429 | `pending_max` |
|---|---|---:|---:|---:|---:|---:|
| `g0base50` | 基线 | 37.20 / 37.53ms | 130.75 / 131.15ms | 0 | 0 | —（基线无此指标） |
| `g0cand50` | 候选 | 10.31 / 19.17ms | 3.47 / 4.17ms | 0 | 0 | 746 |

因此 A/B 采用 50 请求/级：不修改任何配额，只让测量窗口落在桶的突发预算之内；100/级下的
拒绝行为作为**配额边界副作用**单独记录，不进入时延判决，也不被隐藏。

## 冻结的 A/B 协议（Gate 0 通过后写入，A/B 前未再修改）

- 每条腿：独立栈 + 全新 run dir + 重新 seed；worker 两侧相同；平台二进制按 A/B 角色切换。
- 命令（每条腿完全相同，只有 `leg`、`port`、`platform` 不同）：

  ```bash
  ./run_leg.sh <leg> <port> <platform-binary>
  # -> run.py --scenario X1 --rounds 1 --warmup 0 --samples 1 \
  #           --concurrency-requests 50 --allow-misses
  ```

- 顺序：2 轮 × A/B/B/A（基线、候选、候选、基线），共 8 条腿；端口 19701–19708。
- **主指标**：X1 c8 与 c16 的 p95、p99（`summary.json` 的 `concurrency[].p95_ms/p99_ms`）。
  每轮取该轮两条 B 腿的中位与两条 A 腿的中位比较；候选须在 **c8 p95、c8 p99、c16 p95、
  c16 p99** 四个单元上均 ≤ 基线的 90%（≥10% 改善），且两轮同向。四个单元在 4 条腿上的
  合并中位也须 ≥10% 改善。
- **护栏**：c1/c4 的 p50 与 p95 合并中位不得比基线差 >10%；全部腿 `errors=0`、`status_429=0`、
  `rejection_reasons={}`；所有成功请求 `rows=1`；响应字节与基线同分布；fixture 校验通过；
  候选腿 `deferred_durability.inline_total=0`；launcher stop 为 `clean` 且
  `unresolved_operations=False`。
- **无效腿规则**：任一腿出现 `errors>0` 或任何拒绝，该轮四条腿全部重跑，保留无效腿目录并
  记录原因。
- 判据不看单次极值；所有比较都用同轮配对中位。

## 结果

### 主指标（冻结判据：四个单元均 ≥10% 改善，两轮同向）

| 轮 | 单元 | 基线合并中位 | 候选合并中位 | 变化 |
|---|---|---:|---:|---:|
| 1 | c8 p95 | 34.64ms | 15.64ms | **−54.9%** |
| 1 | c8 p99 | 38.21ms | 15.95ms | **−58.3%** |
| 1 | c16 p95 | 126.49ms | 48.20ms | **−61.9%** |
| 1 | c16 p99 | 126.98ms | 48.64ms | **−61.7%** |
| 2 | c8 p95 | 79.26ms | 24.05ms | **−69.7%** |
| 2 | c8 p99 | 119.54ms | 24.73ms | **−79.3%** |
| 2 | c16 p95 | 49.55ms | 21.93ms | **−55.7%** |
| 2 | c16 p99 | 51.38ms | 35.40ms | **−31.1%** |
| 合并 | c8 p95 | 35.97ms | 24.05ms | **−33.1%** |
| 合并 | c8 p99 | 76.30ms | 24.73ms | **−67.6%** |

主指标 **PASS**：两轮 × 四单元共 8 个比较全部同向且 ≥10%（最小 −31.1%）。

### 护栏（冻结判据）

| 护栏 | 基线合并中位 | 候选合并中位 | 变化 | 结果 |
|---|---:|---:|---:|---|
| c1 p50 | 0.472ms | 0.457ms | −3.2% | PASS |
| **c1 p95** | **0.973ms** | **6.370ms** | **+554.9%** | **FAIL** |
| c4 p50 | 0.727ms | 0.555ms | −23.6% | PASS |
| c4 p95 | 104.75ms | 7.35ms | −93.0% | PASS |

- 运行性护栏全部通过：8 条腿 `errors=0`、`status_429=0`、`rejection_reasons={}`、所有成功请求
  `rows=1`、响应字节分布一致（两侧均 308–325，中位 312）、fixture 校验通过、候选 4 条腿
  `inline_total=0`、launcher stop 均为 `clean` 且 `unresolved_operations=False`。
- c1 p95 的失败由每腿 50 个样本的“第 3 高值”决定，逐腿值为
  A：0.90 / 0.52 / 1.04 / 5.33ms；B：7.35 / 5.39 / 0.60 / 9.29ms。c1 p99（参考）反而是
  基线 15.09ms → 候选 11.76ms（−22.1%）。合并原始样本里 >2ms 的 c1 请求为 8/200（A）与
  13/200（B），候选的中间尾部更频繁、但极值更小。
- 反序诊断（`legs-diag/`，不进判决）：候选先跑 c1 p95=0.54ms、基线后跑 c1 p95=0.54ms，
  说明候选可以在干净的宿主状态下打出与基线相同的 c1 p95；冻结协议内的 3/4 候选腿出现
  5–9ms 尖峰，未能归因到某个确定性阶段。

### 机制证据

- 候选 4 条腿 `deferred_durability.pending_max` 为 645–770、`inline_total=0`，账户确实不再
  把突发改写成回复延迟；基线没有该指标。
- 运行结束时候选审计队列仍有 246–337 条、年龄 181–238ms 的待办（基线为 0），说明深度延后
  把工作搬到了回复之后，而不是消失。
- 配额边界副作用（100 请求/级，证据在 `gate0/g0dump/`）：候选因速度快而把固定 500 rps 桶
  提前耗尽，产生 429 / pipeline 内 `quota_exceeded`，且拒绝记录排在延后积压之后，响应约
  500ms。50 请求/级时两侧均干净；该行为单独记录，不进入时延判决。

### 判决

按冻结判据：**主指标 PASS、护栏 FAIL（仅 c1 p95），本轮不合入**。分支与提交保留为证据：

- `861eb8a` 上限 256→4096 与 `deferred_durability` 指标
- `530fcf7` X1 尾部时间线探针

下一轮：在 c1 上做请求级相位归因（open/statement/close 的 journal/audit/native 分段），
先确认 5–9ms 尖峰落在哪一段，再决定是修实现还是修测量方式；在此之前不改变本轮冻结判据。
