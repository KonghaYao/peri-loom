# peri-loom #15：基于 v1.1.17 的长尾优化实验

日期：2026-10-27（Asia/Shanghai）。**未解决 #15，未达到预定性能验收目标。** 本包是通过已执行正确性检查的实验候选，不能按已证实的性能修复发布。

## 版本和新增评论的关系

[v1.1.17 新增复测](https://github.com/KonghaYao/peri-loom/issues/15#issuecomment-6435121521) 与上一轮“未稳定达标”的结论一致。官方 v1.1.17 `1872100d9945b1534ae9d60234365e69a554713a` 已包含上一轮交付的性能代码；逐 Git blob 比较仅 Cargo.toml/Cargo.lock 版本号及 platform/README 三文件不同。本轮直接以这个官方版本为 A，旧实验中的 A 和降幅没有混用。

用户评论来自 Apple M4/OrbStack、含复用 v6 卷；本轮是 Linux x86_64、每场景独立新卷加固定历史。评论中的原始 JSON 和原压测脚本尚未取得。H6 新建逻辑 SDK session，但 Node fetch 可复用 TCP/TLS；不能把它等同于强制新 TCP/TLS 或新进程的“新连接”。原脚本的分位数算法未知；若采用 nearest-rank，50 次采样的 p99 等于最大值，也不应与本轮 2000 次的分位数直接对照。

## 已实现的三个改动

1. 请求内解析页缓存改为有界 CLOCK，保留 4 MiB 计费上限与 1024 项上限，在工作集变化时淘汰旧页。该数字不是实测 RSS 或整个请求的内存上限。
2. 回执恢复校验只隔离短命 replay backend，复用同一请求的 Authority 不可变页缓存；进入/退出时清除该 backend，防止栈地址复用隐藏错误。完整命名空间、hash、order/depth/path 与 pending-page 验证仍保留。
3. 正常逐条追加、可归档的新格式路径通常每次归档 65 项；一般归档数仍为 `min(eligible, excess + 64)`。选择最老 eligible receipt 为锚点，沿完整 BLAKE3 顺序取同批身份，再按原 `(lsn, identity)` 顺序和原 64 条批次重放，减少触及的索引分支。本次新增与无 digest 的 legacy receipt 仍留 inline。inline 不再严格保留最近窗口；最老锚点保证可归档身份持续移出。无 digest 的 legacy 例外仍可使 inline 超过 256 项，未改变原处理方式。

没有改页格式、数据库 schema、存储同步屏障、fencing、reader pin/GC、ACK 条件或 SDK 行为，没有 SQL 自动重试。Go 生产代码完全不变，A/B 使用同一个 Go 二进制。Turso 固定为 `24a3a4609683b73935888f8bc30b47727d100aa8`。

测量候选为 `856d4702bc04f00315cefb3efc89e3b10a2c8ccc`，由 `0b48151`、`3ae3e51`、`856d470` 三个独立提交组成；测量之后仅增加本说明文档。

## 完整两轮 ABBA

`abba-verified`：两轮 A1→B1→B2→A2，每臂 H4/H6 各 2000 timed，共 **32,000 timed**。每场景 1000 行 fixture、512 prelude、50 warmup，C1 串行，实际发起间隔至少 50ms，无追赶或重试。真实 serverless SDK 1.4.1、TLS 验证、严格 ACK/close/精确读回；pack/completion/writer admission/observer 均关闭，配额不变。计时在 SDK 最后一次 resolve 结束后，才核验独立 response clone 和写证据。测试、构建、压缩及分析均在正式计时窗口之外。

以下每个 A/B 合并值各含 4000 次；变化为 B/A−1，负数表示降低。

| 轮次 | 场景 | p50，ms（A→B） | p99，ms（A→B） | p99 变化 | >100ms（A→B） |
|---|---|---:|---:|---:|---:|
| 1 | H4 | 26.602 → 25.864 | 79.082 → 61.322 | -22.46% | 28/4000 → 19/4000 |
| 1 | H6 | 32.481 → 31.430 | 84.066 → 69.495 | -17.33% | 29/4000 → 16/4000 |
| 2 | H4 | 25.932 → 26.511 | 67.192 → 69.769 | +3.84% | 18/4000 → 28/4000 |
| 2 | H6 | 32.034 → 32.801 | 134.620 → 93.801 | -30.32% | 60/4000 → 37/4000 |

预先冻结的通过条件：每轮 H4/H6 的合并 p99 均至少降低 20%；所有相邻配对 p99 不回退、p50 回退不超过 5%；每轮 >100ms 比例降低；所有原始证据检查通过。**只有 R1/H4 同时满足该组全部条件，整体 FAIL。**

关键回退：R2/H4 的 >100ms 从 18/4000 增至 28/4000；R2 的 A2/B2 p99 在 H4/H6 分别回退 10.83%/8.08%；A1/B1 p50 分别回退 5.19%/7.21%。全体 B 的 >100ms 总次数虽从 A 的 135 降至 100，不能掩盖这些分组回退。moving-block bootstrap 的 R2 两组 95% p99 ratio 区间均跨过 1，详见原始审计。

完整新运行的 40,992 次含 prelude/warmup 写入均有精确读回，98,504 HTTP ACK，16 次场景停止均 clean/joined/exit 0；无 Unknown、429 或 SQL 重放。源代码、二进制、SDK、helper、配置与容量边界逐一核对。该结论只属于完整新运行，不包括下面的失败实验。

## 归因进展与仍未解决的原因

另有 A/B 各 4000 timed 的完整深度诊断。候选全 scope 解码总量约减少 25%，后段归档 root mutate 中位数约减少 43%；后段 receipt pages 中位数 H4 为 57→49.5，H6 为 57.5→42.5。真实逐请求证据支持内部重复工作减少，但不足以保证端到端尾部稳定下降。

基线 13 个 >100ms 请求全部匹配实际 receipt roll，12 个在最后 500 次；最慢 H4 发布 383 个对象，group 157.90ms，单体 fsync 最大仅 4.62ms，说明大量对象的累计工作可以主导尾部。候选诊断也出现连续非 roll 慢请求：最慢 779.44ms，write/read/close 多个服务端 intent、terminal、audit、native 持久化阶段同时抬高；其中 native 普通写只有 15 个对象，group 241.73ms。上述最慢请求已用 HTTP/Gateway/Worker request ID、append ID、Authority request ID、publication ID 精确关联；全体请求没有完整的跨层 ID 覆盖，其他事件部分仅按时间窗关联。不能把上述候选尾点叫作纯客户端 GC，也不能仅凭 fsync 墙钟推断设备或宿主根因。

诊断端到端结果保留：H4 p99 64.614→64.552ms，>100ms 6→9；H6 p99 64.086→68.076ms，>100ms 7→13，p50 回退 7.67%。BackendScope 改变 nested local 计数归属，因此解码对比使用全 scope 合计；`parsed_rejected=0` 不代表没有淘汰，候选 H4/H6 分别有 3898/4053 次淘汰。

正式测量关闭 server trace。正式候选最大值 335.35ms（R2/B2/H6 #1922）主要在 read；不能把其他诊断请求的 fsync 原因套到这个事件上。真实 Rust slow status 仍标 `complete=false/non_harness`，虽然无已报丢弃/写错，不能称为完整跨层事件账本。

下一步需要：原 M4/OrbStack 压测脚本与评论中的三个原始 JSON；相同目标主机上的空闲 ABBA、新卷与原 v6 卷分开；同请求的 client event-loop/response-read、Go adapter/audit checkpoint、逐 body sync/rename/dirsync 和宿主调度/块 I/O 时间线。本环境 `/proc` 所需采样不可用，缺失不能当零。本轮不能证明 M4 场景已修复，也不能证明所有极端尾点来自环境。

## 一次实际 ENOSPC 失败，完整保留

第一次正式尝试 `abba-final` 在 R1/B2/H4 的 prelude index 172 发生 RootPublish `No space left on device`。此前 A1/B1 的 8000 timed 全部保留；该失败写只有一个实际 HTTP 请求，返回 Unknown，之后没有读回、close 或 SQL 重试。命名空间隔离且停止为 dirty，不能声称该 SQL 回滚或最终未提交。失败卷未修改、未重启。

当时 32GB 实验盘满。仅删除已验证且可重建的 P0/V1 Cargo 构建缓存及下载归档，保留全部源码、最终 binary、测试/测量日志与实验卷，恢复约 12GB 空间。新增每 arm/scenario 启动前 available≥4 GiB 且 used<90% 的门禁后，另起 `abba-verified` 完整两轮，未拼接旧结果。新运行全部 48 个容量快照及 24 个启动边界通过，最小 available 5.119 GiB。磁盘保护不改变 SQL、持久化、配额或计时。

## 使用与复测

在官方仓库 v1.1.17 基础上应用 `patches/from-v1.1.17.patch`；完整 `source/` 已附固定 Turso 源码。使用 Rust 1.98.1 和 Go 1.23.12 重建；附带二进制仅为 Linux x86_64，不能直接用于 macOS/arm64。生产发布门禁仍以仓库流程为准，本包不替代目标平台验证。

```bash
cargo build --release --locked --manifest-path prototypes/v1/Cargo.toml
cd prototypes/v1/platform
go build -buildvcs=false -o peri-platform ./cmd/peri-platform
```

完整复测入口在 `evidence/current/abba-verified/helpers/PROTOCOL.zh-CN.md` 和 `run-issue15-abba.py`。准备两个干净 checkout、各自二进制与 SDK 依赖；沿用 `--rounds 2 --samples 2000 --warmup 50 --prelude-writes 512 --period-ms 50 --scenarios H4,H6`，并使用该目录冻结的 audit。ZIP 不含 `.git`、node_modules 或编译缓存；原始脚本验证 Git 身份，需要在真实 checkout 应用补丁并提交后运行。
