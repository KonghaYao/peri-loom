# 独立超限性能测试场景与验收设计

日期：2026-10-16。状态：设计稿；未实现独立 runner、未运行基准、没有性能 PASS。

## 1. 目标与边界

建立独立于 Peri 应用和 peri-loom 实现的性能测试规范。Peri 只提供真实负载形态和现有规模参考，不作为测试依赖：运行时不连接真实 Peri、不导入其业务模块、不要求其私有数据、状态文件或压测脚本。生成器、调度器、正确性 oracle 和结果格式由独立测试体系定义；通过目标 adapter 接入原生 TursoDB、peri-loom 或其他候选实现。

目标不是证明小数据测试很快，而是回答：在超过当前业务规模的负载下，系统的安全容量、瓶颈、过载行为和恢复边界是什么？每个正式场景都有强制压力下限与递增阶段。小规模 smoke 只验证工具，不计性能覆盖。

本轮仅设计文档，不创建测试表、不改生产结构、不运行压力。具体测试表、索引与生成器实现须另行提出并批准；下文的“对象、事件、关系”仅是逻辑数据模型，不是 DDL。

## 2. 独立输入：规模快照与合成数据

### 2.1 Peri 是参考样本，不是运行依赖

由一次性、经授权的采集或人工统计提供脱敏规模快照；批准后冻结为普通配置，后续运行离线读取配置并生成合成数据。没有 Peri 访问权限时仍能开发及运行候选负载，但不得宣称已满足“当前 Peri 两倍”。

现有仓库场景代码不是实际业务规模证据。本设计尚未取得当前 Peri 的数据量、并发和请求率，以下符号均为待测输入，不能擅自填零或用默认 fixture 行数替代。

| 符号 | 含义与采集口径 |
| --- | --- |
| N_i / B_i | 各逻辑集合的记录数 / 未压缩逻辑数据字节数；保留集合间关联基数 |
| W_q | 查询族 q 在固定观察窗口实际访问的工作集字节数，不能只报全库大小 |
| C / R | 代表性业务高峰的同时在途操作数 / 每秒业务操作到达率；固定统计窗口，建议使用可得的最近 7 天忙时数据 |
| S / X | 活跃会话数 / 同时在途事务数 |
| D / T | 数据库数 / 租户数，并记录活跃与闲置比例 |
| H / L | 保留提交历史条目数 / 当前待回放 WAL 字节数 |
| V / F | 大值大小分布 / 关系扇出分布，至少记录 p50、p95、p99、最大值 |
| K / G | 一次维护覆盖的脏段数量 / 待回收对象数量 |

快照必须记录采集时间、观察窗口、来源说明、统计方法和配置摘要。冻结后可复现；发布新一轮结果前确认快照仍代表“当前规模”，否则更新快照并建立新基线。原始记录、SQL 参数、凭据和用户内容不得进入文档或公开证据。

### 2.2 查询规模强制规则

对每个被查询的主要集合，而非只对全库总数，要求：

- `N_test_i >= ceil(2 × N_i)` 且 `B_test_i >= ceil(2 × B_i)`。
- 查询工作集 `W_test_q >= 2 × W_q`；扩大取样键空间，不能把库扩大后仍循环查询少量热键。
- 保留字段长度、选择率、关联扇出、热点倾斜及时间分布；重复同一行或填充无关大字段不算达标。
- 正式至少运行 2×档，并沿 4×、8×继续推进，直至容量拐点或预先批准的资源／费用上限。
- 缓存压力档还要求访问工作集超过冻结缓存预算，目标至少为预算的 2×；保持资源预算不变，不随数据扩容偷偷加内存。

“业务规模翻倍”与“系统超限”是两个独立条件：2×可能仍很轻，必须继续加压并记录拐点；未到拐点就触及预算，只能报告已测容量下界，不能声称测得极限。

### 2.3 所有场景的压力构造

每个场景指定一个主要放大维度，正式下限为该维度的 2×现实参考值；推荐阶梯为 2×、4×、8×。先单轴放大归因，再跑明确列出的双轴组合，避免所有维度同时翻倍后无法解释结果。

参考量为零、未知或不足以产生压力时，需要批准明确的合成规模。此类结果标记 `SYNTHETIC_REFERENCE`，不能混入“Peri 2×覆盖率”。已知业务规模不足以压满系统时，继续扩大压力轴，不降低资源隔离要求。

合成数据必须有确定种子、唯一身份和独立 oracle；关联完整，数值聚合可预先计算，包含新旧时间段、热点和长尾。生成器输出数据清单与摘要，两个目标读取同一逻辑数据集。

## 3. 场景目录：每项均为超限场景

下表是正式压力场景，不包括工具 smoke。涉及查询的场景都继承第 2.2 节数据量和工作集下限。每个阶梯的实际规模、完成状态、正确性与压力证据分别记录；某项功能不支持，记 N/A 或 SKIP，不能算通过。

| ID | 场景与负载形态 | 强制超限输入与递增轴 | 正确性 oracle | 主指标与优化方向 |
| --- | --- | --- | --- | --- |
| E01 | 超大数据点查、列表及深分页；来自详情页、历史列表 | 每集合行数/字节/工作集≥2×；2/4/8×数据阶梯；另测 C 的2/4/8×。索引点查、过滤排序、OFFSET与keyset作为独立子项 | 返回身份、顺序、边界及完整分页无重漏，对照生成器预期 | 操作p99、扫描量、CPU/op、RPC/op、结果编码；发现固定开销和深分页退化 |
| E02 | 大范围聚合、排序与多表关系查询；来自统计与检索 | 数据≥2×；中间结果工作集超过缓存预算2×；关系扇出保持真实分布，另设2/4/8×高扇出专项 | 独立计数、求和、分组集合；固定排序次级键 | 峰值内存、临时I/O、CPU、耗时、预算拒绝；定位中间结果膨胀 |

| E05 | 大值、大结果与慢消费者 | 总数据≥2×；大值目标至少2×当前p99；响应目标字节2/4/8×业务p99；消费者限速，冻结速率 | 类型、长度、内容摘要、完整消费状态；超预算请求应明确拒绝 | 峰值内存、首字节/完整结果时间、带宽、背压、取消回收；禁止截断冒充成功 |
| E06 | 小业务表、超长提交历史 | 固定业务表大小，历史长度从max(2H, 10000)起，逐级翻倍；明确保留策略，不把未保留历史计入规模 | 已确认状态、历史保留边界和回执查询结果 | 每次提交metadata GET/bytes、CPU、alloc、p99随H曲线；暴露历史依赖 |
| E07 | 超大WAL恢复与冷启动风暴 | WAL从max(2L, 256MiB)起递增；同库并发首请求从2C起，另测多库；缓存状态分档且有证据 | 恢复后的已确认数据、事务一致性、重复请求无隐式重放 | 下载/校验/回放/首SQL分段耗时、峰值内存、加载次数；识别全量复制与唤醒竞争 |

| E10 | 前台高压叠加checkpoint和GC | 前台数据≥2×、到达率≥2×参考；脏段/待回收对象分别≥2K/2G并递增；固定安全维护计划 | 前台提交与回读、保留对象可读；仅对自有fixture验证回收 | 前台p99、维护独占、上传放大、队列与CAS；定位维护对业务的干扰 |
| E11 | 超容量突发与过载恢复 | 数据≥2×；先测安全容量，再以其1.25/1.5/2×到达率突发，且峰值不低于2R；逐项延长突发时长 | 准入/拒绝/Unknown分类、已确认提交不丢；取消不作为未提交证明 | 计划到达至完成延迟、积压、拒绝、资源峰值、回到稳定容量所需时间 |
| E12 | 超大规模长稳 | 数据≥2×；分别保持历史/目录等规模≥2×；至少24h。持续到达率目标≥2R，但必须位于实测安全容量内 | 分阶段核验账本/摘要、资源生命周期；确认提交与错误不混计 | p99、内存、FD、存储成本的时间趋势；识别泄漏和长期退化 |

补充限定：

- E02若达到资源预算，应明确、可解释地拒绝；“返回更快的错误”不是查询加速。
- E05把合法大结果与越过接口硬限制的输入分开。后者测拒绝与资源边界，不参与成功吞吐排名。
- E06固定小表是为了隔离历史增长，不要求同时扩大业务表；压力轴是历史，不是查询数据量。
- E07的256MiB、E06的10000条是设计建议的合成下限，不是已有业务统计或已获运行授权。物理WAL无法安全构造时记NOT MEASURED，不伪造配置字段。
- E08/09原生单库引擎没有租户/控制面语义时不模拟假平台；只比较公共SQL子负载，其余N/A。
- E10不得通过修改生产对象或绕过保留/读者保护构造GC压力。
- E12若2R超过安全容量，结论为“当前系统不满足2×持续负载”；另跑安全容量内长稳只能补充证据，不能替代2×验收。不要求系统在无限过载下长期成功。

## 4. 原生 TursoDB 对照合同

### 4.1 执行与依赖边界

独立runner只依赖版本化工作负载描述、数据生成器、调度器和adapter接口。工作负载定义逻辑操作、事务边界、参数分布、预期结果和压力计划；adapter仅负责建连、执行、取完结果和生命周期映射，不在adapter中偷偷换SQL、重试或省略结果消费。

原生adapter使用与被测peri-loom相同commit的TursoDB fork、本地持久数据库及明确的同步设置。peri-loom adapter可以使用其公开协议，但测试工具不能导入Peri业务代码，不能依赖现有stress包或P0–P6内部审批文件才可定义场景。实际部署的运行安全准入仍须遵守，独立性不意味着绕开安全机制。

公共SQL场景必须两侧都执行；目标特有能力通过可选capability声明，不支持时明确报告，不能无声降级为不同场景。未来是否增加引擎/存储路径中间层，由实际归因需要决定，不作为第一版运行前提。

### 4.2 公平性与不可比项

- 固定引擎commit、构建模式、特性、数据集摘要、SQL及参数序列、事务批次、资源限制和计时边界。
- 本地TursoDB与远程存储系统持久性边界不同；如实记录同步、加密、TLS、审计、存储介质及网络RTT。原生内存库不得替代主持久基线。
- 对比整个被测服务集合的CPU/内存，并另列分组件指标；不能只计Worker而忽略Gateway/Authority成本。负载发生器独立计费并监控是否饱和。
- 分别报告原生引擎执行延迟与平台端到端延迟；跨边界比值是系统成本对照，不是纯引擎胜负或某模块开销证明。
- 对平台专属E08/09/10等指标，以同配置优化前后比较为主；原生N/A不得填零。
- 各目标串行占用同一隔离资源环境，轮换测量顺序，至少3轮；固定环境不随某目标调参。针对目标的调优必须另开具名配置组。
- SQL正确性门禁的固定64MiB hash预算和禁用快照更新规则保持不变。性能试验另建结果命名空间，明确并冻结两侧相关内存预算，不能冒充既有SQL门禁结果。

## 5. 执行协议与容量判定

### 5.1 每个场景的执行顺序

1. 预检：批准隔离fixture、资源/费用上限、运行时长、数据规模配置与SLO；核对版本及凭据隔离。
2. 小规模smoke：验证adapter和oracle，不计正式覆盖。建立超限数据集并核验真实行数、字节、工作集及分布。
3. 建立1×参考或低负载定位点，仅用于解释曲线，不替代正式2×以上档。
4. 在固定资源下运行2×、4×、8×压力阶梯。先单轴，后组合；每档重新确认数据和状态，写入场景避免运行顺序造成历史污染。
5. 观测拐点后在最后稳定档与首个失败档之间细化一次或多次，报告区间及精度，不制造单一精确极限值。
6. 单独运行E11过载与恢复；任何正确性破坏、隔离失败或硬安全边界触发都停止整批，保留证据，不自动重放写入。
7. 在持续高压前完成容量定位，再运行E12；校验结果、收集资源和负载证据，输出每档报告。

对短时稳态场景，建议每档预热至少2分钟、测量至少10分钟、至少3轮；事件型冷启动/恢复使用独立重复事件，不按固定10分钟假装稳态。大数据初始化与历史/WAL构造单独记成本。尾延迟样本不足时披露样本量，不输出不可信的高分位数结论。

### 5.2 安全容量与足压证据

安全容量是：在冻结资源、数据规模和SLO下，满足正确性、成功完成率、尾延迟、无持续积压及资源上限的最大已验证负载。SLO必须在正式测量前按场景填值并批准；未填只能出探索曲线，不能判性能通过。

容量拐点包括：超出SLO、积压持续增长、吞吐停止随压力提升、准入持续拒绝、资源逼近硬限。错误和拒绝不能提高成功吞吐。平台按设计拒绝可以通过过载安全验收，但该负载不能计入安全容量。

每个正式场景必须提供两类证据：

- **规模足够**：实际达到2×参考及场景附加下限，不仅是配置声明。
- **压力足够**：已找到容量拐点，或明确记录到批准资源/费用上限仍未到拐点。后者标记LIMIT_NOT_FOUND，只能声明容量下界。

开环调度以预定到达时刻记录延迟，单独记录派发滞后，避免coordinated omission。闭环并发用于连接/锁竞争定位，两种结果不可合并。所有操作以业务操作/s和事务/s为主要单位，SQL条数/s作为辅助，避免批量化改变统计口径。

## 6. 验收、报告与优化闭环

### 6.1 分开判断四件事

| 验收项 | 通过条件 | 不得替代的内容 |
| --- | --- | --- |
| 正确性 | 独立oracle通过；提交、错误、Unknown均可分类；无数据损坏/跨租户污染 | 正确不代表性能达标 |
| 规模覆盖 | 每场景2×参考及附加下限有实际证据 | smoke、计划参数和全库无关数据不算覆盖 |
| 性能目标 | 在已批准SLO与预算内完成规定超限档 | 高拒绝率下的低延迟不算通过 |
| 过载安全 | 达拐点后有界排队/拒绝，压力撤除后可恢复，无正确性损失 | 安全拒绝不代表该档业务容量足够 |

每个用例分别输出上述状态，不用一个PASS覆盖全部。未运行为NOT MEASURED，能力缺失为SKIP/N/A，规模未知为REFERENCE_MISSING，达到测试预算但未找到极限为LIMIT_NOT_FOUND。共享开发机结果只能用于探索，不据此承诺生产容量。

### 6.2 必须保留的结果

- 场景ID、目标及版本、配置摘要、种子、数据集摘要、参考快照及倍率。
- 实际行数/字节/工作集、历史/WAL等压力轴实值、缓存状态证据。
- 请求计划/实际到达/完成数量，业务成功吞吐、提交吞吐、p50/p95/p99及样本量。
- 拒绝、超时、已知失败、Unknown、未派发请求分别计数；全量结果与成功子集延迟分别给出。
- 全系统及组件CPU、峰值/稳态内存、磁盘/网络I/O、FD、队列、运行时资源限额。
- 可获得时记录对象存储请求/字节、审计成本、锁等待和分段trace；不可获得就标缺失，不推算为事实。
- 每轮分布、容量稳定/失败区间、停止原因、恢复时间、oracle结果和证据位置。

### 6.3 用场景决定优化方向

每个优化先绑定场景、主指标、成本护栏和假设，再改实现。例如E06验证“提交成本是否依赖累计历史”，E09验证“无关租户是否被共享串行区拖慢”。优化前后使用同一冻结场景；收益必须超过重复运行噪声，且正确性、持久性和安全边界不退化。

优先实现E01/E03/E04/E06/E11：覆盖查询规模、事务竞争、批量写入、历史退化与过载拐点。所有首批正式用例仍执行2×以上规则，优先级不是缩小压力的理由。

## 7. 尚待落实的输入与交付

1. 获取或人工确认脱敏Peri规模快照；未知字段不得由仓库fixture推断。
2. 逐场景批准SLO、合成下限、隔离资源/费用上限及停止条件。资源硬限前的安全停止不计通过，保留未完成原因。
3. 提交独立逻辑数据模型对应的具体表/索引设计供批准，再实现生成器、runner及目标adapter。
4. 新建隔离数据集，不接入生产压测，不使用真实用户数据；不全局drop cache、不对共享进程注入故障、不修改既有部署身份。
5. 验证runner自身吞吐、定时准确性和内存上界；发生器饱和时该轮容量结论无效。
6. 落地后先产出两目标的超限曲线与缺口清单，再据证据确定优化任务；不预先宣称原生TursoDB或peri-loom优胜。
