# 九臂阶梯压测：HEAD `042476a` 的重复观测

日期：2026-10-17。状态：**观测完成，未申请 SLO**。
范围：`prototypes/v1` 本地全栈（Authority + 两台加密 Worker + Controller + Gateway + Key Broker），
数据集 100k 行，单机 `127.0.0.1`，TLS 开启。
被测二进制：main `042476a` 的 debug 构建，Rust sha256 前 16 位 `42e5c3589c3e4d22`，
平台二进制 sha256 前 16 位 `ce76151d458a70f4`，endpoint `https://127.0.0.1:19443`。
分支 `head-042476a`。本序列与 `2026-10-17-nine-arm-stress-observation.md` 使用相同的臂参数，
但二进制多了两次 IO 提交：`c59efa3`（WAL 追加在状态锁外）与 `042476a`（主库发布在状态锁外）。
因此这是一次**同口径重复观测**，不是两次实现之间的 A/B（两次运行的主机负载、后端和运行目录都不同）。

**本文不宣称 PASS、容量、公平性或 SLO，也不给出任何加速倍数。**
产物内 `performance` 与 `capacity` 恒为 `NOT MEASURED`；各臂 `correctness` 只在
`scale_coverage=VERIFIED_BY_COUNT` 且 oracle 回读完成时为 `ORACLE_VERIFIED`，其余为 `INCOMPLETE`。
这些字段都不因本文改变。

## 0. 一句话结论

9 个臂、每臂 ≤60 s、并发 ≤100、单臂预算 4000 次操作：**`timeout` 与 `unknown` 全为 0，
oracle `mismatched` 全为 0**。所有 `known_failure` 仍是平台准入拒绝（`quota_exceeded`），
与网关计数器的同臂增量逐位对应；会话请求超过 16 时，第 17 个起在打开阶段被拒。
导入后、过载后与空闲 30 s 后的 open/close 探针全部 `exit=0`，本次窗口内未复现打开 504。
**这些只说明该序列里没有数据面超时或未知结果，不说明容量、公平性或任何 SLO 已满足。**

## 3. 失败归因：全部是准入拒绝

网关 `/v1/metrics` 是累计计数器，下表是同一臂前后快照的差分：

| 臂 | `concurrency_limit` 增量 | `session_limit` 增量 | 同臂 `known_failure` |
|---|---|---|---|
| h2 | 2756 | 0 | 2756 |
| h3 | 3395 | 17 | 3395 |
| h4 | 3396 | 85 | 3396 |
| h5 | 0 | 85 | 0 |
| h6 | 0 | 85 | 0 |
| h7 | 0 | 85 | 0 |
| h8 | 2245 + `rate_limit` 598 | 0 | 2843 |
| h9 | 0 | 85 | 0 |

读法：

1. 闭环臂的 `known_failure` 与 `concurrency_limit`（h8 另加 `rate_limit`）逐位相等，
   不存在数据面错误或超时。
2. `session_limit` 拒绝的是**打开会话**这一步，不产生查询级 `known_failure`；
   它体现在打开失败数与 `missing_ops` 里。
3. 请求 32/100 个会话时，恰好 16 个成功；这与上一份九臂记录的观察一致。
   能说的只是**这套配置下单次请求里被接受的最大会话数是 16**，不是容量结论。

## 追加更正（2026-10-17 晚）

后续一次维护长时观测发现，本序列使用的
`.claude/skills/e01-benchmark/scripts/run_platform_queries.py` 把每个操作的派发时刻算成了
`当前时刻 + index / rate`，而不是 `固定起点 + index / rate`。结果等待时间随操作序号平方累积：
`index=200`、`rate=20` 时计划时刻落到 +135 s（应为 +10 s），后面的操作在
`max_seconds` 内根本来不及派发。缺陷已在同一提交修复，并写入
`2026-10-17-maintenance-scheduled-under-load.md` §4。

影响范围：

- h1–h4、h8 的 `rate=0`，不经过该计算，**观测不受影响**；
- h5–h7、h9 的 `rate>0`，实际派发率远低于标注值。它们的 success/known_failure 计数仍然
  是真实观测，但**不能**再被读作“按标注开环到达率施加的过载”。
  §3 关于过载与恢复的表述只描述当时的实际派发序列，不构成过载结论；
- 本文其他部分（timeout/unknown 为 0、拒绝原因、探针、未测量项）不变。

用修复后的客户端重跑速率整形臂之前，不应基于这四臂推断 goodput、排队或恢复行为。
