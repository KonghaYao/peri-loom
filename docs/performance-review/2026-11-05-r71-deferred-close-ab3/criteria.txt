P0 — power controls (both must pass before P1 may be interpreted)
-----------------------------------------------------------------
P0.1 zero control (A1 vs A2, same stack, same time window)
  For every valid triple i (the same 30 triples that feed P1):
    r_i = A2_i / A1_i   (block means).
  merged = median(r_i over the 30 valid triples).
  PASS iff 0.95 <= merged <= 1.05 AND the percentile-bootstrap 95% CI of the
  median covers 1.0. Bootstrap: 10,000 draws, seed 20261105, resampling the 30
  per-triple ratios with replacement (percentile interval).
  If P0.1 fails, the design has insufficient power and P1 must NOT be
  interpreted.

  Sample-size reconciliation (recorded before the first leg, not a post-hoc
  change): the round instruction's P0 bullet says "60 triples", while the
  design section specifies "1 round x 30 triples" and P1 says "30 triples".
  A zero control must be same-stack, same-window, and must use the same
  triples as P1; running a second 30-triple round would either split the
  zero control across windows or give P1 a post-hoc round choice. This
  campaign therefore follows the design section: P0 is evaluated on the 30
  valid triples of this round, and the 60 A-side block means (30 A1 + 30 A2)
  are reported as context only. The numeric band (1.00 +/- 0.05) and the
  CI-covers-1.0 rule are unchanged.

P1 — primary metric (short interleaved design)
----------------------------------------------
Request    one Hrana JSON pipeline request
           {"requests":[{"type":"execute","stmt":{"sql":"SELECT 1",
            "want_rows":true}},{"type":"close"}]}
           over one keep-alive connection per stack. The implicit open fuses
           the statement; the close entry retires the session it opened.
Block      exactly 20 consecutive requests; the block sample is the wall
           clock of those 20 requests divided by 20 (milliseconds per
           request).
Triple     three blocks: A1 (stack A), A2 (stack A), B (stack B).
Order      the order of A1, A2 and B inside every triple is a random
           permutation drawn sequentially from random.Random(20261105). A
           void triple retried later draws a fresh permutation from the same
           stream.
Pacing     0.75 s between consecutive blocks (including across triple
           boundaries), 1.2 s after seeding before the first block.
Rounds     exactly 1 round x 30 triples = 30 triples.
Volume     A side: 2 x 20 x 30 = 1200 requests; B side: 1 x 20 x 30 = 600
           requests.
Validity   A block with any transport error, non-200 response, or rejected
           pipeline result is failed. A triple with any failed block is VOID:
           it is recorded, excluded from every statistic, and retried after an
           extra pause (3 s, doubling on each consecutive void up to 60 s).
           Failures are reported, never hidden.
Metric     a_i = mean(A1_i, A2_i); effect_i = B_i / a_i.
           merged ratio = median(effect_i over the 30 valid triples).
           Bootstrap: 10,000 percentile draws, seed 20261105, resampling the
           30 per-triple effects with replacement.
           PASS iff ALL of:
             (a) merged ratio <= 0.92;
             (b) bootstrap 95% CI upper bound < 1.0;
             (c) the direction is B faster (merged ratio < 1.0; implied by
                 (a)); the number of triples with effect_i < 1.0 is reported.
           0.92 < merged ratio < 1.00 => FAIL. No post-hoc threshold changes.
           Also reported (not a pass condition): the paired absolute
           difference d_i = B_i - a_i in ms, its median, and the
           percentile-bootstrap 95% CI of that median (10,000 draws, seed
           20261105).

P2 — regression gate (this round only)
--------------------------------------
P2.1 F1.select-1 json-pipeline and L1.list-20 json-pipeline
  Per leg: --rounds 1 --warmup 1 --samples 125 = 125 timed requests;
  2 rounds x A/B/B/A = 8 legs per scenario => exactly 500 timed requests per
  side per scenario. Fresh volume per leg, same fixture, default quotas,
  no observer.
  Comparison: pooled p50 and p95 per side per scenario (median of the four
  per-leg p50/p95 values); per-round ratios use that round's two A legs and
  two B legs.
  Reproducible degradation: merged B/A > 1.10 AND both round ratios > 1.0.
  PASS if neither p50 nor p95 is a reproducible degradation.

P2.2 Standard Issue 28 X1 concurrency scenario
  Per leg: run.py --scenario X1 --concurrency-requests 100 (the stock
  levels 1, 4, 8, 16, 100 requests per level; c1 and c4 therefore precede and
  warm up c8). 2 rounds x A/B/B/A = 8 legs. Fresh volume per leg, same
  fixture, default quotas, no observer.
  c8 throughput = 100 / (the harness's c8 elapsed seconds). p50/p95 are
  reported. Comparison: median c8 throughput per side; per-round ratios use
  that round's two A legs and two B legs.
  Reproducible degradation: merged B/A throughput < 0.90 AND both round
  ratios < 1.0.
  The c16 level's default-quota 429s are a known protocol artifact: they are
  recorded as diagnostics only, never used as a criterion, and never allowed
  to excuse a c8 problem. c8 must have 0 HTTP 429.
  The run.py exit code may be 1 because the c16 level fails its own
  concurrency verdict; that is recorded, not treated as a P2/P3 failure by
  itself.

P2.3 Sustained c8 (the key test for the R71b c8 degradation)
  8 concurrent clients, one keep-alive Hrana connection per client. One
  request is the same Hrana JSON pipeline as P1: implicit open ->
  execute(SELECT 1, want_rows) -> close.
  Calibration: each client sends 1 request (8 total); all must be ok and have
  no 429. Then a 1.5 s admission refill.
  Blocks: one block = 8 clients x 25 requests = 200 pipeline requests; each
  client's 25 requests inside a block are consecutive. 1.2 s between blocks
  (admission refill).
  Warm-up: 4 blocks = 100 requests per client (discarded).
  Timed: 16 blocks = 400 requests per client = 3200 timed requests per leg.
  Each leg therefore sends 500 requests per client (100 warm-up + 400 timed),
  matching the round instruction's count; the block gaps are the pre-registered
  "equivalent steady-state design" forced by the default quota.
  Why the gaps: the platform's default per-project token bucket has a 500
  burst at 500/s; one pipeline request charges the open and statement actions
  (close is a control action and does not charge the bucket), so 200 requests
  = 400 tokens < 500, and 1.2 s refills 600 tokens. An uninterrupted flow of
  3200 timed requests would exceed the burst and produce 429s, which the
  default-quota rule forbids. The block size and gap are fixed before the
  first leg and are identical on both sides.
  Throughput = 3200 / (sum of the 16 timed block wall seconds); p50/p95 over
  the 3200 timed request durations. Per-block throughput is reported as
  supporting evidence.
  Comparison: median throughput/p50/p95 per side; per-round ratios use that
  round's two A legs and two B legs.
  Reproducible degradation:
    throughput: merged B/A < 0.90 AND both round ratios < 1.0;
    p50/p95:    merged B/A > 1.10 AND both round ratios > 1.0.
  Any failed request (including 429/503/outcome_unknown/session_moved/
  audit_unavailable) makes the leg invalid and must be reported, never hidden.
  The R71b c8-only cold-burst result (B/A 0.84384) is known evidence and is
  NOT a criterion this round. The c8-only driver may be run once as a
  diagnostic; it cannot change any verdict.

P3 — invariants (P1 stacks A and B, plus every P2 leg)
------------------------------------------------------
1. deferred_session_close direction:
   A stack/leg: the key is absent from metrics-before and metrics-after.
   B stack/leg: enqueued_total > 0, failed_total = 0, retried_total = 0,
                unresolved_total = 0, pending = 0 after drain.
                inline_total may be > 0; that is the expected bound behavior
                under c8 and is recorded, not a failure.
2. session_seats = 0 and active_permits = 0 after settle.
3. worker sessions = 0 for every worker after settle.
4. cleanup_ledger.pending_close.count = 0 and every worker
   lifecycle.pending_close.count = 0 after settle/drain.
5. Audit chain continuous in every stack/leg: every record increments seq
   and links to the previous hash; the count is explainable by the requests
   performed (open, statement, close; refused requests may add no SQL
   completion).
6. No 503, no outcome_unknown, no session_moved, no audit_unavailable in any
   leg. 429 is allowed only in the standard X1 c16 diagnostic level (and is
   counted there); c1/c4/c8 of the standard X1 legs and every other leg must
   have zero 429.
7. Clean stop: launcher-stop outcome=clean, unresolved_operations=false,
   docker stop exit 0.
8. F1/L1/sustained-c8 A and B legs of the same scenario/round carry the same
   workload; their audit count deltas must match within two records. Standard
   X1 legs are compared separately because the c16 429 level is a quota
   artifact; their audit chains must still be continuous and their successful
   action counts must be explainable.

PASS iff P0.1 + P0.2 + P1 + P2.1 + P2.2 + P2.3 + P3 all pass.
