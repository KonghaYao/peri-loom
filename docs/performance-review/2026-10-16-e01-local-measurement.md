## 4. 结论（探索性事实）

1. **C1 vs C16/C100**：成功吞吐从 32.0（C1）升到 46.5~47.7 ops/s（约 1.5×），
   但成功请求 p50 从 ~26-28ms 劣化到 ~82-95ms（约 3×），且 **83-85% 的请求被拒绝**
   （诊断 C100 的拒绝码为 `quota_exceeded`）。并发收益有限、延迟与拒绝代价显著。
2. **实际准入并发是 16，不是 100**：C100 配置下只打开 16 个会话（`partial_admission`），
   峰值在途 16。未改配额，如实记录：**"100 并发"在本部署上不可达**。
3. **8M 首档不可达（当前配置）**：导入在 570k 行因 COMMIT 触发 `sql_timeout` 停止。
   小事务提交可继续（100k 全量成功、56 次 10k-row 提交成功），说明瓶颈是**单事务提交时长**，
   而非 INSERT 带宽（INSERT 阶段 3,362 行/s 量级）。
4. **四族之间无显著差异**：同并发下四族 p50 相差 <15%，点查与深分页在本数据规模未分化。
5. 绝对延迟含每请求新建连接的固定开销（本地 loopback 仍 ~26ms），
   因此上表适合**同边界内比较**，不适合当作引擎净延迟。

## 5. 公平性与边界

- **原生对照缺失**：本技能原生 harness 仅支持 ≤2,048 行 fixture 且单线程（无并发），
  无法在同规模/同并发下对照；本轮**未伪造** native 结果。跨目标即使可跑也必须标为
  边界差异（协议、会话、网络、审计、部署），不能当作纯引擎收益。
- 100 会话来源：PostgreSQL 官方文档典型 `max_connections`=100（用户批准），
  **不等价于 active queries，也不是 pgbench 默认值**。
- 资源效率（CPU/op、内存）：本工具不采集主机资源，`NOT MEASURED`。
- 本机为共享开发机（另有并行任务在跑），不承诺生产容量；未获批 SLO，不判 PASS。

## 7. 优化方向

1. **提交路径**：把提交批次降到 1k-2k 行或改批量导入接口，避免单事务超时；
   8M 需要能跨事务续跑且可回读验证的导入流程。
2. **会话准入**：本部署有效并发 16；提高并发前需先解决拒绝率（`quota_exceeded`）。
3. **连接开销**：每请求新建连接约占本地延迟主要部分，值得评估连接复用对 E2E 的影响。
4. **深分页**：当前深度受 oracle 内存上界限制（本报告 570k 档用 0.13% 深度），
   真正深页需要流式 oracle 之外的方案（例如离线索引清单）。

### 8.4 可信比值与不可比解释

- **C1 同计划对比可信**：双方消费同一 `diag-manifest.json`（同 seed、分布、SQL 文本、4000 条查询序列）、
  同为 100k 行并由各自回读核实；差异是 584.2 vs 32.0 ops/s（≈18×），每族 p50 差 28×–683×。
- **不是纯引擎收益**：原生为进程内嵌入式本地库，平台为 TLS 端到端（每请求新建连接、经 gateway/worker、
  含准入与审计）。该差值应读作**同 SQL 的系统成本对照**，不得当作引擎加速比。
- **并发不可严格对比**：平台 C16/C100 有 83–85% 请求被 `quota_exceeded` 拒绝且 100 并发仅准入 16 会话；
  原生 C16/C100 为 100% 成功。两者完成的工作不同，禁止据此并列比值，仅作 `EXPLORATORY_CROSS_BOUNDARY` 参考。
- 未做资源冻结（未固定在相同 CPU/内存配额下运行），且样本窗口短（C1 各 1000 请求 ≈ 6.8s）；
  极短窗口不代表持续容量，未做延长采样。
- 计时包含关系：`prepare` 含 import 与 generate 子阶段（本次 30,266.9ms 中 import 28,815.6ms），
  不得与 `query` 相加当作总时长；吞吐分母固定为查询阶段墙钟（原生=首条 planned→末条 completed，进程内）。
- CPU/op 与内存：无实测，`NOT MEASURED`。
