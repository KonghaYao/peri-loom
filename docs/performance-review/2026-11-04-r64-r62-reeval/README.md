## 为什么需要重新评估

R62 的冻结护栏是「每腿 50 个 c1 样本的 p95」，即第 3 高值：一次宿主停顿就能把它从
0.5ms 推到 5–9ms。R63 已在同一宿主上证明：

- c1-only 腿（无观察器）两侧的 p95 同为 0.55–0.56ms，仅一条腿越过 2ms；
- 观察器腿**每一条腿的两侧**都有 ≥1 条 >5ms 的 c1 样本，两侧最大值 18.56 / 19.51ms；
- 同一腿内实测单次 journal 等待 max 8.1–12.3ms、audit fsync max 7.2–9.8ms，与尖峰同量级；
- c1-only 腿的 `deferred_durability.pending_max` = 200–243 < 基线冻结上限 256，
  `inline_total=0` ⇒ 该改动在 c1 配置下**结构性不可见**。

因此 R64 的判据修订是：**c1 的尾部（p95/p99/max/>2ms 计数）降级为报告项，c1 中位数保留护栏**；
其余主指标与护栏沿用 R62 的口径。修订理由与全部判据写在 `protocol.md`，该文件在第一次 A/B
腿之前提交并推送；测量开始后未修改。R62 自己的冻结判决不受影响（仍然是不合入）。

## 限速器

本轮候选与基线运行在同一宿主、同一 worker、同一配额下。X1 c8/c16 的尾部在基线上主要由
「完成记录的屏障等待在并发下累积」决定（R37 之后的既有结论，本轮基线的 c8 p95 30.83–136.68ms
与 c4 p95 95.93–99.46ms 复现了这一点）。候选把原本要在**回复前内联支付**的屏障留在账户里
（`pending_max` 661–800 > 基线上限 256），审计 drainer 因此能在同一窗口合并更多记录
（audit fsync 17–20 vs 30–32），c8/c16 的 p95/p99 落到 7–21ms 量级。c1 仍是串行屏障链，
中位数 0.45–0.48ms，两侧相同。本轮没有发现新的饱和项需要单独归因；c1 尾部的宿主抖动已在
R63 归因，本轮只作报告。

## 剩余风险与未测量项

- **崩溃/掉电语义**：候选只放宽延后账户的待办上限（256→4096），不改变耐久时点、审计链顺序、
  隔离与 fail-closed 规则；R37 的崩溃恢复 E2E 结论仍适用。但待办上限提高意味着掉电时可能丢失
  的已完成记录更多（仍是「已确认回复的只读/open/close 记录」，属 R37 用户授权范围）。
- **内存**：4096 条待办的上界由审计队列准入（4096 条 / 8 MiB）约束；本窗口 `pending_max`
  661–800，未压到上限，未测 4096 满载时的内存峰值。
- **c1 尾部**：按新判据不再设门槛；本轮 A 6/200、B 8/200 >2ms，形态与 R63 相同。若后续要
  真正降低 c1 尾部，只能改宿主/屏障成本，不能靠改这个上限。
- **未测场景**：本轮只测 X1；W1 写路径、H1/H3 大结果、F1/L1 小查询未复测。候选 diff 不触及
  写路径意图/终态提交（写记录仍同步 durable），但按协议不做外推。
- **未测配置**：仅默认配额、单机 macOS + 本地卷、无 TLS；不代表容量或 SLA。
- **环境事件**：无。8 条腿全部 clean stop，无 429、无拒绝、无 `outcome_unknown`。
