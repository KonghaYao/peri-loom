差额闭合：`−3.889（免 intent）+0.730（每条读都付一次 describe）−0.354（worker 噪声）

即本轮改动对交付路径只做了一件事：把「不可能提交的语句」的 intent 拿掉。

### 3.3 缓存语义的实测代价（本轮唯一的性能让步）

E01 的 4000 个 C1 操作只渲染出 **2059 条唯一 SQL 文本**（`point` 995、`index_list` 1000 全唯一，
`offset` 与 `keyset` 各只有 32 条——深分页族按同一形状反复取页，单条最多出现 48 次），
所以约 48% 的请求是重复文本：

| 轮次 | classify 段出现条数 | 含义 |
|---|---|---|
| A+B（rb2） | 2060 / 4042 | 双向缓存：每个唯一文本只 describe 一次，重复文本免费 |
| B-only（rb3） | **4042 / 4042** | 只读判定不缓存：每条请求都向 worker 重新取证 |

代价 = 约 **0.63–0.73 ms × 重复比例**：按 §3.2 的三方分解（rb3 − rb2 = 0.543 回退A + 0.407 只读缓存 +
0.181 worker 噪声），本轮实测 **0.407 ms/请求**（占读总时 14.36 ms 的 2.8%），与
`每次未命中 describe × 48% 重复率` 的估算同量级。方向仍然大赚：一次 describe（0.730 ms）
省掉的是 intent（3.889 ms），**盈亏平衡需要 describe 慢到 5.3 倍**。
写语句侧：describe 对写语句是纯成本，由「会提交」缓存兜底——同一文本每个 worker
只白付一次。E01 的导入用的是逐批唯一文本，434 条导入请求里只命中 8 次；
真实应用里重复的 `INSERT … VALUES(?, ?)` 只付一次。

## 4. 收益归因与边界

- 收益方向明确且三轮可复现：49.81 → （A+B）65.11 →（B-only）60.17 ops/s。
  **rb3 的起止 load 3.75→4.43 是本组最低**，却比 rb2 慢 1.15 ms——
  这 1.15 ms 是回退 A（约 0.54 ms）与只读判定不再缓存（约 0.41 ms）的净代价，不是负载差异。
  跨轮绝对值仍受同机其他负载影响（基线轮 load 4.62→8.99），不可当同条件对比。
- **B 的边界**：写语句要白付一次 describe（每 worker 每文本一次，之后由「会提交」缓存短路）；
  只读语句每次依赖前都重新取证（重复只读文本没有缓存收益）。两条都是由 §1 的安全方向决定的：
  缓存过期只会让平台多写一次 intent，绝不会少写。
- **B 的残余窗口（未证伪，不是已证明零风险）**：同一条请求内 describe 与真正执行之间仍有窗口，
  判定的依据是 describe 那一刻的 prepare。并发 schema 变更理论上可让同一文本在第二次 prepare
  得到不同程序。本轮没有构造出能让"只读"翻成"写"的语句类别（视图上的 `SELECT` 无论视图如何变化
  都仍是只读；带写语义的语句在 describe 时即为 committing），也**没有**做穷举验证，故记为残余窗口。
  若将来要让只读判定跨请求存活（本轮明确不做），必须先回答这一条——见 §6 条件①。
- **A 的边界（已作废）**：A 的 fsync 重叠在本机没有稳定兑现（两文件 fsync 基本被串行化），
  且带来审计 `Outcome` 语义与 goroutine 恢复边界两处代价，已回退。
- **仍未做、需要明确批准的一级是 C**：把可证明只读请求的**终态台账记录**也降为内存台账（只留 audit）。
  按当前读数约值 −4.1 ms（14.36 → 约 10.2 ms），但会改变读操作的持久化台账语义；§6 的四条前置条件未满足前不做。

## 5. 下一步

- **D（Authority 侧）已完成实测剖分**：`perf/authority-ownership-6b1f4e02`，提交 `0d95202`。
  release、`LocalObjectStore`、p50：head 1,446 B → read 18 µs / decode(冷) 8 µs / validate 22 µs；
  head 95,374 B → 128 / 485 / 196 µs；head 944,974 B → 1,151 / 4,907 / 1,782 µs。
  **结论与开工时的假设相反**：Authority 侧整个租约校验在生产文档尺寸（约 95 KB）下只有约 0.2 ms，
  **不是**读查询里那 4–5 ms 的来源。decode 复用（已实现并以确定性计数器验证：同一 head 64 次校验
  0 次解码、head 前进一版后恰好 1 次）把 decode 项降到约 1/12（95 KB：485 → 57 µs；
  945 KB：4,907 → 564 µs），但 memo 之后 read 又成为主导项（两种尺寸下都约 65%）。
  因此下一步该测的是 **worker↔authority 的 RPC 往返**（本次测量不含网络），而不是继续优化这里的解码。
- **台账无界已被实测证实**：head 随 `ownership.commands` 从 1.4 KB 长到 95 KB 再到 945 KB 时，
  每次校验的成本近似线性上升（22 → 196 → 1,782 µs）。decode 复用只削掉其中 decode 那一半斜率，
  read 那一半（worker 路径每请求读两次 head）仍在。改它要动 root 文档结构或保留策略，
  属于需要你裁决的设计变更，本轮未动。
- **规模放大（1M / 8M）**等 D 的结论合并后再做，按 §6 第 3 条盯三类成本与 §3.3 的命中率。
  本轮结论只适用于单机 loopback、开发 CA、单 Authority、且观察器开启的配置。
- 已知的额外 describe 来源（未做，列在此备查）：Hrana 高层 execute 的只读语句会被分类两次
  （gateway 分类一次 + 管线预检一次），见 `hrana_execute_cursor_test.go`。
