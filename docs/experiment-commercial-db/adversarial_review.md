## 致命缺口（须先关闭才能发布性能结论）

## 证据与口径的具体攻击面

- **遗漏和伪造仍可自洽：** `evidence.py:103-110` 跳过未知 `type`；`evidence.py:159-177` 接受 `offered = 已记录记录数 + queue_expired`，过期 offer 没有逐条 ID/时间证据，也不验证序号连续、计划 ID/预生成 offer 或外部时钟。`has_unverified_offers` 虽使总体 `PARTIAL`、禁止 benchmark，但其数量仍只是报告自称；没有第三方请求/排队轨迹不得叫独立审计。
- **“有数字”不是容量结论：** `evidence.py:200-228` 验证的是报告 elapsed/offering 与记录总数的商数，未证实单调起止、阶段边界、warmup/drain 归属、offered 生成过程、服务端 admission、业务事务粒度或跨租户分母；`requested_duration_ns` 的门槛不证明真实测量窗口达标。即使 `benchmark` 为对象，也不代表有资源/饱和拐点、置信区间、故障尾部或完整 SQL 工作流。应同时公布 ACK-only 与 all-completed 的 N、失败/Unknown/429 与 client drop 的分母、p95/p99 和采样覆盖，区分 offered 与 admitted，不能把 queue drop 当服务端饱和。30 秒窗口与低并发仅是有限冒烟/曲线，不能外推企业级负载。
- **防泄密不是全盘保证：** `evidence.py:235-244` 的 CLI 通常只输出白名单聚合和通用错误，`sha256` 也不是脱敏证明；它不审计原始 JSONL 的自由文本、权限位、复制到报告的片段或上游日志。`evidence.py:74-76` 只拒绝输入目录/两个文件的末级 symlink，不验证父目录可信、文件权限/拥有者、文件大小、读时是否变化，亦不检测恶意的非白名单字段。不能把该脚本描述成完整防泄密工具；对不可信输入应先用隔离副本和资源限制，校验父目录/权限/大小/稳定哈希、输出 allowlist 与原始数据脱敏策略，并用包含秘密哨兵的对抗测试验证 stdout/stderr/归档全链路。
- **修复前后不可选最优值比较：** `00_plan.md` 设 R1→定位→R2→R3，但报告目前只有两次失败的准入复核，并非 R1/R2 压测。后续需固定硬件档位、对象存储与网络、配额、版本、负载混合、数据规模、测量与排空窗口、停止条件；更换 fixture/种子时用等价数据集与重复运行评估方差，记录偏差。首次失败原样保留，修复后用新轮次重跑相同矩阵和独立 oracle，再做盲种子/对抗复核；没有可归因变更或基线就不报提升百分比。
