## 范围及原始数据

- 事前固定参数见 `09_plan.md`。当前机器、专属回环 RustFS 容器上，Rust debug 测试二进制执行原生 SQL；唯一 namespace/DB、一个全新保留桶；16 次串行单行事务、64 次串行按 ID 点读，测试用例耗时 **0.69 s**。无并发、无网关、无生产镜像或专属压测机。客户端 S3 配置 `retries=2`；SQL 层无自动重试，单次耗时包含潜在 S3 重试，并非服务端耗时。
- 原始证据：`trial-ground/private/local-microbench/run-b60b3246a14b9c8a940254bd/intent.json`、同目录 `test.log`、`local-s3-sql-bWAkk3.jsonl`、`adjudicated.json`、`read-only-buckets.jsonl`、`read-only-objects.jsonl`、`post-run-resource.json`。私有文件 0600、运行目录 0700；保留 active/cold 两个本地 cache、桶和对象；无自动清理。本轮证据不包含源代码快照、构建二进制哈希、独立审计签名，因此不能当冻结发行版本。
- 下表单位 **ms**，从每条操作单调时钟纳秒计数除以 1,000,000，独立按 nearest-rank 排序重算；不使用 `0.69 s` 用例总时长或 RustFS 容器 CPU 作为 SQL 时延。

## 正确性及失败

- 用例返回 16/16 笔写和 64/64 次查询预期值；丢弃数据库对象后使用**新的空缓存**打开同一远端 namespace，逐行读回 ID=amount=1–16、count=16、sum=136，`PRAGMA integrity_check` 返回 `ok`。原始 JSONL 共 87 行（2 setup/open + 16 写 + 64 读 + 5 冷检查），每行包含目标桶、重试配置、operation/index、期望和观测值、correct、latency_ns；所有行的预期来自事前固定公式，而非从读回结果反向定义。冷路径是进程内重新打开，不是容器重启/节点故障恢复验证。
- 前次只读清单含 10 桶，本次只读 `mc ls` 得 11 桶，集合差恰好是新桶且旧桶无消失；本桶事后只读对象清单包含 **23** 个成功列出的文件。只证明核验时条目可列出，不证明逐对象字节内容或跨时间持久性。核验前后重查容器身份、回环端口、数据卷、凭据匹配和 512 MiB/0.5 CPU 配额；不能据此证明测量期间持续身份未变。
- 测完后**单点** `docker stats`：RustFS CPU 0.12%、内存 248 MiB / 512 MiB、PIDs 19；不是运行峰值或执行端 Rust 资源开销。用例失败未见 SQL 正确性错误；**已见包装器日志格式假设错误，首次 exit=1**，已修但不追认首次包装器 PASS。首次报告和原始日志保留，可另做独立复核。
