# 验证报告 01：日志缓冲与 Authority 响应解析

## 总体评估

**PARTIAL，可开展第 2 轮。** 未发现推翻本轮机制结论或需要阻断后续实验的数据错误。固定 1 MiB 分配确实出现在所测实际 Go 方法中；严格单解析在独立 Rust 模型中减少分配与解析时间。证据不足以确认当前公开 API 的收益或瓶颈排序，报告对此保持了限制。

本验证只读取源码和原始记录，并独立核算统计；没有重跑基准、构建或修改业务代码。审查对象为冻结 `c8990c406588a23a203a46033cf10103681d188c`，不是持续变化的共享工作区。

## 逐维度评估

### 数据完整性：PASS

- 完整读取两份 Go 原始日志、Rust 原始日志、harness、生成/运行/统计脚本、Cargo manifest/lock、冻结结构与校验代码，以及计划、版本身份和环境记录。Go 小批 8 组、容量边界 4 组、Rust 6 组，每组均有 6 个记录，共 108 个计时记录；Rust 另有 25 个契约记录，全部 `equal`。
- 独立只读计算所得各组中位数、均值、样本标准差，以及 Go 最小/最大值，与 `01-summary.json` 完全一致。报告三张数值表的数值和四舍五入一致。例：Go 单条实际路径 frozen 的两个中间值为 4,203,593 与 4,655,678 ns，得到 4,429,635.5 ns；Rust 1 MiB single 为 93,865 与 93,880 ns，得到 93,872.5 ns。没有发现择取有利轮次。
- 核对环境记录列出的四个业务源码 SHA-256，均与 lab 文件相符；进一步与 `git show c8990c4:<path>` 字节对比也全部相同。归档 Go/Rust harness 与现存 lab 文件相同。因此身份可以通过源码核实，尽管环境记录中的 `git status` 实际失败。
- 分配字节和调用数足以支撑局部机制结论；没有采集峰值内存、CPU profile、队列分布或请求 p99，报告没有把它们写成已测指标。Rust 六轮来自同一进程，不能视作六次独立进程重复或生产分位数样本。

### 方法正确性：PARTIAL

**Go 实际路径与公平性成立。** `01-go-bench_test.go:69–81` 通过真实 `openOperationJournal` 打开 `*os.File`，frozen 直接调用冻结方法；exact 与冻结方法的业务差异仅为长度求和和缓冲容量。两臂均做路径身份检查、相同 payload 的 `WriteAt`、一次 `file.Sync()`、相同 witness 构造与写入。核对冻结 `operation_journal.go:597–599` 后确认 witness 写入不含第二次 Sync，位于该屏障之后。没有隐藏 mock 或删除持久化成本。

本机 Go 1.23.4 的 `os.File.Sync` 调用 `internal/poll.FD.Fsync`；Darwin 实现在 `fd_fsync_darwin.go:16–30` 使用 `F_FULLFSYNC`，在 ENOTSUP 时回退 `fsync`。因此这是实际文件屏障调用。没有 syscall trace，不能从源码确定当时是否走回退；也没有掉电试验，最终文件字节正确不能代替持久化恢复证明。

输入按实际 JSON/hash 形态构造，输出完整文件与 witness、记录顺序逐字节比较。单条与 32 条是每批调用口径；32 条小记录仅 7,511 B，报告明确没有将其冒充字节满载。补充的 1,047,959 B 场景提供了有意义反例：两种容量均落到 1 MiB 分配级，没有小批节省。合成超长 remove 标识只验证容量边界。

**Rust 对照的局部有效性成立，但依赖没有完全冻结到业务版本。** `RpcResponse` 字段和 `deny_unknown_fields` 与冻结源码相同；两臂共用校验，single 用 `deserialize_with` 要求 result 存在而允许显式 null。`black_box` 保留结果，返回值释放计入时间。计时和分配计数分开，allocator 两臂相同，报告已披露计数关闭仍有开关读取。

具体缺口：冻结 `prototypes/v1/Cargo.lock` 的 **serde_json 为 1.0.151**，而 harness lock 和构建日志为 **1.0.154**；serde 均为 1.0.229。业务 manifest 启用 serde_json `raw_value`，独立 manifest 未启用。两臂内部依赖一致，足以比较本 harness；其数值和契约案例不能直接标为冻结业务依赖下的原样结果。报告应补写这一版本/feature 差异。无需为了继续第 2 轮重跑。

**缓存与误差已限制外推，仍应明确热态条件。** Go 反复覆盖同一 offset、相同数据，排除了增长日志和 compaction；真实屏障并不会使它自动代表连续追加负载。Rust 同一输入反复解析，先热身 50 次，是输入与 allocator 的热态微测，没有冷缓存或实际体量分布。交替臂顺序减轻先后偏差，但不消除共享机负载、同进程 allocator 状态、温度和缓存的影响。Go 单条实际路径 3.12–6.38 ms 等较大波动与所报告 SD 一致。

### 结论合理性：PASS

- 真实 Go 小批 B/op 与隔离模型吻合，足以否定“编译器消除了固定大缓冲”的反例。不能把 buffer 模型的时间倍数用作持久化或请求收益；报告没有这样做。
- 单条实际路径 exact 中位数更慢；近容量上限没有分配优势。它们约束了“这必然是当前主要延迟瓶颈”的推断。另一方面，32 条小记录的 exact 在六个同轮对照中都更快，这是局部有利信号；范围重叠本身不构成无效应证明。报告使用“不能确认稳定时间收益”，而不是宣称“没有收益”，仍属合理保守结论。
- Rust 三个体量的时间和分配差支持双物化的局部成本；约 0.408/0.513 µs 和 101.08 µs 的绝对差可以复算。没有真实 HTTP、网络等待、body 读取、后续 base64 解码或 Authority 工作，无法推出主要瓶颈、当前 p99 或百分比收益。
- 25 个定向契约案例确认的是 harness 的接受/拒绝、返回值和 Precondition/KnownRejection 分类。nested duplicate result 的完整 `Outcome` 相等断言保留了相同解析结果，顶层重复 result 的两种 null 顺序均检查。它没有覆盖全部 JSON、所有版本依赖、错误文本/优先级或观察器副作用；报告没有把这组案例表述为形式证明。

### 报告质量：PARTIAL

报告结构、单位、分配统计语义、失败反例、原始证据链接与实际路径排除项清楚，事实与外推限制基本分开。有三处应补充审计说明：

1. Rust 依赖/feature 差异尚未披露，见方法部分。
2. 小批 Go 日志的 `verified` 行位于 harness 第 78 行，归档最终 harness 为第 82 行；容量边界日志为第 82 行。这与后来增加满载场景的少量源码行相符，但最终归档没有保留小批计时时的独立源码版本及 hash。数字没有因此出现矛盾；应说明该编辑顺序，最好归档原版本或可审查 diff，勿将最终文件当成两次运行均完全相同的字节身份。
3. 环境声称本地 APFS，但 `df -T` 记录为空，没有文件系统类型的成功输出。只能确认本地临时路径和真实文件 API；若保留 APFS 细节应另补只读系统证据，或将其改为环境声明。
