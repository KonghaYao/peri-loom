# 对抗验证报告：读写性能诊断与反证实验

## 总结

我尝试推翻综合结论，最强攻击是：低层成本存在不代表它解释当前缓慢；去重和空 WAL 对照不代表完整请求收益或并发正确性；找到普遍命题的反例也不等于推翻原报告已经限定的模型。原诊断若被理解为当前主要瓶颈或收益排序，确实应降低置信度；但其稀疏新内容 32× 模型没有被推翻，反而得到复现。当前 `conclusion.md` 已将这些区别、版本差异和实验缺口纳入边界，因此没有找到能推翻其保留机制结论的致命缺陷。最终裁定针对当前收窄后的综合结论，而不是给原性能排序或后续业务补丁签字。

本次只读审查了两轮报告、两份独立验证、源码攻击、identity/version 记录、修订后的原报告，以及必要的 harness、原始日志、统计数据和 `git show c8990c4` 冻结源码。独立提取了实验 02 的 21 条 RW02 记录，重算 H5 双向段 body 和 Go 配对方向；没有构建、重跑实验、改业务代码或派发子 agent。

## 攻击结果

### 攻击 1：整项调查仍可能没有找到用户当前缓慢的原因

- **目标结论**：固定分配、双解析、File 锁、候选复制或 checkpoint 发布是当前主要瓶颈，或足以给出收益排序。
- **攻击角度**：替代解释、因果外推、遗漏。
- **攻击内容**：实验未采当前 API 的分段延迟、排队、吞吐、p99 或真实工作量分布。全服务可能受 operation/audit 的持久化等待、准入、网络、缓存 miss、维护排他或冷恢复支配。旧 14.357 ms 样本中的约 59% 不能排除这些因素在新版本中的不同占比。H3/H4/H5 的确定性事件和字节计数提供存在性证据，没有提供发生频率或总耗时占比；即使这些机制全部存在，当前业务延迟也可能几乎不受它们影响。没有数据可给这一影响下正的收益下界。
- **严重程度**：严重；对当前主要瓶颈和收益排序构成实质削弱，对存在性结论无致命影响。
- **建议处理**：撤回当前主要瓶颈与实测收益排序，保留候选成本。当前综合结论已这样处理；原报告的低改动成本优先思路和“收益未测”限制也应保留。若未来恢复性能归因，需冻结实际版本、配额、后端、历史规模和缓存，采请求分段与同条件 API A/B，并显示目标成本的实际覆盖率和占比。

### 攻击 2：部分“成功反证”瞄准了比原报告更强的命题

- **目标结论**：去重对照推翻了原 checkpoint 32× 诊断；单条日志慢于对照证明缓冲优化无收益。
- **攻击角度**：逻辑链、数据选择。
- **攻击内容**：原报告已限定 4 KiB 稀疏页、128 KiB 段的新内容模型，并多次声明收益未测。实验的新且不同内容臂仍是 32×，所以该模型被复现；相同内容、已存在内容和满段覆盖只反驳不加条件的推广。日志实验也不是一面倒的反证：单条中位时间 4.43→4.92 ms，但 32 条小记录六个同轮对照全部更快，独立重算的差值均为负，约 -0.168 到 -2.700 ms。共享机噪声和六组数据不足以用单条反向中位数证明无效或有害，也不能仅凭范围重叠否定批次收益。
- **严重程度**：中等；会夸大调查推翻原判断的程度。
- **建议处理**：明确“8 dirty 必有 8 PUT”“所有 checkpoint 都 32×”是被排除的过宽外推，不归为原报告已经提出的普遍断言；写“未证明当前稳定收益”，保留六轮有利信号。主线程已将这一攻击落实到综合结论。未来可用实际批次分布、随机/交替顺序的独立重复和请求 A/B 区分噪声与真实效果，无需为本轮扩大测试。

### 攻击 3：去重减少上行 PUT，没有减少这个模型中的双向段 body 总量

- **目标结论**：H5 的 32→4→0 表明去重显著降低了整体传输放大或 checkpoint 成本。
- **攻击角度**：指标遗漏、替代解释。
- **攻击内容**：从 `02-frozen-raw.log` 独立求和，三个稀疏臂的段 GET 返回 body 加 PUT body 均为 **1,048,576 B**，相对 32,768 B 写入调用输入都为 **32×**。相同新内容是 917,504 B GET + 131,072 B PUT，已有内容是 1,048,576 B GET + 0 PUT。每臂也仍有 8 次段 GET。该反例证明了新 PUT 数不等于脏段数，却没有证明总 body、往返、CPU 或耗时下降；如果下行 GET 是主成本，减少 PUT 甚至可能缺乏用户可见价值。已有内容臂无实际业务变化，32× 的这个求和同样只是“每写入调用字节”的比值。
- **严重程度**：中等；对只定义为 PUT body 的数值无影响，对整体成本改善的解读构成削弱。
- **建议处理**：在综合结论显式列出该双向求和，继续区分上行、下行、元数据、wire 和时间。主线程已将这条算术补入综合结论与实验 02；该攻击的越界风险已被处理。若要证明实际成本下降，应在真实后端分别测 GET/PUT body、请求层级、延迟及计费相关量；仅凭这组数据不能做此声称。

### 攻击 4：File 的推进不是 SQL 正确性，EOF 尤其不能承担此证明

- **目标结论**：pread 补丁已使同库 SQL 并发，或已经证明读写/checkpoint 的完整并发协议正确。
- **攻击角度**：外部效度、遗漏。
- **攻击内容**：H3 使用合成非 SQLite 主库和空 WAL，read helper 只检查调用未报错与 Completion.finished，没有核对返回长度或内容；空 WAL 的成功实际是 EOF。started 在调用前发送，1 秒负观察并不能独自证明线程已到 mutex。真实 Shared.try_lock、冻结源码 guard 范围、独立 IO/直接 storage 正控制和最小补丁足以定位这个夹具的阻塞机制，但无法跨越到有效页/WAL、快照、revision 重试、truncate/reset、撤权或失败发布的一致性。维护夹具只是持有真实 operations 写 guard，没有执行真实慢 checkpoint 与前台 SQL；native pager 命中还可能绕过 File。
- **严重程度**：严重；若用于并发正确性或完整 SQL 收益验收会失效。
- **建议处理**：保留“该 File 路径的调度阻塞得到定位”，拒绝用它验收完整 1198b18 或当前 WIP 的正确性。综合结论已明确这一点。未来若对补丁作正确性声称，需有效 SQLite/WAL 输入、长度/内容断言、真实 session 交错和 read/write/truncate/revision/失败发布等边界；若只讨论本次锁机制，不需要追加这些实验。

### 攻击 5：候选复制计数不能说明每次提交成本，也没有验证历史 index 曲线

- **目标结论**：每次 SQL/提交都复制整个 WAL；copied_bytes 是提交总复制或内存峰值；本轮证明了 receipts/index 历史增长的时间曲线。
- **攻击角度**：分支选择、测量口径、遗漏。
- **攻击内容**：冻结源码 `validate_index_append` 确实 clone `Vec<u8>` 后调用 `observed_copy(image.len())`；34,336 / 548,896 / 4,390,944 B 是这条明确 clone 的语义计数，非 allocator 或系统 memcpy 采样。fixture 显式调用真实校验函数，未运行 Worker→Authority session，也没测该分支命中率。冷验证/失配/CAS retry 可全量重放；receipt 命中、空 pending sync 和成功 compact 又是不同路径，不能将其中任何一种的频率假定为 100%。三个规模的 entries/receipts 均为 2，index 仅 584/586/586 B，完全没有隔离或测出累计回执增长的时间曲线。无新增 index 被拒绝属于非法调用，不是合法提交不复制的反例。
- **严重程度**：中等；对冻结指定分支的深复制机制无影响，对频率、峰值、历史曲线和当前主因有实质限制。
- **建议处理**：继续只给该分支存在性高置信度；历史规模风险保留为源码支持。综合结论已处理。未来需同时记录活跃镜像、index/receipts 规模、Authority 分支命中、重试、compact 周期和总提交耗时，分别控制 image 与 index 规模，才能测复制与索引的独立贡献。

### 攻击 6：parser 精确收益和契约结论无法投射到新提交

- **目标结论**：0.408/0.513/101 µs 是冻结生产 parser 的精确节省；25 个契约案例验证了 df93605 的完整实现。
- **攻击角度**：方法、版本、外部效度。
- **攻击内容**：Rust harness 使用 serde_json 1.0.154，冻结业务是 1.0.151 且启用 raw_value；两臂共同约简了错误对象、观察器和错误优先顺序，后续业务提交还使用不同三态实现。六轮为同进程、同输入热态解析，1 MiB 内容是单个无转义 ASCII 字符串，没有真实响应体量分布、网络、body 读取、后续类型转换或 base64 解码。这个模型的局部差异很清楚，但不能给实际请求精确节省；约半微秒的小响应节省也不代表在高调用量下 CPU 总贡献为零。
- **严重程度**：中等；生产精确数值和新实现契约未建立。
- **建议处理**：保留“该独立模型内的成本”以及实际生产贡献未知，避免把“小响应绝对节省小”写成“优化不值得”。当前结论已按依赖和提交限制。未来若声称 df93605 收益或等价性，直接对冻结业务依赖与真实实现做契约/响应体量对照，并保持错误分类和必要副作用。

### 攻击 7：不断推进的 HEAD/WIP 和同名计数器可能制造假的前后改善

- **目标结论**：e8beae4、c899、pread 局部补丁、1198b18 和当前 WIP 可视为同一对象，或 recovery 新旧 copied_bytes 可直接比较。
- **攻击角度**：时间外部效度、混淆变量。
- **攻击内容**：identity、version-followup 明确实验冻结期间业务继续变化。memo 已在 c899 中；缓冲、parser 与主库 pread 后续分别合入；Authority/recovery WIP 又尝试消费旧状态原地延长并改变计数含义。因此旧 clone 计数不能证明最新工作区仍有该 clone，也不能将新 copied_bytes 降低直接当作系统总复制减少。c899+单文件 pread 配对同样没有验证完整 1198b18 或其他 IO WIP。memo 断言证明稳定文档复用 decode，却没给 memo 后 commands/root 规模时间曲线。
- **严重程度**：严重；跨版本因果比较会失效。
- **建议处理**：分别报告每个证据的 commit/patch/工作区身份和指标定义；后续收益必须重新冻结且按同一口径比较。当前结论与原报告订正已完成这一区分，不把后续提交重新列为未实施建议，也不接受其提交说明替代独立验证。

### 攻击 8：证据归档支持审阅，但尚不支持干净环境的一条命令复现

- **目标结论**：现有脚本已保证独立干净重建的完整运行身份。
- **攻击角度**：可复现性、方法。
- **攻击内容**：Go 小批计时当时的独立源码/二进制 hash 未保留，最终 harness 后加过容量边界输入，虽修改说明和现有数据无矛盾，仍不能逆向补齐构建身份。`02-run.sh` 依赖临时绝对 lab，只恢复 files.rs；prepare 遇既有模块标记会保留代码，不对全树做拒绝式身份检查。归档足够人工核查本次机制，但脚本在被改过的 lab 上可能运行另一套源码。文件系统类型与 Sync 的具体系统调用回退路径也没有运行时证据，不能把最终文件字节正确当作掉电证明。
- **严重程度**：中等；降低独立运行复现保证，不构成已观测数据造假或机制失效证据。
- **建议处理**：当前结论已明示实验身份缺口和保留 lab 的重放边界。未来如果声称跨机器复现，提供冻结快照创建、submodule/toolchain/依赖前置条件、完整 hash 检查，并保留运行时源码与二进制身份；本轮无需改写 raw 或重新构建来掩盖缺口。

## 综合评估

| 攻击 | 严重程度 | 结论是否仍成立 |
|------|---------|--------------|
| 机制无法解释当前缓慢或建立收益排序 | 严重 | 原排序被削弱；当前已撤回，成立 |
| 反例攻击了比原报告更强的命题 | 中等 | 原稀疏 32× 模型仍成立；当前已明确 |
| 去重没有降低本模型双向段 body | 中等 | PUT 口径成立；整体成本改善未建立 |
| EOF/File 推进不证明 SQL 或并发正确性 | 严重 | 仅指定 File 调度机制成立 |
| clone 分支与 index 曲线覆盖不足 | 中等 | 指定 clone 机制成立；提交分布与历史时间未知 |
| parser 依赖与实现不等同生产 | 中等 | 独立模型内成立；生产收益/新契约未知 |
| HEAD/WIP 与指标口径混淆 | 严重 | 按冻结版本解释后成立 |
| 重放入口与构建身份存在缺口 | 中等 | 本次人工机制审查成立；完整重建保证不足 |

上述“严重”描述的是把实验扩展为性能归因、跨版本比较或正确性验收的后果；不是已在当前综合结论中发现这些越界。没有发现挑选有利轮次或删除不利结果的证据；最有利和最不利的日志结果均被保留。H5 的双向 body 求和属于本次新增的定量边界，不改变原始数据。
