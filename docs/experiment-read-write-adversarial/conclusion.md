# 读写性能猜想的对抗复核

日期：2026-10-17。两轮实验、逐轮独立验证与最终独立对抗审查已完成。

[最终对抗审查](adversarial_review.md) 裁定 **CONCLUSION_STANDS**，仅针对本文收窄后的机制结论；原诊断若被理解为当前主要瓶颈或实测收益排序，则为 **WEAKENED**。这不代表当前缓慢已获解释或解决。

## 研究问题与证据范围

检查原报告提出的成本是否真实存在、有哪些反例，以及它们能否解释用户观察到的当前读写缓慢。目标是主动推翻外推，不要求证明原判断正确。

原报告基线 e8beae4；本轮实验冻结 c8990c4，Turso 固定版本、初始工作区和隔离 lab 见 [identity.json](identity.json)。实验串行，只使用临时文件和独立对象存储，不接触运行服务。业务工作区在实验期间继续推进，版本必须分开解释。

## 已确认的修正

1. **撤回主要瓶颈与收益排序。** 源码中的成本不等于当前请求的主要耗时；本轮没有当前公开 API 的分段 A/B、吞吐或 p99 证据。原报告已多次说明收益未测，且顺序部分按改动成本安排；这些谨慎表述仍成立。撤回的是把它概括成“当前主要瓶颈”或实测收益排序的解释，而不是宣称局部改动没有收益。
2. **固定分配真实，但持久化路径收益有反例。** 实验 01 单条批次 B/op 从约 1,050,068 降至 1,352；含真实 Sync 的中位时间却为旧 4.43 ms、对照 4.92 ms。32 条小记录六轮均有利，中位为 4.97→3.78 ms；近满载两臂都分配约 1 MiB、中位约 4.5 ms。保留全部结果，不能宣称“优化无效”，也不能从 buffer 模型倍数推算请求收益。
3. **小 RPC 响应的解析节省很小。** 独立 release harness 中约百字节/1 KiB 响应节省约 0.408/0.513 µs，1 MiB 节省约 101 µs。该模型 serde_json 1.0.154，冻结业务为 1.0.151、feature 也不同；它只证明局部实现的成本，不是生产 parser 或 HTTP 的精确成本。25 个契约案例仅比较 harness 两臂，不验证后续单解析提交。
4. **59% 仅属于旧测量。** 两类串行持久化等待仍有结构证据，但旧 14.357 ms 样本的占比不能解释当前版本，更不能作为当前优化顺序。
5. **root 每次完整解析的说法已过期。** 792f546 已合入按完整字节摘要复用解码的 memo；命中仍有 root GET 与全字节哈希，更新/失效仍需解析。commands 内嵌和 prepare 遍历是另外的规模成本，不能以旧租约计时代表 memo 后结果。
6. **锁与 checkpoint 的结论需要收窄。** native pager 命中可能绕过 File；checkpoint/compact 还有更上层 operations 排他门。即使主库 File 放锁有效，也不能据此说所有热 SQL 曾被阻塞，或维护期间 SQL 现在可以并行。
7. **32 倍仅是特定稀疏新内容模型。** 已有内容跳过 PUT，同内容跨段可复用，native checkpoint 已保留每页最新帧、合并连续 writev；Authority 内部也已有 put_group。逻辑 dirty 数不是新物理 PUT 数，仍需分别统计 GET/PUT 字节与元数据操作。

详细数据与方法限制见 [实验 01](01_experiment_report.md)、[验证 01](01_verification.md)；分支、锁与去重的独立源码攻击见 [source-challenge.md](source-challenge.md)。

## 第二轮机制与反例

以下是冻结版本的确定性小实验，不报告生产时间收益。[独立验证 02](02_verification.md) 数据/结论 PASS，总体 PARTIAL；限制已纳入下文。[独立验证 01](01_verification.md) 亦为总体 PARTIAL、数据/结论 PASS。

### File 与维护门

慢段 GET 到达后，旧主库 File 路径的 Shared try_lock 不可得，同 IO 的空 WAL File pread（返回 0 字节）与另段 pread 在放行前不完成；直接 storage 与独立 IO 可完成。只应用主库 pread 放锁补丁后，两项同 IO 读取均在放行前完成。该对照定位了 File 阻塞机制，不证明完整 SQL 都经过 File 或新并发协议全面正确。

另一个内部测试持有真实 maintenance_operation，operations.try_read 返回 WouldBlock，而 WAL File 读取可完成。它证明上层门独立于 File 锁；没有运行真实慢 checkpoint 与前台 SQL 的交错实验，也没有验证非空 WAL 载荷或 checkpoint 并发读取的一致性。

### WAL 候选复制

真实 validate_index_state→validate_index_append，固定只新增一个 frame：

| 原 frame 数 | 原 image 字节 | 记录的候选复制字节 | 新校验扫描字节 / frames |
| ---: | ---: | ---: | ---: |
| 64 | 34,336 | 34,336 | 568 / 1 |
| 1,024 | 548,896 | 548,896 | 568 / 1 |
| 8,192 | 4,390,944 | 4,390,944 | 568 / 1 |

新增扫描没有随前缀增长，候选镜像复制仍随当前镜像增长。两条 entries/receipts 固定，index JSON 584/586/586 B；本实验**没有**测出 index 随历史回执增长的时间曲线。无新增 index 的不合法调用在复制前拒绝，不能用作合法 append 的优化路径。源码还给出 receipt 命中、冷验证和 compact 等路径反例，详见 source-challenge。

### publish 去重

每臂 8 个逻辑脏段，按 segment body 单独计数，不含元数据和传输编码：

| 输入 | 段 GET 数 / 返回字节 | 新段 PUT 数 / body 字节 | PUT body / 本轮写入字节 |
| --- | ---: | ---: | ---: |
| 每段 4 KiB，新且不同 | 8 / 0 | 8 / 1,048,576 | 32 |
| 每段 4 KiB，相同新内容 | 8 / 917,504 | 1 / 131,072 | 4 |
| 每段 4 KiB，最终内容已存在 | 8 / 1,048,576 | 0 / 0 | 0 |
| 连续完整覆盖 8 段 | 8 / 0 | 8 / 1,048,576 | 1 |

“8 个脏段必然 8 次新 PUT”和“所有 checkpoint 都 32 倍”这两种宽泛外推均被反例击穿；它们不是原报告已经作出的普遍断言。原报告明确限定的稀疏新内容 32 倍模型本身未被推翻，本轮反而复现了它。最终对抗复核补算：三种稀疏臂的段 GET 返回字节 + PUT body **均为 1,048,576 B / 32,768 B 输入 = 32 倍**，连续满段臂为 1 倍。因此这些去重反例只降低新 PUT 和上行 body，不证明本夹具最终 publish 的双向段 body 总量下降；更不等于真实部署 wire 总量。这是总量相同、方向改变的反例。已有内容臂只是重复写入、没有实际业务内容变化，0 仅是 PUT/body 与写入调用字节之比，不是实际业务写放大。零 PUT 仍可能有 1 MiB 段 GET；这些是 MemoryObjectStore 包装计数下的 RemoteStorage.publish，不是实际 native SQL checkpoint/S3 的频次分布或往返成本。

详见 [实验 02](02_experiment_report.md)、[验证 02](02_verification.md)。原样复跑的 memo 测试亦 PASS：稳定文档预热后 64 次校验不再 decode，新文档 64 次只 decode 一次，畸形新文档拒绝；这是断言通过，不是新的时间曲线。

## 当前版本与局限

观察到后续 94534c5、df93605、1198b18 已分别合入缓冲、单解析和主库 pread 锁调整，不能再次列为待实现项。它们的提交说明或测试结果不等于本调查独立完成的性能/正确性验证；当前未提交的 Authority/recovery 改动同样未纳入冻结实验：只读观察到它正在将候选 clone 改为消费旧状态并原地延长，还改变了 copied_bytes 的统计含义；本报告不验证该修改的正确性或收益，尤其不能跨版本直接对比同名计数器。

Go 持久化测量只覆盖 writeBatchAt，重复覆盖同一 offset，不含排队、持续追加、压缩与公开 API；共享主机有噪声。早期小批 harness 未单独归档原二进制/源码 hash；文件系统类型未核实。Rust 同输入热态微测不包括网络、base64 后续解码和 Authority 工作。第二轮确定性机制不能用 debug 时间推断生产性能，也不构成完整并发正确性或恢复证明。File 对照检查 completion/成功状态，没有核对非空读取返回字节；H3 空 WAL 不证明内容一致性。复现脚本依赖 identity.json 指向的仍存在临时 lab；归档提供了源码/patch/hash，但尚无已验证的从干净目录自动重建入口。

## 后续建议

先在冻结 release 构建、实际后端与配额内采一轮请求分段数据：operation/audit 排队与 Sync、RPC 响应大小、Authority 验证分支、WAL image/index/receipts 规模、维护 operations 等待和段 GET/PUT 字节。按实际等待/CPU占比决定优化目标。

若长历史写入暴露 copy/index 成本，再评估候选镜像共享和回执分页；若维护等待占优，优先减少 checkpoint 的串行往返与工作量，再单独设计可并发维护协议。只有当前 API 同条件 A/B 才能确认用户可见改善。原诊断已订正：[读写性能排查与建议](../performance-review/2026-10-17-read-write-diagnosis.md)。

## 最终审查处理

已采纳两项具体攻击：明确原报告限定的稀疏新内容 32× 模型未被推翻，并保留 32 条小记录六轮有利的配对信号；补算三稀疏臂双向段 body 同为 1 MiB，拒绝由 PUT 减少推断总传输下降。其余关于 API 归因、EOF/File、Authority 分支、依赖版本、WIP 计数器与复现入口的攻击均保持为已知边界，没有将其写成性能或正确性验收。独立审查未发现需要补实验的致命问题。
