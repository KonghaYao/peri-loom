# E01 独立合成规模提案（待用户确认）

状态：2026-10-16。用户已选择"使用独立合成规模"。以下 N、payload、各档逻辑字节、
工作集、并发/到达率与预算**均为建议值，未经批准，也未运行**。永远标记
`SYNTHETIC_REFERENCE`；2/4/8× 一律解释为*合成基准倍数*，不宣称"真实 Peri 2×覆盖"。

## 0. 口径与不可测量的部分

- `logical_bytes = N × (24 + UTF-8 payload 字节)`：三项有符号 int64 加正文长度，
  不含 JSON 编码、数据库页、索引与压缩。真实与合成必须同口径。
- 黑盒约束：公开 API 只返回行与时间，**不发布**内部扫描量、页访问或缓存驻留。
  因此 E01 不报告"引擎工作集"或"冷缓存证明"，只报告可从响应与场景推出的量：
  返回字节工作集、被查询键空间覆盖、参数化深度下界。这些是**场景侧下界**，
  不是引擎内部测量；引擎侧扫描/缓存一律 `NOT MEASURED`。
- 深分页的实际代价无法从公开响应测得，只能用"ORDER BY 需走过的索引条目数下界"
  （= offset 深度）表达；keyset 的对应下界是同一游标位置的深度。
- 导入速率尚未测量：正式阶梯前必须先做一次小规模导入标定（见第 5 节）。

## 1. 推荐方案 A（主推，默认建议）

合成 1× 基准：

| 项 | 值 |
| --- | --- |
| `rows`（N_ref） | 4,000,000 |
| payload 桶 | [64, 128, 256] 等权，均值 149.33 B |
| 行逻辑字节均值 | 173.33 B |
| `logical_bytes` | ≈ 693 MB |
| 分组 | 32 组，倾斜权重（首组约 25%，尾部约 0.2%） |
| `time_span` | 7,776,000,000（按毫秒解释，90 天；组内时间并列稀疏但存在） |
| `hot_fraction_ppm` / `hot_access_ppm` | 20000（2% 热键区间）/ 600000（60% 访问落热区） |
| `per_family` | 200 次/族/测量窗口 |
| `page_size` | 50 行 |
| `deep_ppm` | 130000（13% 组内深度，按组大小等比放大） |

数据阶梯（2/4/8×，先单轴放大）：

| 档 | 行数 | 逻辑字节 | 最大组行数 | 最深 offset 下界 | 物理占用估计 |
| --- | --- | --- | --- | --- | --- |
| 2× | 8,000,000 | ≈ 1.39 GB | ≈ 3.0 M | ≈ 390 K | 2.1–3.1 GB |
| 4× | 16,000,000 | ≈ 2.77 GB | ≈ 6.0 M | ≈ 780 K | 4.2–6.1 GB |
| 8× | 32,000,000 | ≈ 5.55 GB | ≈ 12.0 M | ≈ 1.56 M | 8.3–12.2 GB |

（物理占用估算 = 逻辑 × 1.5–2.2，含表、复合索引、页开销与 WAL 余量；未实测。）

两级独立子阶梯：

- **A1 深度阶梯**：固定低到达率 4 ops/s、并发 1，depth 按 2/4/8× 递增。
  回答"深分页单次代价随深度如何退化"。
- **A2 到达率/并发阶梯**：只用点查、`index_list` 与一页固定 keyset（浅页），
  到达率 200/400/800 ops/s（R_ref = 100 ops/s 的 2/4/8×），并发 16/32/64
  （C_ref = 8 的 2/4/8×）。回答吞吐拐点与排队，不与深度轴混合。

工作集覆盖要求（两目标都必须达到）：

- 返回字节工作集：每族每窗口返回字节 ≥ 2× 合成基准（按被访问键空间扩大，禁止只循环热键）。
- 键空间覆盖：每族每窗口 distinct 查询键（点查 id；列表的 group+时间窗；分页锚点）
  ≥ 2× 合成基准，且键取自全键空间而非固定热集。
- 缓存压力：按"被触及索引键数 × 16 B"给出场景侧下界，需 ≥ 2× 冻结页缓存预算
  （建议 native 侧显式设 128 MiB；平台公开 API 不能设置缓存预算，
  故平台侧该条件记为不可控、不可比，不冒充已制造缓存压力）。

预算（推荐 A）：目标进程独占 8 CPU 核、内存上限 8 GiB；
发生器 4 核、内存 4 GiB（发生器饱和则该轮无效）；
磁盘空余 ≥ 60 GiB（含 8× 数据集、WAL、SQL 文本与日志，低于 60 GiB 停止）；
单档（导入 + 预热 + 3 轮 × 10 min 测量）≤ 45 min，整条阶梯单目标 ≤ 6 h；
外部服务费用 0（纯本地）。

方案 B 足以暴露固定开销与深分页退化趋势，但**不足以**代表容量上限；
它能先产出可比较的 2/4/8× 曲线与缺口清单，再决定是否升级到方案 A。

## 4. 待实现/待补能力（正式运行前置）

1. **流式生成**：当前生成器只支持 smoke（≤2048 行，全量驻留内存）；
   正式规模需流式逐行生成与分批 SQL 文本输出，并记录数据集 SHA-256。
2. **正式导入**：单事务 + 字面量多行 VALUES 仅适合 smoke；正式需分批事务、
   批量上界与失败回滚证据；平台侧还需核对公开 `sql_limit`/`sql_budget_exceeded` 边界。
3. **调度器与资源采集**：开环到达、并发阶梯、目标进程 CPU/内存/磁盘采集、
   发生器自身饱和度检测；黑盒路径不得使用平台内部遥测来推断扫描量或缓存。
4. **导入速率标定**：先跑 1 M 行（方案 B 的 2× 档）标定行/s 与字节/s，
   据此确认 8× 档是否落在预算内；未标定前不批准 8× 档。
5. 平台侧会话策略与真实端点能力（DDL/事务/行数上界）需在用户提供的隔离端点上验证。
