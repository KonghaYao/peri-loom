# 持续性能迭代

把一次性能优化从想法推进到「可复现的收益 → 合入 → 发版」，每一轮都留下可审计的
git 记录与实测数字。适用于用户说「进入实验状态」「一轮一轮来」「看有没有提升」
「有用的改动才合入 main」这类目标。

## 理念（先读这一节）

1. **证据优先于叙事**。结论只来自受控测量：同一数据、同一容器、同一配额，配对运行。
   没有测量就没有收益，没有复跑就没有 PASS。
2. **一轮一记录**。每轮以 git 为界：分支、提交、验收数字、判决、文档提交。无提升即
   默认 reset 丢弃分支（不合入、不叠加），失败原因与关键证据留档（附 commit sha），不删除失败样本、不跨协议混算。
3. **只合入证实的收益**。收益必须超过噪声门槛，且机制上能解释；不能解释的差异先归因，
   归因不了就如实记「不可确认」，不写成改进。
4. **判定变量是端到端指标**。锁等待、fsync 次数、分配量、重连次数是解释变量，不是收益本身；
   减少工作量但吞吐/延迟不变的结果按「中性，不合入」处理（R15/R19/R22/R29/R33）。
5. **瓶颈会迁移**。每轮结束重新剖面；上一轮的中性结论只在当时的限速器下成立，换限速器后必须复测
   （R19 的 256→1024 当时中性，R32 在屏障合并之后同一改动 +19.39%）。
6. **判据先冻结**。测量前写死主指标、门槛、样本数、例外条件；看见数据后不得改判据、
   不得把绝对目标降级为「报告项」、不得换更慢的基线窗口（R5 的 verifier FAIL 被改判）。
7. **如实报告**。中位数、轮次、样本数、失败项、噪声范围、未测量项都要写出来。
   禁止把投影当实测、把计划当结果、把一次运行当结论。
8. **失败是资产**。环境故障、回归、撤销轮次都留档；它们决定了下一轮的方向与边界。
9. **安全边界先于速度**。不为了跑分放宽配额、跳过审计/持久化、绕过 fail-closed 门禁。
   性能实验的合法上限是「不改变耐久时点与安全语义」；审计/日志写入时点属于高风险改动，
   除非用户明确授权，不得在迭代中变更。
10. **删除优于兼容**（仅限内部实现）。重构直接删旧路径，不留 deprecated shim；
    对外协议兼容义务单独评估。
11. **先广度后深度、先完成再完整**。先跑通用户可观察的主指标，再按风险补回归与失败路径；
    不为低概率边界过早投入。

## 角色与授权

协调者（主 agent）负责目标、拆分、决策与最终汇报；默认把可并行的独立工作交给 subagent。
本仓库的实践是用 `general-purpose` agent 承担反思、执行、验证三类角色。

- **反思（reflect）**：只读分析现状与瓶颈，产出 2–5 个实验方向，每个方向给出机制假设、
  预期收益、风险、验收场景与回滚方式。不写代码。
- **执行（execute）**：按已选方向实现并自测，产出分支 + commit + 变更清单 + 局部验证结果；
  遇到设计分歧升级给协调者，不自行扩大范围。
- **验证（verify）**：独立测量与复核，产出原始数据、统计口径、判决与未闭合项。
  验证者不得复用执行者的结论，只信原始输出。
- **规划（plan）**：默认不用。只有用户明确要求，或涉及耐久/恢复语义、跨模块结构性改动且
  reflect 无法收敛时，才允许一次只读 `plan`（产出设计与风险，不写代码）；派发后必须检查
  产出，派了 agent 不等于有结论（R4 的 plan 任务在 6 条消息后没有可用设计）。

授权边界：批准 `Agent` 等于把继承工具的执行权交给 subagent；subagent 内部不再逐工具审批。
交接必须自包含：目标、范围、约束、验收标准、已有证据、需要回传的证据格式。

- 验证者的 FAIL 不得由协调者单方面推翻。若判据本身有问题，只能修改下一轮的判据，
  不能追溯为当前轮放行（R5：verifier 已判 FAIL，协调者把预声明的「<20ms 绝对目标」改称
  「报告项」后合入）。
- 耐久语义变更的授权要引用用户原文。「你自己决定」是授权范围，但记录里必须写原文与解释；
  只有协调者批准不算用户授权（R4 的耐久时点变更记录写作「协调者批准」，没有用户原文）。

## 单轮流程

1. **进入实验状态**。冻结基线：当前 `main` 的二进制哈希、容器/卷/端口、配额、数据集与
   fixture 计数；任何一项变化都要在记录中写明。
2. **一轮 = 一条 git 记录**。分支、commit、验收数字与判决同属一条记录，轮次之间不混算。
3. **反思（subagent）**。由 `general-purpose` 只读分析代码与既往记录，得出 2–5 个实验方向；
   协调者只做选择与汇总，标准：机制清晰、改动局部、可回滚、预期收益大于噪声、不触碰安全边界。
4. **上限探针（写生产代码前）**。用最小探针测目标动作的理论上限：R7 实测 `describe` 均值
   0.391ms/次 = 单查询 2.4%，因此 609 行的方案不值得写；R30 先用「跳过 settle」的不安全
   探针测到 +16.4%，再实现安全版。上限低于门槛就不实现；探针不得合入。
5. **执行（subagent）**。在新分支上按选定方向实现并自测（单元/定向测试、格式、构建），提交
   信息用中文全角冒号（`perf(area)：…`）；设计分歧升级给协调者，不自行扩大范围。
6. **执行完成即 commit**。先把这个候选状态钉死在 git 上，再开始测量；commit 是验收的输入，
   不是收益的结论。
7. **机制核验（Gate 0，先于 A/B）**。确认新路径真的被执行：新路径命中计数 >0、关键计数器
   相对基线变化方向与机制一致；能关掉就做「关掉改动」的对照。机制未生效时，任何 A/B 数字
   都无效。R28 第一版把已挂好的授权快照覆盖成空对象，6 轮 A/B 仍测出 +5.4% 纯噪声。
8. **性能验收**。按下一节协议对该 commit 做受控 A/B：先主指标，再回归门，最后不变量核对；
   只认本轮候选二进制现算的数字。
9. **判决**。有提升 → 记录（`CLAUDE.md` 表格加行 + 小节，格式见下；文档提交与代码提交
   分开，`docs(perf)：…`）。无提升 → `git reset` 丢弃该实验，记录只留失败原因与关键证据，
   再从 `main` 开新分支。
10. **合入与下一轮**。只有经证实有用的改动才合入 `main`（`git merge --no-ff`）；随后在新的
    `main` 上开分支进入下一轮，不在上轮分支上叠加未合入实验。

## 性能验收协议

**机制核验（Gate 0，先于 A/B）**

- 新路径命中计数必须 >0；关键计数器（`batch_max`、`coalesced`、缓存命中率、fallback 次数）
  的变化方向必须与机制一致。没有计数器就加临时探针，探针在测量前移除。
- 能关掉新逻辑就做一次「关掉」对照：关掉后计数器应回落到基线；不能关就至少用调用点标签
  证明路径被走到。
- `git diff` 只能证明「可能影响」；要证明「实际影响」，必须看运行时证据。R28 的 6 轮空转
  证明：机制没生效时，A/B 也能测出 5% 的假收益。
- 观测器只用于归因：A/B 期间不开启会改变吞吐的观测器；观测器绝对值不写进对外汇报。
  需要开观测器时，先测它的开销，并把它和正式 A/B 分成两次运行。

**环境**

- 只测 peri-loom 自身（Go platform + Rust worker），不依赖客户端 SDK、本地 SQLite。
- 固定容器、固定卷、固定端口与配额；切换平台/worker 二进制时先干净停止（`docker stop -t 60`，
  确认 exit 0），换文件后再启动，并核对容器内 `sha256sum`。
- 不碰运行中的其他容器；不重启 Docker daemon；不 `prune`；不清除 marker/proof/ownership。
- 单场景受控运行用 `scripts/perf-reliability/issue28/run.py`（`--scenario`、`--protocol`、
  `--rounds`、`--warmup`、`--samples`、`--allow-misses`），一次只测一个场景族。
- 结果目录按「版本-场景-轮次」命名，保留 `raw.jsonl`、`summary.json`、`metrics.json`。
- 记录平台/worker 二进制 SHA256、构建命令、Go/Rust 工具链、镜像 digest、`durability_source`、
  配额、卷名、数据集来源与 fixture 计数；任何一项与默认值不同都要标出。
- 测量脚本必须进仓库（`scripts/perf-reliability/`）或随记录附上完整版本；只存在于 `/tmp`
  的 `dev.py`/harness 改动不算可复现实验。
- 证据放持久目录（`docs/performance-review/...` 或仓库内），`/tmp` 只作临时中转；
  删除卷/容器/证据前先复制并校验哈希，不可逆删除需用户确认。

**配对**

- 顺序用 A/B/B/A 或 B C C B B C C B：基线、候选交错，抵消冷启动与漂移。
- 每个场景至少两轮同向；关键指标做配对差值（同一轮次内候选/基线），而不是只比总中位数。
- 记录每轮的中位数与样本数；不把「最大/最小」当主指标。

**限速器与上限**

- 每轮先列候选限速器（fsync、锁、队列、CPU、网络、worker 串行段），用相位分解/计数器
  确认当前饱和项，只优化饱和项。R31/R32/R34/R36 的相位探针把「审计批 2.9ms 里屏障 2.18ms、
  提交 0.45ms、状态锁 0.26ms」拆开后，才找到压缩与 GC 的真实占比。
- 优化后限速器没有移动，说明改错了变量；「减少锁获取/fsync 次数」不能作为合入理由
  （R15/R19/R22/R29/R33）。
- 记录「在什么限速器下中性」，限速器变化后复测。R19 的 256→1024 在当时中性，R32 在屏障
  合并之后同一改动 +19.39%。
- 微基准只能用来排除方向，不能代替端到端：R13 的 `fdatasync` 微基准 1.42→0.84ms，
  生产路径无收益，已回退。

**配置与配额**

- 默认生产配置与容量实验配置分开记录。不得为了跑分静默放宽 `max_concurrent`、
  `max_sessions`、worker 每库上限、GC 目标或耐久模式。
- 若必须放宽以测扩展性，标记为「容量实验（非默认配置）」，结论不得外推到默认配置；
  发版前用默认配额补主场景。
- 任何未进仓库的 `dev.py`/harness 改动都不算可复现实验；把脚本提交到
  `scripts/perf-reliability/` 或随记录附上。

**门槛（默认口径）**

- 硬门：主指标候选中位数相对基线改善 ≥10%，且至少两轮同向；或使用测量前写明的绝对判据
  （如 `max(cand) ≤ 0.90 × min(base)`）。低于门槛默认不合入。
- 例外：只有用户明确批准才可放行，记录用户原文、理由、补偿实验与影响范围，并在表格标「例外」。
  不得事后把「绝对目标」改称「报告项」（R5）。
- 累积发布：若要允许单轮 <10%，必须在批次开始前声明「发布级门槛」——上一版 vs 本批
  endpoint A/B 改善 ≥10% 且无回归，每轮机制核验通过；不得在轮次结束后才发明这条规则。
- 耐久/恢复变更（fencing、journal/audit 提交时点、恢复路径、隔离释放）额外要求：崩溃恢复
  E2E 通过（在定义的 kill 点重启，验证无丢失/重复、审计链连续、隔离正确）才能合入；
  没有 E2E 只能留在实验分支或默认关闭的 flag 后。R10/R11/R12 的耐久语义变更在合入时没有
  这个证据，是本会话最大的未闭合风险。
- 回归门：其余场景不得出现 >10% 且可复现的退化；方向不可确认时写「不可确认」，并做机制核对。
- 机制核对：用 `git diff --stat <base>..<cand>` 确认改动范围能/不能影响被比较路径；
  若 diff 不含该路径，必须明确写「机制上不可能由本轮引起」。
- 不变量：wire 字节数、行数、结果内容、审计链连续性与条数、`audit fsync / 请求`、
  seats/permits、错误码与 `warnings`。任何一项变化都要解释。

**噪声与退化**

- 先看同版本重复运行的离散度；离散度接近或超过效应量时，增加配对轮次，而不是下结论。
- 环境出现启动失败、reconcile 超时、`outcome_unknown`、审计不可用等异常时，本轮测量作废；
  先恢复环境，再重测。恢复不了就换独立新卷重建环境，旧卷原样保留。
- 不要在同一卷上无限累积写负载后继续比较：数据增长本身会改变基线。

**统计口径**

- 报告写清楚：运行次数、配对方式、中位数、范围、离群轮次，以及百分比的分母。
- 每轮数字必须用本轮候选二进制现算，不得复用上一版本或其他测量窗口的结果当本轮结果——
  数据增长与环境漂移会让旧数字不再对应本轮基线；跨测量窗口只比结构（倍率/方向），不比绝对值。
- 性能验收不宣称容量、公平性或长期稳定性；没有专门容量实验就不写「可承载」。

## 记录规范（CLAUDE.md）

在 Issue 28 实验表追加一行：分支/commit（merge）、方案一句话、实测结论、状态（合入 / 已 reset 并记录失败原因）。

随后追加一节，至少包含：

- 方案与改动边界（哪些文件、为什么不会影响其他路径）。
- 验收数字：场景、协议、样本数、中位数、改善百分比、判据是否满足。
- 限速器、机制计数器、上限探针与 Gate 0 结果。
- 配置偏离：配额、耐久模式、工具链、观测器、未进仓库的脚本；平台/worker 二进制 SHA256。
- 回归门：复测了哪些场景、结果、哪些不可确认及原因。
- 正确性：新增测试、差分/逐字节核对、微基准（如有）。
- 测试命令与结果（格式、构建、定向测试、离线用例）。
- 剩余风险与未测量项（工具链偏离、已知缺口、环境事件）。
- 若本轮中性/失败：写明「在什么限速器下、什么配置下中性」，以及复测触发条件；
  不要写「此路不通」——限速器变化后同一改动可能重新有效（R19→R32）。
- 环境事件若与代码无关，明确写「未归因本轮」。

禁止：把未跑的场景写成 PASS；把投影/字节预算写成实测；用单次运行代替同向复跑；
删除失败轮次的证据链接；把观测器绝对值或计划写成结果。

## 发版节奏

**时机**：一批（≥1 项）经证实且已合入 `main` 的改进之后；用户要求发版时；
或需要对外交付镜像时。发版前确认：`main` 工作区干净、文档已记录、已知缺口未扩大。

**发布前验收**

- 做上一版 vs 新版的 endpoint A/B：平台与 worker 一起换，同 harness、同数据、每侧新卷、
  逐轮交替；报告逐场景 PASS/FAIL、失败数与已知缺口，不只报累计倍率。
- 用仓库内 harness 跑默认配额的主场景；容量实验的非默认配额数字单独标注，不混入发布结论。
- 发布报告列出未修的正确性/契约缺陷（如 R9 的 502 `outcome_unknown`）与 workaround，
  不能只列 E1 known-gap。
- 等 CI 完成并核对镜像、manifest、release 后再宣布发布；P0/矩阵完成前只能说「已触发」。

**步骤**

1. bump：`prototypes/v1/Cargo.toml` 与 `prototypes/v1/Cargo.lock` 的
   `peri-loom-v1` 版本一致递增；提交 `chore(release)：vX.Y.Z`，正文列本轮收益与边界。
2. 推送 `main`。
3. 打 annotated tag（`git tag -a vX.Y.Z -m "vX.Y.Z"`）并推送；工作流要求
   `RELEASE_TAG == v$version`，tag 必须在 bump 之后。
4. `v1-image` 会先跑发布门禁（P0 + 官方 SDK 矩阵），再构建多架构镜像并创建 preview release；
   用 `gh run list --workflow=v1-image.yml` 取 run id，`gh run watch <id> --exit-status` 跟踪。
5. 完成后核对：run 成功、manifest list 与两个平台镜像存在、release 已创建。
   失败时先看失真的 job（`check` / `baseline` / `build`），修因后重新 bump + tag，
   **不删除、不移动已推送的 tag，不 force-push**。

## 反范式（本会话已验证，看到就停）

- 先改代码后核机制：R28 的空快照让 6 轮 A/B 测出 +5.4% 假收益。
- 把「减少工作量/锁获取次数」当收益：R15/R19/R22/R29/R33 都没换来吞吐。
- 在未决栈加深的前提下做提交/等待流水线：R14/R21 分别 −25%/−24%。
- 把一次有序等待拆成跨锁往返：R16/R29 分别 −19%~−29%/−25.6%。
- 微基准有效就合入：R13 的 `fdatasync` 微基准 1.42→0.84ms，生产路径无收益。
- 选更慢的基线窗口或单轮下结论：R5 的 verifier 已判 FAIL，协调者改判后合入。
- 观测器开着做 A/B 并对外汇报绝对值：R31/R32/R34/R36 的相位/耐久观测器会压低吞吐、
  放大请求计数，只能用于归因。
- 同卷累积负载后继续比较：R13 已修正为同容器连续采样 + 中位数/分布。
- 删除失败证据/卷：R6/R7 期间旧卷被清理、`/tmp` 证据在磁盘事故中处于高风险状态。
- 发布只报累计倍率、不报逐场景 FAIL：v1.1.27 的 endpoint A/B 是 +1636%，
  但 F1 仍超 13ms 目标。

## 红线与故障处理

- 不 force-push `main`；不 `commit --amend`；不删 tag；不删失败证据。
- 不手工修改签名启动记录、stop/terminal proof、ownership marker、authority seal。
- launcher 的 fail-closed 是设计行为：`requires_operator`、`operation_incomplete`、
  dirty marker/seal 都不是「故障」，不得用清 marker、强启、删除卷来绕过。
- 容器/卷进入需要 S05 evidence 的状态时：保留现场（先 `docker logs` 抓日志再删容器），
  换新卷重建环境继续实验；把事件写进「当前交付缺口」，不要当作已修复。
- 构建/压测前做资源预检（磁盘、内存、Docker VM）；低于阈值先清理或停止，不硬跑。
  测量期间不并行跑镜像构建、CI 或其他重负载。磁盘/VM 事故后只报告、不擅自重启/修复
  其他项目的容器或卷；把受保护容器清单写进记录。
- `/tmp` 不是证据的唯一副本；卷、marker、proof、失败样本不得在未确认的情况下删除。
- 性能轮发现的正确性/契约缺陷（如 502 误分类）不得静默挂起：开独立修复任务，
  发版前列入 known-gap 或修掉。
- 密钥只在环境变量或私有文件中流转；任何含 `Authorization` 的输出替换为
  `Bearer <REDACTED>`；连接文件不可公开或写入文档。
- 性能数字只对被测二进制与工具链负责；发布镜像按仓库固定工具链构建时，
  要注明实测工具链与发布工具链是否一致。
